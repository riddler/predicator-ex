# Research: the store opcode and Predicator.execute/2 (px-tbv.2)

**Date**: 2026-08-08T12:56:52-0600
**Git Commit**: 8a0ce8fe60e69eb0f43a71b05682fd797ec42107
**Branch**: px-tbv.2-store-opcode-execute
**Beads Issue**: px-tbv.2

## Research Question

px-tbv.2 adds compilation and execution for the statement layer:

- `["store", n]` pops n lhs segment values plus a value, calls
  `ContextLocation.put/3` against the evaluator's context, and replaces it.
- lhs computed segments compile as ordinary expressions pushing segment values
  ahead of the store.
- A statement boundary compiles to `["pop"]`, discarding expression-statement
  values.
- `Predicator.execute(program_or_source, ctx)` returns
  `{:ok, %Context{}} | {:error, e, %Context{}}`.
- Errors abort the sequence; the third tuple element is the context as of the
  last successfully completed statement. **Not rollback** - px-h66 verified
  against W3C SCXML 1.0 §4.9 and IRP test 156 that SCXML is stop-on-error
  *without* rollback, so an all-or-nothing processor is non-conformant.

This document maps what exists today: the statement AST px-tbv.1 landed, the
compiler and visitor emission path, the VM loop and its error channel, the
write algorithm, the Context struct, the ISA spec and its sync harness, the
conformance corpus, and the public façade `execute/2` will sit beside. It
describes; it does not design.

## Summary

Twelve findings carry the weight.

1. **px-tbv.1 has landed in full.** `{:program, [statement], pos}` and
   `{:assignment, lhs, rhs, pos}` exist (`parser.ex:169,183`),
   `Parser.parse_program/2` (`parser.ex:361`) and `Predicator.parse_program/2`
   (`lib/predicator.ex:518`) are the statement entry points, and `=` is a hard
   parse error in expression position (`parser.ex:694-700`).

2. **The assignment lhs is the raw access chain, deliberately.** It is the same
   `{:identifier,...}` / `{:property_access,...}` / `{:bracket_access,...}`
   subtree `parse_postfix/1` builds for any expression, unmodified. A bracket
   key is an arbitrary sub-expression - `a[k+1] = 1` stores
   `{:arithmetic, :add, ...}` in the key slot. The chain's **depth** is the
   `n` that `["store", n]` needs, and it is derivable structurally at compile
   time (`parser.ex:158-169`).

3. **The ISA is at v3, not v2, and v3 is already minted.** `@isa_version 3`
   (`instructions.ex:45`); `docs/isa.md:58` says `Current version: **ISA v3**`;
   §7's history table (`isa.md:467-473`) records v3 as `-` introduced, `and`/`or`
   retired, shipped in 4.0.0. The bead's description ("this is the third new
   opcode in [3.7's ISA v2]") is stale on both counts. **Whether `store`/`pop`
   join v3 or mint v4 is unstated anywhere** - see Open Questions.

4. **Tier 6 "statements" already exists and is empty**, reserved for `store` and
   `pop` (`isa.md:197`, `generator.ex:43-50`). §6 reserves both names verbatim
   (`isa.md:434-447`). §2 "Two execution modes" (`isa.md:117-152`) already
   specifies statement mode's halt contract, including that `empty_stack` is
   never raised in statement mode and that the partial context is a host-API
   property, not a VM guarantee.

5. **The evaluator's context is read-only today.** No `execute_instruction/2`
   clause ever writes `%__MODULE__{evaluator | context: ...}`. `context` appears
   only in the typespec (`evaluator.ex:26`), the struct default (`:54`),
   doctests, and the `evaluate/3` initializer (`:231`). `store` would be the
   first context-writing opcode in the VM's history.

6. **The VM already returns the final state on error, and already has a
   state-preserving entry point.** `run_state/1` (`evaluator.ex:287-295`)
   returns `{:error, error_struct, evaluator}` where `evaluator` is the
   **pre-step** state, and `run_prepared/1` (`:87-104`) is the public
   `{:ok, result, final} | {:error, error, final}` surface `evaluate/3` already
   uses. The three-element error tuple px-h66 wants exists one layer down.

7. **`ContextLocation.put/3` takes a flat path, never an AST** -
   `@spec put(Types.context(), location_path(), term()) :: put_result()`
   (`context_location.ex:206`), where `location_path :: [binary() | integer()]`
   (`:73`) and `put_result :: {:ok, Types.context()} | {:error, LocationError.t()}`
   (`:88`). Its errors are `:not_assignable` (empty path), `:not_a_container`,
   and `:invalid_index`. `store` popping n segment values yields exactly that
   flat path.

8. **`Context.assign/3` is the second entry point to the same algorithm**
   (`context.ex:173-180`): resolve a path (list passed through, string parsed via
   `ContextLocation.resolve_expression/2`), then `put/3`, then rebind `data`.
   `store` would be the third. The AC's "one write algorithm, three entry
   points" is already two-thirds true.

9. **`InstructionsVisitor` has no clause for `:program` or `:assignment` and no
   catch-all** - an unhandled node raises `FunctionClauseError`
   (`instructions_visitor.ex:116-277`). `StringVisitor` already has both clauses
   (`string_visitor.ex:265-271`) and a `@level_statement 0` precedence
   (`:79,389-390`). `Compiler.to_string/2` and `Visitor.accept/3` already accept
   `Parser.program()`; `Compiler.to_instructions/2` does **not**.

10. **The jump opcodes are the existing template for a compile-time computed
    operand.** `offset = length(right_instructions) + 1`
    (`instructions_visitor.ex:182,194`) - the operand is derived by counting the
    annotated sub-list, which is exactly the shape `["store", n]`'s `n` needs.
    `["call", name, arity]` (`:260`) is the only 2-operand instruction emitted
    today, and `arity` is likewise a compile-time count.

11. **Four guard tests exist specifically for this bead to flip.**
    `test/predicator/instructions_test.exs:210,219` assert `store` and `pop` are
    unknown opcodes; `test/predicator/parser_test.exs:1772,1780` assert
    `Compiler.to_instructions/2` raises `FunctionClauseError` on a program and on
    an assignment AST. All four carry comments naming px-tbv.2.

12. **Adding an opcode owes the corpus a case or a documented exclusion, and
    that is gate-enforced.**
    `test/predicator/conformance/opcode_coverage_test.exs:33-45` fails naming any
    opcode in `Instructions.opcode_set(isa_version())` with no case, and
    `corpus_freshness_test.exs:19-30` fails if `conformance/corpus/*.json` and
    `manifest.json` are not byte-identical to a fresh `mix corpus.generate`.
    `manifest.json` records `isa_version` (currently `3`) and a `corpus_hash`,
    both of which move when the ISA does.

## Detailed Findings

### 1. The statement AST px-tbv.1 produced

**The types** (`lib/predicator/parser.ex`):

```elixir
@type assignment :: {:assignment, ast(), ast(), position()}       # :169
@type statement :: assignment() | ast()                            # :174
@type program :: {:program, [statement()], position()}             # :183
@type program_result ::
        {:ok, program()} | {:error, binary(), pos_integer(), pos_integer()}  # :188-189
```

`ast/0` is the unchanged 17-shape union at `:139-156`. **Neither `assignment`
nor `program` is a member of `ast/0`** - that is deliberate, so an expression
consumer's pattern match never has to widen (`parser.ex:176-182`). `position/0`
(`:200`) is `Types.position() | Types.span() | nil`, the same trailing slot
every node carries.

**The lhs is the raw access chain.** The typedoc at `parser.ex:158-168` states
it outright:

> `location` is the raw access chain the parser built - an `{:identifier, ...}`
> optionally wrapped in any number of `{:property_access, ...}` and
> `{:bracket_access, ...}` nodes. It is kept as a chain rather than flattened to
> a path because a bracket key may be an arbitrary expression, resolvable only
> against a context; `Predicator.ContextLocation.resolve/2` does that at
> runtime. The chain's depth is the segment count `["store", n]` needs
> (ADR-0001).

`user.items[0].name = 'Ada'` parses to a four-deep chain:

```elixir
{:assignment,
 {:property_access,
   {:bracket_access,
     {:property_access, {:identifier, "user", {1, 1}}, "items", {1, 5}},
     {:literal, 0, {1, 11}},
     {1, 10}},
   "name", {1, 14}},
 {:string_literal, "Ada", :single, {1, 21}},
 {1, 19}}                                  # the assignment's slot is the `=` token
```

`a[k+1] = 1` puts a full sub-AST in the bracket key slot:

```elixir
{:bracket_access,
  {:identifier, "a", {1, 1}},
  {:arithmetic, :add, {:identifier, "k", {1, 3}}, {:literal, 1, {1, 5}}, {1, 4}},
  {1, 2}}
```

This is the AC's "lhs computed segments compile as ordinary expressions" already
holding structurally: the key slot *is* an expression node the existing visitor
knows how to emit.

**`parse_program/2`** (`parser.ex:361-379`) builds state exactly as `parse/2`
does, captures `program_start_point/1` (`:386-392`) before parsing so the
program's point position is the first token rather than an interior operator,
runs `parse_statement/1`, loops through `parse_program_rest/2` (`:430-458`) on
`:semicolon`, and finishes with `finish_program/4` (`:402-413`), which reapplies
`parse/2`'s "did we consume everything" gate and reports
`"Unexpected token ... after statement"`.

`parse_statement/1` (`:462-470`) probes:

```elixir
defp parse_statement(state) do
  case try_parse_assignment(state) do
    {:ok, _ast, _state} = ok -> ok
    {:error, _message, _line, _col} = error -> error
    :not_assignment -> parse_expression(state)
  end
end
```

`try_parse_assignment/1` (`:481-499`) parses an **addition**-level candidate
(one level below where `parse_comparison/1` intercepts `=`), and if the next
token is `:eq` hands off to `build_assignment/4` (`:512-526`), which gates on
`assignable_location?/1` (`:533-541`) - a purely syntactic recursive predicate
over identifier / property_access / bracket_access - and otherwise emits
`"Left side of '=' must be an assignable location - an identifier, a property
access, or a bracket access."` at the `=` token's position.

**Trailing `;` is accepted and dropped**; a doubled `;` is a parse error via the
ordinary primary-position path (`:425-429`). The program's span is
`{node_start(first_statement), node_end(last_statement)}` (`program_loc/3`,
`:418-423`), deliberately excluding a trailing `;`.

**`=` in expression position** (`parse_comparison/1`, `parser.ex:686-700`):

```elixir
{:eq, op_line, op_col, _len, _value} ->
  {:error,
   "'=' is not an equality operator - use '==' for equality. " <>
     "Assignment is only valid at the start of a statement.", op_line, op_col}
```

`:eq` remains a legal member of `comparison_op/0`; the parser simply stopped
producing it, so a hand-built `{:comparison, :eq, ...}` still compiles to
`["compare", "EQ"]`.

**Relevant `types.ex` definitions**: `instruction/0` is `[binary() | value()]`
(`:100`); `instruction_list/0` (`:107`); `context/0` is
`%{required(binary() | atom()) => value()}` (`:75`); `location_path/0` is
`[binary() | non_neg_integer()]` (`:202`) - note this is **narrower** than
`ContextLocation.location_path/0`, which is `[binary() | integer()]`
(`context_location.ex:73`) so a pre-write `-1` can be represented and rejected;
`evaluator_state/0` (`:223-229`) is a documentary map type that does **not**
match the real `%Evaluator{}` struct's field set; `result/0` (`:157`),
`internal_result/0` (`:166`), `scxml_result/0` (`:192`).

**`Compiler`** (`lib/predicator/compiler.ex`), three public functions:

| Function | Spec line | Accepts a program? | Delegates to |
|---|---|---|---|
| `to_instructions/2` | `:50` | **No** - `Parser.ast()` only | `Visitor.accept(ast, InstructionsVisitor, opts)` (`:52`) |
| `to_instructions_with_positions/2` | `:78-79` | **No** | `InstructionsVisitor.visit_with_positions/2` directly (`:81`) |

`Visitor.accept/3`'s spec is already `Parser.ast() | Parser.program()`

**`InstructionsVisitor`** (`lib/predicator/visitors/instructions_visitor.ex`).
`@type annotated :: {[binary() | term()], Types.position() | Types.span() | nil}`
(`:53`). Every `visit_annotated/2` clause returns `[annotated()]` - one pair per

left intact. `visit/2` (`:70-76`) strips positions; `visit_with_positions/2`
(`:95-110`) zips with `Enum.with_index/1` and drops `nil` entries.

| Node | Lines | Emits |
|---|---|---|
| `:literal` | 118-120 | `["lit", value]` |
| `:string_literal` | 122-125 | `["lit", value]` |
| `:identifier` | 127-129 | `["load", name]` |
| `:property_access` | 131-135 | left ++ `["access", property]` |
| `:comparison` | 137-144 | left ++ right ++ `["compare", op]` |
| `:arithmetic` | 146-153 | left ++ right ++ `[op]` |
| `:unary` | 155-161 | operand ++ `[op]` |
| `:bracket_access` | 163-171 | object ++ key ++ `["bracket_access"]` |
| `:logical_and` | 173-186 | left ++ `["jump_if_falsy_or_pop", n]` ++ right |
| `:logical_or` | 188-198 | left ++ `["jump_if_true_or_pop", n]` ++ right |
| `:logical_not` | 200-206 | operand ++ `["not"]` |
| `:list` | 208-230 | all-literal fast path `["lit", [...]]`, else ++ `["make_list", n]` |
| `:object` | 232-243 | `["object_new"]` ++ per-entry ++ `["object_set", key]` |
| `:membership` | 245-252 | left ++ right ++ `[op]` |
| `:function_call` | 254-263 | args ++ `["call", name, arity]` |
| `:duration` | 265-270 | `["duration", units]` |

**No catch-all clause and no error channel.** `visit/2`'s spec is
`:: [[binary() | term()]]` - a bare list, not `{:ok, _}`. An unhandled node
raises `FunctionClauseError`, which is the deliberate gap
`test/predicator/parser_test.exs:1766-1786` pins.

**The computed-operand template** (`:173-186`, offset at `:182`):

```elixir
defp visit_annotated({:logical_and, left, right, position}, opts) do
  left_instructions = visit_annotated(left, opts)
  right_instructions = visit_annotated(right, opts)
  offset = length(right_instructions) + 1
  jump_instruction = [{["jump_if_falsy_or_pop", offset], position}]

  left_instructions ++ jump_instruction ++ right_instructions
end
```

The comment at `:178-179` records that the annotated list holds one entry per
instruction, so offset arithmetic is unchanged from the plain-list era. `["call",
function_name, length(arguments)]` (`:260`) is the only 3-element instruction
emitted anywhere.

**`StringVisitor` already handles both statement nodes**
(`string_visitor.ex:265-271`):

```elixir
defp do_visit({:program, statements, _position}, opts) do
  Enum.map_join(statements, "; ", &do_visit(&1, opts))
end

defp do_visit({:assignment, lhs, rhs, _position}, opts) do
  "#{do_visit(lhs, opts)} = #{do_visit(rhs, opts)}"
end
```

with `precedence/1` clauses returning `@level_statement 0` (`:79`, `:389-390`).
It also has no catch-all.

### 3. The evaluator: state, loop, error channel

**The struct** (`lib/predicator/evaluator.ex:22-33` typespec, `:49-60`
defstruct): `instructions` (a list on construction, converted to a tuple with
`:erlang.list_to_tuple/1` on the first `step/1` and cached alongside `size`,
`:303-309`), `instruction_pointer` (0-based index), `stack` (a plain list,
head-first LIFO; `push_stack/2` at `:662-665` is `[value | stack]`), `context`
(a plain map), `functions`, `positions`, `halted`, `unbound_loads`,
`on_unbound`, `size`.

**The loop.** `run_state/1` (`:287-295`) is the driver:

```elixir
defp run_state(%__MODULE__{halted: true} = evaluator), do: {:ok, evaluator}

defp run_state(%__MODULE__{} = evaluator) do
  case step(evaluator) do
    {:ok, new_evaluator} -> run_state(new_evaluator)
    {:error, error_struct} when is_struct(error_struct) -> {:error, error_struct, evaluator}
  end
end
```

`step/1` (`:302-326`) halts when `finished?/1` (`ip >= size`), otherwise fetches
via `:erlang.element/2` and pipes
`execute_instruction/2 |> advance_instruction_pointer/1 |> attach_position/2`.

**Representative clauses:**

```elixir
defp execute_instruction(%__MODULE__{} = evaluator, ["lit", value]) do   # :376-378
  {:ok, push_stack(evaluator, value)}
end
```

```elixir
defp execute_compare(%__MODULE__{stack: [right | [left | rest]]} = evaluator, operator) do
  result = compare_values(left, right, operator)                          # :552-560
  {:ok, %__MODULE__{evaluator | stack: [result | rest]}}
end

defp execute_compare(%__MODULE__{stack: stack}, _operator) do
  {:error, EvaluationError.insufficient_operands(:comparison, length(stack), 2)}
end
```

```elixir
defp execute_jump_if_falsy_or_pop(%__MODULE__{stack: [top | _rest]} = evaluator, offset)
     when top == false or top == :undefined do                            # :1287-1305
  {:ok, jump_to(evaluator, offset)}
end
```

`jump_to/2` (`:1329-1332`) sets `ip + offset - 1` so the unconditional `+1` in
`advance_instruction_pointer/1` lands on `ip + offset`.

**Error surfacing.** Every clause returns `{:ok, %__MODULE__{}} | {:error, struct}`
(`@spec` at `:374`). `advance_instruction_pointer/1` (`:543-550`) passes
`{:error, _}` through unchanged; `attach_position/2` (`:333-338`) stamps the
failing instruction's position/span from the `positions` table via
`attach_error_position/2`. `run_state/1` then returns
`{:error, error_struct, evaluator}` with the **pre-step** state (comment at
`:283-286`: it "keeps the state a failing step would otherwise discard") and
stops - it never calls `step/1` again. **That is stop-on-error with the surviving
state already in hand.**

**Public entry points:**

- `run_prepared/1` (`:87-104`) - `{:ok, result, final} | {:error, error, final}`.
  It is also where `empty_stack` is manufactured, the one error made outside
  `execute_instruction/2`:

  ```elixir
  {:ok, %__MODULE__{stack: []} = final} ->
    {:error,
     EvaluationError.new("Evaluation completed with empty stack", "empty_stack", :evaluate),
     final}
  ```

  This is the expression-mode rule `docs/isa.md:128-137` says must never fire in
  statement mode.
- `evaluate_prepared/1` (`:113-119`) - drops the final state,
  returns `Types.internal_result()`.
- `evaluate/3` (`:226-236`), `evaluate!/3` (`:258-268`), `run/1` (`:275-281`),
  `step/1` (`:302-326`), `unbound_loads/1` (`:149-152`),
  `unbound_loads_with_locations/1` (`:182-183`), `merge_functions/1` (`:69-76`),
  `resolve_key/2` (`:1190-1193`).

**The context is read-only.** Reads happen in `load_from_context/2`
(`:1143-1150`), a plain string-key `Map.get(context, name, Undefined.value())`
called from the `["load", name]` clause (`:381-393`); function calls receive
`evaluator.context` as a read-only third argument (`:1087`, `call_function/4` at
`:1112-1130`). **No clause writes it.**

**ISA checking at runtime.** The evaluator never calls `required_isa/1`. Its only
ISA touchpoint is the retired-opcode fallback (`:503-515`), reached only after
every live clause failed:

```elixir
defp execute_instruction(%__MODULE__{}, [opcode | _operands] = unknown)
     when is_binary(opcode) do
  case Instructions.retired_in(opcode) do
    {:ok, version} when is_integer(version) -> retired_opcode_error(opcode, version)
    _live_or_unknown -> unknown_instruction_error(unknown)
  end
end
```

Unknown opcodes become
`EvaluationError.new("Unknown instruction: #{inspect(unknown)}", "unknown_instruction", :evaluate)`
(`:533-541`).

### 4. The write algorithm and the Context struct

**`ContextLocation.put/3`** (`context_location.ex:206-215`):

```elixir
@spec put(Types.context(), location_path(), term()) :: put_result()
def put(context, path, value)

def put(context, [], _value) when is_map(context) do
  {:error, LocationError.not_assignable("empty location path", [])}
end

def put(context, path, value) when is_map(context) and is_list(path) do
  do_put(context, path, value, [])
end
```

`location_path :: [binary() | integer()]` (`:73`);
`put_result :: {:ok, Types.context()} | {:error, LocationError.t()}` (`:88`).

Write-time errors:

| Error | Constructor | Site |
|---|---|---|
| empty path | `LocationError.not_assignable("empty location path", [])` | `:209-211` |
| interior segment holds a scalar | `LocationError.not_a_container(...)` | `vivify/3`, `:391-393` |
| negative list index, reading | `LocationError.invalid_index(...)` | `fetch_in/3`, `:404-406` |
| non-integer key against a list, reading | `LocationError.not_a_container(...)` | `fetch_in/3`, `:408-410` |
| negative list index, writing | `LocationError.invalid_index(...)` | `set_in/4`, `:422-424` |
| non-integer key against a list, writing | `LocationError.not_a_container(...)` | `set_in/4`, `:426-428` |

Write behavior: ECMAScript-like auto-vivification - a missing/`nil`/`:undefined`
interior slot becomes `[]` when the *next* segment is an integer and `%{}`
otherwise (`vivify/3`, `:378-393`); an integer past a list's end pads with
`Undefined.value()` (`write_at/4`, `:434-436`); the leaf is always overwritten
(`do_put/4`, `:364-366`); string and integer keys only, never atoms (caveat at
`:172-180`).

**`resolve/2`** (`:125-131`) turns an AST node into a flat path *against a
context*, because a bracket key can be a variable.
`resolve_bracket_key/2` (`:311-356`) accepts a string literal, an integer
literal, a negated integer literal, and an identifier whose bound value is a
string or integer; **anything genuinely computed falls to the catch-all and
returns `LocationError.computed_key(...)`** (`:350-356`). So `a[k+1] = 1` is
rejected by `resolve/2` today - which is precisely why the AC routes computed
segments through the compiler and the stack instead.

`resolve_expression/2` (`:142-156`) composes tokenize -> `Parser.parse/2` ->
`resolve/2`, wrapping lexer/parser failures as `%ParseError{}`.

**`Predicator.Context`** (`lib/predicator/context.ex:38-45`):

```elixir
@type t :: %__MODULE__{
        data: Types.context(),
        functions: %{binary() => {Evaluator.function_arity(), function()}},
        on_unbound: on_unbound()
      }

defstruct data: %{}, functions: %{}, on_unbound: :undefined
```

`new/2` (`:79-86`) normalizes `data` (atom keys to string keys, `nil` to
`Undefined.value()`, recursive through maps and lists, structs untouched -
`normalize_value/1` at `:195-206`, `normalize_map/1` at `:220-237`), merges
builtin functions via `Evaluator.merge_functions/1`, and validates `on_unbound`.
`bind/3` (`:118-121`), `bound?/2` (`:146-149`).

`assign/3` (`:173-180`) - the second entry point to the write algorithm:

```elixir
@spec assign(t(), binary() | ContextLocation.location_path(), Types.value()) ::
        {:ok, t()} | {:error, struct()}
def assign(%__MODULE__{data: data} = context, path_or_expression, value) do
  with {:ok, path} <- resolve_path(data, path_or_expression),
       {:ok, new_data} <- ContextLocation.put(data, path, value) do
    {:ok, %{context | data: new_data}}
  end
```

### 5. `docs/isa.md`: version, opcode format, reservations

**Current version: ISA v3** (`isa.md:58`). Structure: preamble (1-16),
§1 Versioning (18-62), §2 Execution model incl. "Two execution modes" (64-152),
§3 Value types (154-166), §4 The opcode table incl. Tiers / Opcodes / Retired
(168-252), §5 Per-opcode semantics and errors (254-432), §6 Not in the ISA
(434-465), §7 Version history (467-485), §8 Conformance corpus (487-503).

**An opcode is a row, not a block.** The §4 table (`:207-233`):

```text
| Opcode | Operands | Pops | Pushes | ISA | Tier | Emitted by compiler | Removed in |
|---|---|---|---|---|---|---|---|
| `make_list` | count (int >= 0) | count | 1 | v2 | 3 | yes | - |
```

with a matching §5 prose bullet naming the private evaluator functions that
implement it (`:391-397`). An opcode also appears in the **tier-names table**
(§4, `:190-197`) and the **version-history table** (§7, `:469-473`). A reserved
but unimplemented name lives in **§6** instead of the opcode table.

**§2 "Two execution modes"** (`:117-152`) is already written for this bead:

> - **Statement mode** - the result is **the context at halt**, not a stack
>   value. The stack is scratch space between statement boundaries: a
>   well-formed statement program ends each statement with a `store` or a `pop`
>   and therefore halts with an **empty stack by design**. That is a normal
>   halt. `empty_stack` is an expression-mode rule and is never raised in
>   statement mode. A non-empty stack at halt is likewise not an error in
>   statement mode; the residue is discarded [...]

> A statement program that halts on an error has no result. Whether the
> partially applied context from the statements that completed before the error
> is kept or discarded is a property of the host API, not of the VM; the VM
> specifies only that execution stops at the failing instruction.

> A host may additionally surface the value of the program's last expression
> statement alongside the context. That is a host-API convenience, not an ISA
> guarantee - the statement boundary's `pop` discards it as far as the VM is
> concerned.

> Until `store` and `pop` exist (§6), no evaluator has a statement entry point
> and no program is a statement program.

**§6's reservation** (`:434-447`), verbatim:

> - `["store", n]` - specified by ADR-0001 for the 4.0 statement layer, not
>   implemented and not accepted by any current evaluator clause. Reserved
>   name, tier 6.
> - `["pop"]` - the statement-boundary opcode of the same 4.0 statement layer:
>   it discards an expression statement's value so the next statement begins
>   from a clean stack. Not implemented and not accepted by any current
>   evaluator clause. Reserved name, tier 6, beside `store`. It is **not**
>   related to `jump_if_falsy_or_pop` / `jump_if_true_or_pop` [...]

§6 also still carries "A statement entry point. [...] no current evaluator
exposes one, so every program any implementation runs today is an expression
program" - a sentence this bead falsifies.

**Tier 6 exists and is empty** (`:197`):
`| 6 | statements | (none yet - reserved for `store` and `pop`) |`.

**§7's history table** (`:469-473`):

```text
| ISA | Opcodes introduced | Opcodes retired | Shipped in |
|---|---|---|---|
| v1 | everything not listed below | - | up to 3.6.x |
| v2 | `jump_if_falsy_or_pop`, `jump_if_true_or_pop`, `make_list` | - | 3.7.0 |
| v3 | - | `and`, `or` | 4.0.0 |
```

**§1's binding rules** (`:22-56`), abbreviated: an opcode's semantics never
change under its own name; adding an operand form is a new version but not a new
name; an additive version ships in a minor release; retirement mints the next
integer and takes a major release plus an upgrade path; **a version's opcode set
is a half-open interval and is fixed once minted**.

### 7. The conformance corpus

**Tiers** are a property of opcodes, never of value types
(`conformance/README.md:167-169`), and are cumulative (`:173-179`). The tier
names table lives in `lib/predicator/conformance/generator.ex:43-50`
(`@tier_names`), duplicated for display in `coverage.ex:136-143`, mirrored in
`docs/isa.md:190-197`, and materialized into `conformance/manifest.json`. The
generator's own comment (`generator.ex:41-42`) records that tier 6 "statements"
is a placeholder for when `store` lands and currently has no opcodes.

**Authored-case format.** Files: `access.json`, `arithmetic.json`,
`comparison.json`, `core.json`, `dates.json`, `durations.json`, `errors.json`,
`functions.json`, `legacy.json`, `membership.json`, `objects.json`,
`short_circuit.json`. A complete entry (`conformance/cases/core.json:2-7`):

```json
{
  "id": "core/literal-integer",
  "source": "42",
  "expected": { "result": 42 },
  "notes": "the simplest possible tier-1 case: a bare literal, no context"
}
```

Fields, per `conformance/schema/case.json`: `id` (required, stable forever);
exactly one of `source` (an expression string) or `instructions` (a raw list, for
evaluator-only cases the compiler cannot produce); `context` (tagged-value
encoded, defaults `{}`); `expected` as `{"result": ...}` or
`{"error": {"type":..., "reason":...}}` - an **assertion** verified against the
real pipeline at generation time (`generator.ex:406-436`); optional `tier`
(asserted against `max(tier(opcode))`, `generator.ex:442-483`); optional
`features`; `notes`.

**`mix corpus.generate`** (`lib/mix/tasks/corpus.generate.ex`) reads
`conformance/cases/*.json`, runs each case through the real compiler and
evaluator via `Predicator.Conformance.Generator.generate/1`, and writes
`conformance/corpus/tier-N.json` (one JSON object per line, sorted by id) plus
`conformance/manifest.json` with a computed `corpus_hash` (`hash_corpus/1`,
`:139-143`). Generated output **is committed**; `--check` (`:44-49`, `:152-168`)
regenerates in memory and raises on drift. A case that fails to generate aborts
the whole write (`:178-185`).

**`mix corpus.coverage`** is **not** the opcode gate. It statically scans the
ExUnit suite for literal `Predicator.evaluate/compile` calls and reports
opcode/operand *pattern* drift against the corpus, explicitly "never fails the
gate" (`lib/mix/tasks/corpus.coverage.ex:38-40`).

**The opcode gate is an ExUnit test**
(`test/predicator/conformance/opcode_coverage_test.exs:33-45`):

```elixir
def evaluate(expression, context, opts) when is_binary(expression) and is_map(context) do
  case Lexer.tokenize(expression) do                                          # :178-193
    {:ok, tokens} ->
      case Parser.parse(tokens, opts) do
```

`reject_positions_option!/1` (`:233-247`) raises `ArgumentError` if a caller

The private core (`:200-223`):

```elixir
defp evaluate_instructions(instructions, %Context{} = context, opts) do
  evaluator = %Evaluator{
    instructions: instructions,
    context: context.data,
    functions: context.functions,
    positions: Keyword.get(opts, :positions, %{}),
    on_unbound: context.on_unbound
  }

  case Evaluator.run_prepared(evaluator) do
    {:error, error_struct, final_evaluator} when is_struct(error_struct) ->
      {:error, unbound_or_type_mismatch(error_struct, final_evaluator)}

    {:ok, :undefined, final_evaluator} -> undefined_result(final_evaluator)
    {:ok, result, _final_evaluator} -> {:ok, result}
  end
end

defp evaluate_instructions(instructions, context, opts) when is_map(context) do
  evaluate_instructions(instructions, Context.new(context, opts), opts)
end
```

Note the shape: **a bare map is normalized into a `%Context{}` first**, and the
`%Context{}` clause is where the `%Evaluator{}` is built. `execute/2`'s
`{:ok, %Context{}}` return therefore has a natural source - the `%Context{}` the
evaluator was built from, with `data` replaced by the evaluator's final context.

`:undefined` into an `UndefinedVariableError` naming the unbound root;
`undefined_result/1` (`:296-302`) turns `{:ok, :undefined}` into an
`UndefinedVariableError` when the evaluator recorded unbound loads.

`evaluate!/3` (`:281-286`) raises a plain `RuntimeError`:
`raise "Evaluation failed: #{error_struct.message}"`.

## Architecture Documentation

**The pipeline is unchanged**: source -> Lexer -> Parser -> Compiler ->
Instructions -> Evaluator, with `StringVisitor` branching off for decompile
(`docs/architecture.md:12-18`). px-tbv.1 added a second parser entry point
without disturbing it.

**Errors are values** (ADR-0004, CLAUDE.md). Every evaluator instruction clause
returns `{:ok, state} | {:error, struct}`; nothing raises at a leaf. The two
exceptions in the current tree are both visitors - `InstructionsVisitor` and
`StringVisitor` have no catch-all and no error channel, which
`docs/plans/260807-px-tbv.1-statement-grammar.md:1038-1042` records as a known
convention gap worth its own bead.

**Programs stay flat and serializable** (ADR-0001). A statement program is an
ordinary instruction list; the mode lives at the entry point, never in the
artifact (`docs/isa.md:117-124`). `docs/plans/260807-px-z5m-pop-and-statement-halt.md:224-236`
records the rejected alternatives: a program header, and inferring the mode from
the presence of `store`/`pop` (unsound in both directions).

**`Predicator.Compiled` is the shape later entry points inherit.** ADR-0009's
Consequences (`0009:198-203`) pre-empt this bead explicitly:

> **Later entry points inherit the shape rather than reinventing it.**
> `Predicator.execute/2` (`px-tbv.2`) and any future compile-a-program path
> should return or accept the envelope rather than growing a fourth tuple
> element, which is a decision this ADR pre-empts rather than one those beads
> re-argue.

`docs/plans/260808-px-35i.5-compiled-envelope.md:240-241` repeats it from the
other side: "Not implementing `Predicator.execute/2` (px-tbv.2). ADR-0009
pre-empts its shape; building it is that bead's job."

**Area labels.** The bead carries `area:api, area:build, area:docs,
area:evaluator`. The work as mapped here also touches
`lib/predicator/visitors/instructions_visitor.ex` (`area:visitors`) and, if a
corpus case is authored, `conformance/**` and `test/predicator/conformance/**`
(`area:conformance`). `area:build` is already present and is exclusive, so the
bead lands alone regardless; per CLAUDE.md the honest fix for the two unlabeled
areas is to widen the label before merging rather than to notice it at merge
time.

## ISA Impact

**This bead adds two opcodes, `store` and `pop`, both already reserved at tier 6
(`docs/isa.md:434-447`, `:197`).**

Per ADR-0003 (`0003:191-195`) an ISA change owes a version bump, a `docs/isa.md`
entry, a corpus tier assignment, and a migration note if stored artifacts are
affected. Taking those in turn against the current tree:

- **Version.** The change is purely **additive** - no existing instruction list
  changes meaning, nothing is retired - so by `docs/isa.md:33-35` and
  `0003:90-97` it is a minor-release-shaped change that does not invalidate
  anything. **Whether it joins the already-minted v3 or mints v4 is not settled
  anywhere.** §1's "a version's set is fixed once minted" argues for v4; the fact
  that v3 has not shipped in a tagged release (`mix.exs` is at `@version "3.8.0"`,
  `git tag` tops out at `v3.8.0`, and §7 lists v3 as "Shipped in 4.0.0" -
  a release that does not exist yet) argues that v3's set is still open. See Open
  Questions.
- **`docs/isa.md` entries.** Two rows in §4's opcode table (`:207-233`), removal
  of the two §6 bullets (`:434-447`), the tier-6 cell (`:197`) changing from the
  prose placeholder to backticked names - which also removes the special case
  `isa_sync_test.exs:255-261` documents - §6's "A statement entry point [...] no
  current evaluator exposes one" sentence, §2's closing "Until `store` and `pop`
  exist (§6)" sentence (`:150-152`), and, if the integer moves, `:58`'s
  `Current version:` line and a new §7 row. §5 gains a prose bullet per opcode
  naming the private evaluator functions that implement them.
- **Corpus tier assignment.** Tier 6 already exists and is empty. Both opcodes
  are already specified as tier 6.
- **Migration note.** None owed. No stored artifact is invalidated: an existing
  expression program contains neither opcode and runs identically.

**What the harness forces to move together:** `@isa_version` /
`Current version:` (only if the integer moves), the `@opcodes` map, §4's opcode
table, §4's tier-names table, `@opcode_count 25` in `isa_sync_test.exs:30`, an
`execute_instruction/2` clause head per opcode (the regex at
`isa_sync_test.exs:290` requires the literal `defp execute_instruction(%__MODULE__{}..., ["name"` form),
§7's history table, `conformance/cases/*.json`, and the regenerated
`conformance/corpus/tier-6.json` + `manifest.json` (whose `isa_version` and
`corpus_hash` both change).

**One second-order effect worth naming:** `conformance/manifest.json`'s
`corpus_hash` is what a sibling's `RATCHET.md` registry pins against
(`RATCHET.md:129-171`). Regenerating the corpus changes that hash, which is a
normal consequence of a corpus change rather than a defect, but it is what a
sibling re-pins to.

## Open Questions

Recorded rather than resolved. No human was available to adjudicate, and
answering them is design work belonging to `/create-plan`, not to this
documentation pass.

1. **Do `store` and `pop` join ISA v3, or mint ISA v4?** This is the largest
   open question and nothing in the tree settles it. §1 says "a version's opcode
   set is fixed once minted" (`isa.md:47-51`), which argues for v4. But v3 has
   not shipped in a tagged release - `mix.exs` is at `3.8.0`, `git tag` tops out
   at `v3.8.0`, and §7 records v3 as "Shipped in 4.0.0", a release px-tbv.5 has
   not cut - which argues its set is still open and both opcodes belong in the
   same 4.0.0 version that retired `and`/`or`. The choice cascades into
   `@isa_version`, `isa.md:58`, §7's table, `isa_sync_test.exs`'s max-version
   test, `manifest.json`'s `isa_version`, and what a sibling's ratchet pins to.

2. **What exactly does `["store", n]` pop, and in what order?** ADR-0001 says
   "n path segments plus a value". Whether the value is pushed before or after
   the segments, and whether the segments are pushed root-first or leaf-first, is
   unspecified. The existing convention is that the stack holds operands
   reversed - `make_list` explicitly reverses them back (`isa.md:391-397`), and
   `compare` pops right then left (`:271-273`) - so there is a house convention
   but no statement of which one `store` follows.

3. **Does `store` push anything?** Every current opcode either pushes exactly one
   value or (the jumps) pushes none. If `store` pushes nothing, an assignment
   statement needs no trailing `pop` and only expression statements do; if it
   pushes the assigned value, every statement ends with `pop` uniformly.
   `docs/isa.md:131-133` says "a well-formed statement program ends each statement
   with a `store` or a `pop`", which reads as the former, but the opcode table's
   Pushes column has no entry yet.

4. **How does a `LocationError` from `put/3` become an evaluator error?**
   `LocationError` has no `:position` or `:span` field
   (`location_error.ex:58-62`), so `Errors.put_position/2` is a no-op on it
   (`errors.ex:52-54`), and the evaluator's `attach_position/2` would leave a
   store failure unpositioned. Whether `store` returns the `LocationError`
   directly, wraps it in an `EvaluationError`, or `LocationError` gains the
   position fields is unspecified.

5. **What does `execute/2` accept and return, exactly?** px-h66 fixes
   `{:ok, Context.t()} | {:error, error(), Context.t()}`, and ADR-0009 says later
   entry points should accept the envelope. But `execute/2`'s first argument is
   described in the bead as `program_or_source`, and there is no
   `compile_program/1` today - `compile/1` and friends all call `Parser.parse/2`,
   the expression entry point. Whether this bead also adds a program-compiling
   façade function, and whether `execute/2` accepts a `%Compiled{}`, is unstated.

6. **Where does the "last expression's value" come from?** The AC says the final
   context is the program's value "plus cheaply the last expression's value", and
   `isa.md:144-147` calls that a host-API convenience the VM's `pop` discards.
   Whether the host reads it off the pre-`pop` stack, whether the compiler omits
   the final `pop`, or whether `execute/2` simply does not surface it, is
   undecided - and the three choices differ in whether the emitted instruction
   list is uniform.

7. **Does `Compiler.to_instructions/2` widen to accept a program, or does a new
   function appear beside it?** `to_string/2` and `Visitor.accept/3` already
   accept `Parser.ast() | Parser.program()`; `to_instructions/2` and
   `to_instructions_with_positions/2` do not. Widening makes one function return
   instructions for two disjoint input types, which is the same shape px-tbv.1
   rejected for `parse/2` (its plan, Q1). A separate entry point would be the
   consistent echo.

8. **Does `InstructionsVisitor` gain an error channel here?** It returns a bare
   list and can only raise. `docs/plans/260807-px-tbv.1-statement-grammar.md:1038-1042`
   records this as worth a bead of its own; whether teaching it two new nodes is
   the moment to change that, or explicitly not, is a scope call.

9. **Does the corpus get tier-6 cases, and can it?** `conformance/schema/case.json`
   allows `instructions`-only cases, so a raw `[["lit", 1], ["lit", "a"], ["store", 1]]`
   can be authored. But every `expected` shape today is `{"result": ...}` or
   `{"error": ...}` - there is no "expected context" shape, and the generator
   checks results by running `Predicator.evaluate`-shaped paths
   (`generator.ex:406-436`). Whether tier 6 needs a new `expected` variant, a new
   generator path, or an exclusion entry is unaddressed anywhere.

10. **What happens to the four guard tests, and to the `errors.json`
    `empty_stack` note?** The two `instructions_test.exs` guards must flip to
    positive assertions; the two `parser_test.exs` `FunctionClauseError` guards
    must be replaced by instruction assertions. px-z5m assigned the `empty_stack`
    note correction here (`260807-px-z5m-pop-and-statement-halt.md:181-184`), but
    that note lives in an authored corpus case, so editing it regenerates the
    corpus and moves `corpus_hash` - which is a real cost to weigh, not an
    obviously free edit.
