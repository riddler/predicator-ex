# Research: the statement grammar and parser (px-tbv.1)

**Date**: 2026-08-07T19:04:08-0600
**Git Commit**: babed481129fac22a16d594526cd28ec38613e57
**Branch**: px-tbv.1-statement-grammar
**Beads Issue**: px-tbv.1

## Research Question

px-tbv.1 adds a statement grammar and parser:

```text
program    := statement (";" statement)* [";"]
statement  := assignment | expression
assignment := location "=" expression   -- lhs must parse as an assignable location
```

`=` leaves the expression grammar entirely; `==` and `===` become the only
equality operators; a bare `=` in expression position must be a pointed parse
error rather than a silent reinterpretation. Scope is parser-and-grammar only:
no compiler, no evaluator, no opcodes.

This document maps what exists today - the lexer's `=` handling, the parser's
entry points and precedence chain, the AST node union, the assignable-location
machinery, every AST consumer, the test surface that pins current behavior, and
the prose that bears on the change. It describes; it does not design.

## Summary

Eight findings carry the weight.

1. **The AST node union lives in `parser.ex`, not `types.ex`.** All 17 shapes are
   declared at `lib/predicator/parser.ex:132-149`, and the trailing slot of every
   one is `position() | span() | nil` (`parser.ex:160`). px-tbv.8's deletion of
   the legacy shapes is complete in `lib/` - `bare_ast/0`, `bare_object_key/0`,
   `strip_positions/1`, and `ensure_positions/1` appear nowhere in source, only in
   plan docs and the changelog.

2. **`Predicator.Parser.parse/2` is the only public parser entry point**, and its
   body is a single `parse_expression/1` call wrapped in a
   "did we consume everything" gate (`parser.ex:263-286`). There is no top-level
   loop, no `:program` production, no assignment node, and no semicolon anywhere
   in the grammar.

3. **The lexer already distinguishes `=`, `==`, `===` cleanly by maximal munch**
   (`lexer.ex:293-306`), emitting `{:eq, line, col, 1, "="}` for the bare form.
   **There is no `;` token.** A literal `;` falls to the catch-all at
   `lexer.ex:421-422` and produces `{:error, "Unexpected character ';'", line, col}`.
   Newlines are pure whitespace; the token stream carries no statement marker.

4. **`:eq` is currently indistinguishable from any other comparison operator in
   the parser.** It sits in the same guard list as `:gt`/`:lt`/... at
   `parser.ex:467-478`, falls through the `_other_op_type -> op_type` catch-all at
   `parser.ex:484-490`, and lands in `{:comparison, :eq, left, right, pos}` -
   the same shape `==` produces with `:equal_equal` in the operator slot.
   `InstructionsVisitor` maps both to `"EQ"` (`instructions_visitor.ex:280-289`).

5. **`warn_deprecated_equals/1` (`parser.ex:288-315`) is what this bead replaces.**
   It is a pre-parse `Enum.find/2` over the raw token list for the first `:eq`
   token, logging one `Logger.warning`, gated by
   `Application.get_env(:predicator, :deprecation_warnings, true) != false`. Its
   own leading comment already anticipates this bead:
   *"In 3.8 there is no assignment grammar, so every `:eq` token is
   expression-position; the statement grammar (px-tbv.1) must refine this check
   rather than inherit it."*

6. **The assignable-location machinery already exists and already consumes AST
   nodes.** `ContextLocation.resolve/2` (`context_location.ex:125-131`) walks
   `{:identifier, ...}` / `{:property_access, ...}` / `{:bracket_access, ...}`
   into a flat `location_path :: [binary() | integer()]`, and rejects all 11
   other node shapes with a `LocationError` naming why
   (`context_location.ex:220-309`). `put/3` (`context_location.ex:206-215`) takes
   that flat path, not an AST node. This is the exact predicate the bead's
   "lhs must parse as an assignable location" already has an implementation of.

7. **Only three modules pattern-match on AST tags** and would need a clause for a
   new node type: `InstructionsVisitor` (no catch-all - `FunctionClauseError`),
   `StringVisitor` (no catch-all - `FunctionClauseError`), and `ContextLocation`
   (has a catch-all at `context_location.ex:307-309`, so a new node silently
   becomes "not assignable"). `Visitor`, `Compiler`, `Evaluator`, and
   `lib/predicator.ex` are generic over `Parser.ast()` and need no per-tag change.
   `StringVisitor` renders `:eq` as `"="` and `:equal_equal` as `"=="`
   (`string_visitor.ex:276-277`) - two clauses that are the round-trip's whole
   `=` story.

8. **`docs/isa.md`'s "Two execution modes" is the newest and most authoritative
   prose, and several older documents disagree with it.** Section 6 also
   documents that no statement entry point exists in any implementation today.
   The conflicts are enumerated in the "Conflicts with the landed spec" section
   below.

## Detailed Findings

### Lexer (`lib/predicator/lexer.ex`)

**`=` family production, `lexer.ex:293-306`.** One `case rest do` doing
longest-match-first purely by clause order:

```elixir
?= ->
  case rest do
    [?=, ?= | rest3] -> token = {:strict_equal, line, col, 3, "==="} ...
    [?= | rest2]     -> token = {:equal_equal, line, col, 2, "=="} ...
    _rest            -> token = {:eq, line, col, 1, "="} ...
  end
```

The `!` family mirrors it at `lexer.ex:278-291`: `:strict_ne` (`"!=="`), `:ne`
(`"!="`), `:bang` (`"!"`). Same shape for `>`/`>=` (`lexer.ex:256-265`) and
`<`/`<=` (`lexer.ex:267-276`). There is no separate peek helper; the lookahead
*is* the pattern match on the head of the remaining charlist, and each branch
advances `col` by exactly the characters consumed.

**Token shape.** Every non-`:string` token is a flat 5-tuple
`{type, line, column, length, value}`, documented at `lexer.ex:35-39`; `:string`
is a 6-tuple carrying `:double | :single` (`lexer.ex:44`). The full `@type token`
union is `lexer.ex:40-87`. `value` for an operator is the literal lexeme
(`"="`, `"=="`).

**No semicolon.** A repo-wide grep for `semicolon` / `:semicolon` / a `;` clause
returns nothing. `;` falls to `lexer.ex:421-422`:

```elixir
_char -> {:error, "Unexpected character '#{[char]}'", line, col}
```

**Entry point.** `Lexer.tokenize/1` (`lexer.ex:155-160`) is the module's only
public function; `@type result :: {:ok, [token()]} | {:error, binary(), pos_integer(), pos_integer()}`
(`lexer.ex:92`). The token list always ends with an `:eof` tuple
(`lexer.ex:164-166`).

**Whitespace.** `lexer.ex:176-186`: space/tab advance the column, `\n` increments
`line` and resets `col`, `\r` is dropped outright. None emit a token. There is no
end-of-line or end-of-statement marker in the stream. A second helper,
`skip_whitespace/1` (`lexer.ex:577-582`), exists only for the identifier-followed-by-`(`
lookahead that promotes an identifier to `:function_name`.

**No operator attribute list.** There is no `@operators` or equivalent anywhere in
`lib/`. Operators are enumerated implicitly by `case char do` clauses
(`lexer.ex:174-423`), by `classify_identifier/1` (`lexer.ex:482-499`) for keyword
operators, and by the `token()` type union itself.

### Parser (`lib/predicator/parser.ex`)

**Public surface: one function.** `parse/2` at `parser.ex:263-264`, `@doc` at
228-262. `parse/1` exists only via `opts \\ []`.

```elixir
@spec parse([Lexer.token()], keyword()) :: result()
def parse(tokens, opts \\ []) when is_list(tokens) do
```

`@type result :: {:ok, ast()} | {:error, binary(), pos_integer(), pos_integer()}`
(`parser.ex:214`) - a bare 4-tuple, not a struct; the `%ParseError{}` wrapping
happens above this module. One option is recognized, `:spans` (boolean, default
`false`), which switches every node's trailing slot from a point to a span.

The body (`parser.ex:264-286`), in order:

1. `warn_deprecated_equals(tokens)` (line 265), before any parsing.
2. Build state `%{tokens: tokens, position: 0, spans?: ...}` (line 267).
3. `parse_expression(state)` (line 269) - the single top-level production.
4. Post-hoc leftover check (lines 272-281):

```elixir
case peek_token(final_state) do
  {:eof, _line, _col, _len, _value} -> {:ok, ast}
  {type, line, col, _len, value} ->
    {:error, "Unexpected token #{format_token(type, value)} after expression", line, col}
  nil -> {:ok, ast}
end
```

That single gate is the only place trailing tokens are rejected. It is what a
statement loop would sit in place of.

**Precedence chain**, lowest to highest. Left-associative levels use a
`parse_X` / `parse_X_rest` / `parse_X_rest_token` triple: parse the left operand,
then tail-recurse through `_rest` accumulating into `left`, with a fallback
`_rest_token(left, state, _token) -> {:ok, left, state}` terminating the loop.
Prefix levels recurse into themselves.

| # | Function | Lines | Handles |
|---|---|---|---|
| 1 | `parse_expression/1` | 320-322 | entry; delegates down |
| 2 | `parse_logical_or/1` + rest | 327-374 | `OR`, `\|\|` |
| 3 | `parse_logical_and/1` + rest | 379-426 | `AND`, `&&` |
| 4 | `parse_logical_not/1` | 431-454 | `NOT`, `!` (prefix) |
| 5 | `parse_comparison/1` | 462-528 | `>` `<` `>=` `<=` `=` `==` `!=` `===` `!==`, `in`, `contains` |
| 6 | `parse_addition/1` + rest | 533-583 | `+`, `-` |
| 7 | `parse_multiplication/1` + rest | 588-656 | `*`, `/`, `%` |
| 8 | `parse_unary/1` | 661-697 | unary `-`, `!` |
| 9 | `parse_postfix/1` + `parse_postfix_operations/2` | 700-772 | `[expr]`, `.name` |
| 10 | `parse_primary/1` + `parse_primary_token/2` | 778-892 | literals, identifiers, calls, `(...)`, list/object, duration/relative-date |

Every level's `@spec` is
`parser_state() :: {:ok, ast(), parser_state()} | {:error, binary(), pos_integer(), pos_integer()}`.
Errors thread by explicit `case` pass-through at every step; no exceptions.

Note that `parse_comparison/1` has **no `_rest` loop** - a single optional
operator - so comparison does not chain at its own level.

**How `:eq` threads into `comparison`.** Guard at `parser.ex:467-478`:

```elixir
{op_type, op_line, op_col, _len, _value}
when op_type in [:gt, :lt, :gte, :lte, :eq, :equal_equal, :ne, :strict_equal, :strict_ne] ->
```

Then the operator normalization at `parser.ex:484-490`:

```elixir
normalized_op =
  case op_type do
    :equal_equal -> :equal_equal
    :strict_equal -> :strict_eq
    :strict_ne -> :strict_ne
    _other_op_type -> op_type
  end
```

`:eq` falls through the catch-all unchanged, and the node is built at
`parser.ex:492-494` as
`{:comparison, normalized_op, left, right, binary_loc(state, {op_line, op_col}, left, right)}`.
The `comparison_op` type (`parser.ex:188-189`) is
`:gt | :lt | :gte | :lte | :eq | :equal_equal | :ne | :strict_eq | :strict_ne`.

Membership is a separate guard clause in the same `case` (`parser.ex:503-518`),
producing `{:membership, op, left, right, pos}` via `map_membership_operator/1`
(`parser.ex:988-989`).

**`warn_deprecated_equals/1`, `parser.ex:288-315`** - verbatim, including its
leading comment:

```elixir
  # Emits a single deprecation warning if the token stream uses `=` as an
  # equality operator. In 3.8 there is no assignment grammar, so every `:eq`
  # token is expression-position; the statement grammar (px-tbv.1) must refine
  # this check rather than inherit it.
  @spec warn_deprecated_equals([Lexer.token()]) :: :ok
  defp warn_deprecated_equals(tokens) do
    if deprecation_warnings_enabled?() do
      case Enum.find(tokens, &match?({:eq, _line, _col, _len, _value}, &1)) do
        {:eq, line, col, _len, _value} ->
          Logger.warning(
            "[predicator] `=` as an equality operator is deprecated and becomes " <>
              "a parse error in Predicator 4.0. Use `==` instead. " <>
              "First occurrence at line #{line}, column #{col}. " <>
              "Silence with `config :predicator, deprecation_warnings: false`."
          )

        nil ->
          :ok
      end
    end

    :ok
  end

  @spec deprecation_warnings_enabled?() :: boolean()
  defp deprecation_warnings_enabled? do
    Application.get_env(:predicator, :deprecation_warnings, true) != false
  end
```

Properties: token-level scan, not position-aware (it fires on any `:eq` anywhere,
including one the parser would never reach); first occurrence only, so once per
call to `parse/2`; runs before `parser_state` is even built. It is the only
"fix-it"-shaped message in `lib/` - a grep for "did you mean" / "use " / "instead"
across `lib/` finds no suggestion-style *error* message anywhere.

**Parser state.** A plain map, no struct (`parser.ex:222-226`):

```elixir
@type parser_state :: %{
        tokens: [Lexer.token()],
        position: non_neg_integer(),
        spans?: boolean()
      }
```

`peek_token/1` is `Enum.at(tokens, pos)` (`parser.ex:897-900`); `advance/1` is
`%{state | position: pos + 1}` (`parser.ex:902-905`).

**No statement vocabulary exists.** Grepping the file for
`assign|statement|semicolon|program` finds only two comment hits: the
`warn_deprecated_equals/1` comment quoted above, and an unrelated "The nested case
statements handle..." at `parser.ex:458`. No `:program` tag, no assignment node,
no separator handling, no top-level loop. The moduledoc grammar
(`parser.ex:12-32`) begins and ends at `expression`.

**Location parsing.** `parse_postfix/1` (`parser.ex:700-708`) parses a primary and
hands it to `parse_postfix_operations/2` (`parser.ex:711-772`), which loops:

- `:lbracket` (`parser.ex:715-740`) - full `parse_expression` for the key, requires
  `:rbracket`, builds `{:bracket_access, expr, key_expr, location}`.
- `:dot` (`parser.ex:742-766`) - requires `:identifier` or one of the
  duration/relative-date keyword tokens reused as property names
  (`:last_op, :next_op, :ago_op, :from_op, :now_op`, `parser.ex:749`), builds
  `{:property_access, expr, property_name, location}` with `property_name` a raw
  binary, not a node.
- anything else (`parser.ex:768-770`) ends the chain.

Chains nest left-associatively, so `a.b[0].c` is a right-nested tree whose
innermost node is the `{:identifier, ...}` from `parse_primary`. These three
shapes - identifier, property_access, bracket_access - are exactly what
`ContextLocation` accepts as assignable.

### The AST node union (`lib/predicator/parser.ex:132-149`)

```elixir
@type ast ::
        {:literal, value(), position()}
        | {:string_literal, binary(), :double | :single, position()}
        | {:identifier, binary(), position()}
        | {:comparison, comparison_op(), ast(), ast(), position()}
        | {:arithmetic, arithmetic_op(), ast(), ast(), position()}
        | {:unary, unary_op(), ast(), position()}
        | {:membership, membership_op(), ast(), ast(), position()}
        | {:logical_and, ast(), ast(), position()}
        | {:logical_or, ast(), ast(), position()}
        | {:logical_not, ast(), position()}
        | {:list, [ast()], position()}
        | {:object, [object_entry()], position()}
        | {:function_call, binary(), [ast()], position()}
        | {:bracket_access, ast(), ast(), position()}
        | {:property_access, ast(), binary(), position()}
        | {:duration, [{integer(), binary()}], position()}
        | {:relative_date, ast(), relative_direction(), position()}
```

Seventeen shapes, arities 3 to 5, each ending in one slot:

```elixir
@type position :: Predicator.Types.position() | Predicator.Types.span() | nil   # parser.ex:160
```

`nil` is the documented value for a hand-built AST (`parser.ex:47-48, 110-112`).
One parse produces one kind throughout; positions and spans never mix
(`parser.ex:66-68, 156-158`).

Supporting types: `object_entry :: {object_key(), ast()}` (167),
`object_key :: {:object_key, binary(), object_key_style(), position()}` (177),
`object_key_style :: :identifier | :double | :single` (183),
`comparison_op` (188-189), `arithmetic_op` (194), `unary_op :: :minus | :bang` (199),
`membership_op :: :in | :contains` (204),
`relative_direction :: :ago | :future | :next | :last` (209).

**`lib/predicator/types.ex` holds no AST type.** Its contents are the value domain
and the wire/side-table types: `duration/0` (27-36), `value/0` (53-62),
`context/0` (75), `instruction/0` (98), `instruction_list/0` (105),
`position/0 :: {pos_integer, pos_integer}` (111),
`position_table/0 :: %{non_neg_integer() => position()}` (119),
`span/0 :: {position(), position()}` with an **exclusive** end (133),
`span_table/0` (143), `result/0` (152), `internal_result/0` (161),
`scxml_error/0` / `scxml_result/0` (173-187),
`location_path/0 :: [binary() | non_neg_integer()]` (197), `location_result/0` (206),
`evaluator_state/0` (218-224), plus `undefined?/1` (241) and `types_match?/2` (269-280).

Note two independently declared near-duplicate location types:
`Types.location_path/0` is `[binary() | non_neg_integer()]` (`types.ex:197`) while
`ContextLocation.location_path/0` is `[binary() | integer()]`
(`context_location.ex:73`, permitting the negative index a `-1` bracket key
resolves to pre-write). `resolve/2`'s spec is written against the latter.

### Assignable locations (`lib/predicator/context_location.ex`)

**What a location is.** Once resolved, a flat list of segments -
`location_path :: [binary() | integer()]` (`context_location.ex:73`,
moduledoc 9-17). `user.items[0].name` resolves to `["user", "items", 0, "name"]`.
All AST nesting is flattened before `put/3` sees it.

**`put/3`, `context_location.ex:206-215`:**

```elixir
@spec put(Types.context(), location_path(), term()) :: put_result()

def put(context, [], _value) when is_map(context) do
  {:error, LocationError.not_assignable("empty location path", [])}
end

def put(context, path, value) when is_map(context) and is_list(path) do
  do_put(context, path, value, [])
end
```

`put_result :: {:ok, Types.context()} | {:error, LocationError.t()}`
(`context_location.ex:88`). **It takes a flat path, never an AST node.** Errors it
can produce: `:not_assignable` (empty path, line 210), `:not_a_container`
(`vivify/3` 391-393, `fetch_in`/`set_in` 409/427), `:invalid_index` (negative index,
404-406 reading and 422-424 writing). Write behavior: ECMAScript-like
auto-vivification - a missing slot becomes `%{}` for a string segment or `[]` for
an integer (`vivify/3`, 378-385); an integer past a list's end pads with
`Undefined.value()` (`write_at/4`, 434-436); the leaf is always overwritten
(`do_put/4`, 364-366); string and integer keys only, never atoms (172-180).

**The AST-to-location converter exists: `resolve/2`, `context_location.ex:125-131`:**

```elixir
@spec resolve(term(), Types.context()) :: location_result()
def resolve(ast_node, context) when is_map(context) do
  case do_resolve_base(ast_node, context) do
    {:ok, path} -> {:ok, path}
    {:error, _error} = error -> error
  end
end
```

`resolve_expression/2` (`context_location.ex:142-156`) composes tokenize ->
parse -> `resolve/2`, wrapping lexer/parser failures as `%ParseError{}` via
`ParseError.new/3` (lines 150, 154).

`do_resolve_base/2` is the assignability predicate, expressed as clause coverage:

**Assignable:**
- `{:identifier, name, _pos}` -> `{:ok, [name]}` (220-222)
- `{:property_access, left, property, _pos}` -> recurse left, append property (225-231)
- `{:bracket_access, left, key_node, _pos}` -> `resolve_bracket_key/2`, recurse left, append (234-245)

**Not assignable**, one clause each, all returning `LocationError` with a phrase:
`{:literal, ...}` "literal value" (250-252), `{:string_literal, ...}` (255-257),
`{:function_call, ...}` (260-262), `{:arithmetic, ...}` (265-267),
`{:comparison, ...}` (270-272), `{:logical_and|:logical_or|:logical_not, ...}`
(275-285), the 2-arity legacy `{:unary_minus, _}` / `{:unary_bang, _}` shapes that
no longer match parser output (288-294), the live `{:unary, op, _, _}` (297-299),
`{:list, ...}` (302-304), and a catch-all `invalid_node` (307-309).

`{:duration, ...}`, `{:relative_date, ...}`, and `{:object, ...}` have no clause
and reach that catch-all.

`resolve_bracket_key/2` (312-356) turns a key sub-AST into a segment:
`{:string_literal, key, _, _}` -> the string (316-319);
`{:literal, index, _}` when integer -> the integer (322-324);
`{:unary, :minus, {:literal, value, _}, _}` -> `-value` (327-333);
`{:identifier, name, _}` -> context lookup, which must yield a binary or integer
else `:undefined_variable` / `:invalid_key` (336-347); anything else ->
`:computed_key` (350-356).

`LocationError`'s `error_type/0` union
(`lib/predicator/errors/location_error.ex:49-56`) is
`:not_assignable | :invalid_node | :undefined_variable | :invalid_key | :computed_key | :not_a_container | :invalid_index`,
with a constructor per type (71-170).

**Callers today** (four, all in `lib/`):
`lib/predicator.ex:661` (`resolve_expression/2`), `lib/predicator.ex:714` (`put/3`),
`lib/predicator/context.ex:177` (`Context.assign/3` -> `put/3`),
`lib/predicator/context.ex:187` (`Context.resolve_path/2`).

### Parse errors and positions

**`ParseError`, `lib/predicator/errors/parse_error.ex:1-42`** - post-px-tbv.7 shape:

```elixir
@enforce_keys [:message, :position]
defstruct [:message, :position]

@type t :: %__MODULE__{message: binary(), position: Predicator.Types.position()}

@spec new(binary(), pos_integer(), pos_integer()) :: t()
def new(message, line, column), do: %__MODULE__{message: message, position: {line, column}}
```

No `:line`, no `:column`, no `:span` field (unlike `EvaluationError`,
`TypeMismatchError`, `UndefinedVariableError`, which do carry `:span` and are
populated by `Predicator.Errors.put_position/2` at `lib/predicator/errors.ex:41-56`).
Nothing in `lib/predicator/errors/` is a `defexception`; there is no
`Exception.message/1` implementation anywhere.

`ParseError.new/3` has four call sites, all converting the parser's/lexer's
4-tuple: `lib/predicator.ex:173`, `lib/predicator.ex:177`,
`lib/predicator/context_location.ex:150`, `lib/predicator/context_location.ex:154`.
Messages do not embed position text - `test/predicator_test.exs:59-63` pins
`%ParseError{message: "Expected number, string, ... but found end of input", position: {1, 8}}`.

**`format_token/2`, `parser.ex:991-1037`** - one clause per token type, output
always spliced into a larger "Expected X but found Y" string:

```elixir
defp format_token(:integer, value), do: "number '#{value}'"
defp format_token(:string, value), do: "string \"#{value}\""
defp format_token(:identifier, value), do: "identifier '#{value}'"
defp format_token(:gt, _value), do: "'>'"
...  # one per punctuation/keyword token, including :eq -> "'='"
defp format_token(:eof, _value), do: "end of input"
```

**Every distinct error shape in `parser.ex`.** The parser never constructs a
struct; it returns `{:error, message, line, col}`.

| Line(s) | Message |
|---|---|
| 277 | `"Unexpected token #{format_token(...)} after expression"` |
| 732 / 735 | `"Expected ']' but found ..."` / `"... end of input"` |
| 761 / 765 | `"Expected property name after '.' but found ..."` |
| 852 / 855 | `"Expected ')' but found ..."` / `"... reached end of input"` |
| 887 | `"Expected number, string, boolean, date, datetime, identifier, function call, list, object, or '(' but found ..."` |

## ISA Impact

**None from this bead.** px-tbv.1 adds no opcode, changes no opcode's semantics,
and emits nothing. The relevant spec text is what constrains the bead downstream.

`docs/isa.md` §2, "Two execution modes" (isa.md:115-150), landed by px-z5m and is
the authority:

> A program is a flat instruction list with no header, so nothing in the wire
> format says whether it is an expression or a statement program. **The mode is
> carried by the entry point, not by the artifact.** In this implementation
> `Predicator.evaluate/2,3` is expression mode and `Predicator.execute/2` - the 4.0
> statement layer, §6 - is statement mode [...] The instruction set is identical in
> both: no opcode is restricted to one mode, and no opcode means anything different
> in the other. Only what "result" means differs.

> - **Statement mode** - the result is **the context at halt**, not a stack value.
>   The stack is scratch space between statement boundaries: a well-formed statement
>   program ends each statement with a `store` or a `pop` and therefore halts with an
>   **empty stack by design**. That is a normal halt. `empty_stack` is an
>   expression-mode rule and is never raised in statement mode.

> A statement program that halts on an error has no result. Whether the partially
> applied context from the statements that completed before the error is kept or
> discarded is a property of the host API, not of the VM [...]

> A host may additionally surface the value of the program's last expression
> statement alongside the context. That is a host-API convenience, not an ISA
> guarantee - the statement boundary's `pop` discards it as far as the VM is
> concerned.

> Until `store` and `pop` exist (§6), no evaluator has a statement entry point and
> no program is a statement program.

§6 (isa.md:431-459) reserves both names:

> - `["store", n]` - specified by ADR-0001 for the 4.0 statement layer, not
>   implemented and not accepted by any current evaluator clause. Reserved name,
>   tier 6.
> - `["pop"]` - the statement-boundary opcode of the same 4.0 statement layer: it
>   discards an expression statement's value so the next statement begins from a
>   clean stack. [...] It is **not** related to `jump_if_falsy_or_pop` /
>   `jump_if_true_or_pop` [...]
> - A statement entry point. §2's "Two execution modes" specifies statement mode's
>   halt contract, but no current evaluator exposes one [...]

§6 also states, on surface syntax:

> Surface syntax, including the `=` grammar break (ADR-0002). Both `=` and `==`
> compile to `["compare", "EQ"]`, so no instruction-level divergence exists between
> them: a parse-time deprecation warning is the entire difference, and it is outside
> the conformance corpus's scope.

§8 confirms the corpus "does **not** cover parse or lexer errors (every authored
case's `source`, when present, compiles successfully)" - so nothing in this bead
belongs in the conformance corpus, and `area:conformance` is not implicated.

**What the landed spec constrains for a parser-only bead:**

- The mode-is-the-entry-point rule is an ISA/evaluator statement, and `docs/plans/260807-px-z5m-pop-and-statement-halt.md:224-236`
  records the rejected alternatives explicitly: a program header, and inferring
  the mode from the presence of `store`/`pop` ("unsound in both directions, since a
  single-expression statement program contains neither, and a hand-built expression
  list could contain a `pop`"). Whether that rule propagates down to the parser's
  own API shape - a distinct `parse_program`-style entry point versus a
  `mode: :statement` option on `parse/2` - is nowhere stated in any landed
  document. See Open Questions.
- The compiler must be able to choose `pop` versus `store` per statement, and to
  identify the last expression statement if a host wants its value. Both are facts
  about the AST's statement kinds, so the AST must distinguish an assignment
  statement from an expression statement. The grammar production
  `statement := assignment | expression` already says so directly.
- `store`'s operand `n` is "n path segments" (ADR-0001:83-84). For px-tbv.2 to
  compute `n`, the assignment lhs must be represented such that its segment count
  is derivable. Nothing in `docs/isa.md` or the px-z5m plan says more about `n`.
- The error contract's third element (`{:error, e, %Context{}}`, px-h66) is
  populated from VM state at evaluation time, not from AST inspection. It places
  no statement-index or statement-granularity requirement on the AST beyond the
  source positions the parser already threads.

## Conflicts with the landed spec

Where the bead's own text or older prose disagrees with what is in `docs/isa.md`
today, **the landed spec wins**. The disagreements, explicitly:

1. **The bead's AC says nothing about the entry point carrying the mode; the spec
   does.** px-tbv.1's AC reads "A statement-sequence entry point parses
   program/statement/assignment as above". `docs/isa.md:117-124` is stricter: the
   mode is carried by the entry point and cannot be recovered from the artifact.
   The bead's phrasing is compatible but underdetermined; the spec's rule is the
   binding one for anything downstream that has to decide the mode.

2. **px-tbv.2's original AC justified discard-on-error by "matching SCXML's
   all-or-nothing error story". That justification is false.** px-h66 verified it
   against W3C SCXML 1.0 §4.9 and IRP test 156 and found SCXML is stop-on-error
   *without* rollback, so an all-or-nothing processor is non-conformant. The
   contract is now `{:ok, %Context{}} | {:error, e, %Context{}}`
   (`docs/design/260807-px-h66-scxml-error-semantics.md`, adopted into
   `docs/isa.md:137-140`). This belongs to px-tbv.2, not px-tbv.1, but any
   px-tbv.1 planning prose echoing "all-or-nothing" is stale.

3. **`docs/architecture.md:20-49` still describes `=` as a live, deprecated member
   of the `comparison` production**, and its grammar block contains no `program` or
   `statement` production at all. It is one release behind the change this bead
   makes.

4. **`docs/reference/language.md:39-57` still lists `=` in the Comparison Operators
   table** with "Equal - deprecated, use `==`" and the example `status = 'active'`,
   and describes the statement grammar as "forthcoming". Same staleness. This file
   is doctested (`test/docs_examples_test.exs:14`).

5. **`conformance/cases/errors.json`'s note that `empty_stack` is "only reachable
   via an empty hand-built instruction list" is stale with respect to statement
   mode**, where an empty stack at halt is the normal, by-design outcome. The
   px-z5m plan (lines 181-184) declined to correct it and assigned that to
   px-tbv.2. Noted here only so it is not mistaken for a px-tbv.1 obligation.

6. **`docs/isa.md:451-455` says "a parse-time deprecation warning is the entire
   difference" between `=` and `==`.** That sentence is true today and becomes
   false the moment this bead lands - the difference becomes a parse error in one
   position and an assignment in another. The instruction-level claim it is making
   (both compile to `["compare", "EQ"]`, no interchange divergence) stays true; the
   "deprecation warning is the entire difference" clause does not.

7. **`parser.ex:288-291`'s comment already names this bead** and states the
   obligation: the check "must refine ... rather than inherit" the current
   token-level scan. That is a source-level instruction, not a conflict, but it is
   the most specific existing directive about what happens to
   `warn_deprecated_equals/1`.

8. **The bead's description says px-tbv.8 is a consumer of px-tbv.1's AST.**
   px-tbv.8 closed on 2026-08-06, merged via PR #79, before this research. The
   legacy AST shape is already gone; there is no compatibility layer left for a new
   node type to interact with.

## Open Questions

Recorded rather than resolved; no human was available to adjudicate, and answering
them is design work that belongs to `/create-plan`, not to this documentation pass.

1. **Does the parser get a separate program entry point, or an option on
   `parse/2`?** `docs/isa.md:117-124` and the px-z5m plan (224-236) establish that
   *execution* mode is carried by the entry point and must not be inferred from the
   artifact or signaled by a header. No landed document extends that rule to the
   parser. The analogy is close - `parse/2` today has `spans:` as an option, so
   there is precedent for both shapes in this codebase.

2. **How is a statement sequence represented in the AST?** The existing union has no
   list-of-nodes shape other than `{:list, [ast()], pos}` and
   `{:object, [entry], pos}`. Whether a program is a new tagged node, a bare list of
   statement nodes, or something else is unspecified anywhere.

3. **Does a single-statement program parse to the same AST as a bare expression?**
   If so, `Predicator.decompile/2` and both visitors need no new clause for the
   common case; if not, all three modules that pattern-match on tags need one, and
   two of them fail with `FunctionClauseError` rather than a graceful error if it is
   missed.

4. **What does the assignment lhs node hold?** ADR-0001 needs `n` path segments to be
   computable by px-tbv.2's compiler, and `ContextLocation.resolve/2` already turns
   the identifier/property_access/bracket_access chain into a flat path - but it does
   so *at runtime against a context*, because a bracket key can be a variable
   (`context_location.ex:336-347`). Whether the parser stores the raw access chain,
   a segment list, or something that defers to `resolve/2` is unspecified, and it is
   the one decision px-tbv.2 is most directly downstream of.

5. **Where does the assignability check happen - parse time or later?** The bead says
   "its lhs must parse as an assignable location", which reads as parse time. But the
   only implementation of assignability, `ContextLocation.do_resolve_base/2`, takes a
   context and can fail for runtime reasons (`:undefined_variable`, `:invalid_key`).
   The purely syntactic part of that predicate - is the node an identifier /
   property_access / bracket_access chain - is separable, but no landed document says
   which half the parser owns.

6. **What exactly does the fix-it message say, and does it replace or supplement
   `warn_deprecated_equals/1`?** The AC requires a pointed message ("use == for
   equality"). There is no suggestion-style parse error anywhere in `lib/` to model
   on, and no landed document fixes the wording. Whether the 3.8 warning function is
   deleted, or narrowed to the cases the new grammar still tolerates, is also
   unstated - though `parser.ex:288-291`'s own comment says "refine ... rather than
   inherit", which reads as narrowing rather than deletion.

7. **Does `;` become a lexer token, and does anything else change in the lexer?**
   Adding `:semicolon` means a new member of the `token()` union
   (`lexer.ex:40-87`), a new `case char do` clause, and a new `format_token/2`
   clause. Whether newline also becomes a statement terminator is not addressed
   anywhere - the grammar in the bead uses `;` only.

8. **What happens to the three `=`-as-equality doctests and the doctested docs
   files?** `lexer.ex:135`, `parser.ex:251`, and `parser.ex:255` use `=` as equality
   in `iex>` examples, and `test/docs_examples_test.exs` executes fenced examples in
   four `docs/` files. These break mechanically when `=` leaves the expression
   grammar; whether that is in this bead's scope or a follow-on is not stated in the
   AC.
