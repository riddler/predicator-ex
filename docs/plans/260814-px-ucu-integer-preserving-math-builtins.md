# Integer-Preserving Math Builtins Implementation Plan

## Overview

`Math.pow` and `Math.sqrt` are the only two members of the `Math` namespace
that always return a float. `Math.pow(2, 3)` is `8.0`, so `Math.pow(2, 3) === 8`
is `false`, and `Math.sqrt(16) === 4` is `false` for the same reason. Every
other Math builtin already preserves integers. This plan makes both outliers
return an integer when the arguments are integers and the result is
integer-exact, updates the two conformance cases that pin the old floats,
states the return-type rule per function in the language reference, and records
the change as breaking. Bead: px-ucu.

## Current State Analysis

- `lib/predicator/functions/math_functions.ex:62` is `{:ok, :math.pow(base,
  exponent)}` and `:72` is `{:ok, :math.sqrt(value)}`. Both Erlang functions
  are float-returning by definition, for every input.
- The rest of the namespace already preserves integers:
  `call_floor/2` (`:96`) and `call_ceil/2` (`:106`) both `trunc/1` their
  result, `call_round/2` (`:116`) uses `round/1`, and `call_abs/2` (`:85`),
  `call_min/2` (`:125`), `call_max/2` (`:135`) delegate to kernel functions
  that return whatever type they were handed. `call_random/0` (`:145`) is
  float by contract and stays float.
- `lib/predicator/evaluator.ex:757` is `compare_values(left, right,
  "STRICT_EQ"), do: left === right`, so `===` is Elixir's `===`: `8.0 === 8`
  is `false`. Non-strict `==` is loose across numeric types, which is why
  `Math.pow(2, 10) == 1024` in `docs/reference/language.md:476` reads as
  working today and hid the problem.
- **`:math.pow/2` is a second, independent defect.** It converts to float
  before exponentiating, so `Math.pow(10, 20)` is not exactly `10^20` -
  the value is not representable in a 64-bit float. `Integer.pow/2` computes
  the exact bignum.
- **The conformance corpus pins both floats.** `conformance/cases/functions.json`
  carries `functions/math-pow` with `expected.result` `8.0`, and
  `functions/math-sqrt` with `expected.result` `4.0` plus the note "always
  returns a float, even for a perfect square". `Predicator.Conformance.Generator`
  evaluates each case and compares against the authored `expected`
  (`lib/predicator/conformance/generator.ex:166-170`, `check_expected/2`), and
  `test/predicator/conformance/corpus_freshness_test.exs` byte-compares the
  regenerated corpus against what is checked in. **Changing the return type
  without editing those two cases in the same commit leaves the gate red**,
  which is why the corpus edits are not a separate phase.
- The existing unit tests assert with `==`, not `===`:
  `test/predicator/functions/math_functions_test.exs:25` (`result == 8.0`),
  `:58` (`result == 4.0`), `:238` (`result == 8.0`). All three keep passing
  unchanged after this change, because `8 == 8.0` is true - they do not
  currently pin the type at all and must be tightened to `===` to become
  meaningful.
- The moduledoc doctests at `lib/predicator/functions/math_functions.ex:21-29`
  assert `8.0` and `4.0` literally and **will** go red; `doctest MathFunctions`
  runs them (`test/predicator/functions/math_functions_test.exs:10`).
- `docs/reference/language.md:458-467` documents the Math namespace as a
  Description column only ("Exponentiation", "Square root"). Nothing there
  states a return type; that ambiguity is what the bead calls out.

### Key Discoveries:

- `lib/predicator/functions/math_functions.ex:61-81` - the two clauses to
  change; both already guard `is_number/1`, so the new integer branches slot
  in above them as more specific clauses.
- `lib/predicator/conformance/generator.ex:166` - the corpus is derived by
  *evaluating* each case, so a return-type change is caught mechanically. The
  corpus is the exported specification (ADR-0003), so its diff is explained in
  the commit message and the PR body.
- `conformance/cases/functions.json` is the authored source;
  `conformance/corpus/*.json` and `conformance/manifest.json` are generated by
  `mix corpus.generate` and never hand-edited (CLAUDE.md, Conventions).
- ADR-0014 (functions are provided by modules) is the governing ADR for the
  function surface. Nothing here changes how providers are registered or
  dispatched, so ADR-0014 is untouched.
- **This is not an ISA change.** No opcode is added, removed, renamed, or
  altered; the instruction lists for these expressions are unchanged
  (`["lit",2],["lit",3],["call","Math.pow",2]`). `docs/isa.md` says the
  builtin function set is not part of the ISA, and
  `conformance/cases/functions.json`'s `functions/unknown-function` note
  repeats it: "the builtin function set itself is not part of the ISA - see
  the Language Reference". So no `docs/isa.md` entry and no ISA version bump
  are owed, and this plan carries no `## ISA Impact` section per
  `.claude/wurk/plan.md`. **Verified, not assumed** - if a reviewer finds an
  opcode moving in the implementation, that finding overrides this paragraph
  and the plan needs the ISA section added before the phase lands.

## Desired End State

- `Math.pow(2, 3) === 8` evaluates `true`; `Math.pow(10, 20)` is the exact
  integer `100000000000000000000`.
- `Math.sqrt(16) === 4` evaluates `true`; `Math.sqrt(2)` is still
  `1.4142135623730951`.
- `Math.pow(2, -1)` is `0.5`, `Math.pow(2.0, 3)` is `8.0`, `Math.sqrt(2.25)`
  is `1.5` - float in, float out, and negative exponent means float out.
- `conformance/cases/functions.json` and the regenerated `conformance/corpus/`
  agree with the new behavior, with notes explaining the rule.
- `docs/reference/language.md` states the return type of every Math function.
- `CHANGELOG.md`'s `## [Unreleased]` records the change under `### Changed`,
  marked **BREAKING**.
- Full `mix quality` green.

Verify by running `mix quality` and by evaluating the six expressions above
in `iex -S mix`.

## What We're NOT Doing

- **Not touching the other seven Math builtins.** `abs`, `floor`, `ceil`,
  `round`, `min`, `max` already preserve integers and `random` is float by
  contract. Documenting their return types (Phase 3) is not changing them.
- **Not coercing integer-valued floats anywhere in the evaluator.** That is
  exactly what statifier's ADR-0023 rejected, and it would change what `===`
  observes for every expression in the language. The fix is per-builtin, at
  the builtin.
- **Not changing `==`, `===`, or any comparison semantics.**
- **Not adding an ADR.** ADR-0003 already governs how an exported-specification
  change moves (version it, note it, explain the corpus diff), and ADR-0014
  already governs the function surface. A per-builtin return type is a library
  contract detail, recorded in `CHANGELOG.md`, `docs/reference/language.md`,
  and the corpus notes - three durable places. A fourth would restate them.
- **Not bumping `@version` in `mix.exs` or promoting the changelog.** Release
  mechanics need an explicit release request naming a version (CLAUDE.md
  authority table). This plan records that the change *is* breaking so the
  next release is cut as a major; it does not cut it.
- **Not extending integer preservation to `Math.pow` with a float base that
  happens to be integral** (`Math.pow(2.0, 3)` stays `8.0`). Float in, float
  out is the ECMAScript-shaped rule and the one the other builtins follow;
  inferring integer-ness from a float's value is the coercion this plan
  rejects.

## Implementation Approach

### Design call 1: this is breaking - SETTLED, breaking

It changes the documented return type of two public builtins, and the
conformance corpus - the artifact siblings implement against - changes with
it. Any host that pattern-matches `{:ok, r} when is_float(r)` on a
`Math.pow` result, or that JSON-encodes one and expects `8.0` on the wire,
observes the change. That is a major-version change under semver, and the
corpus diff makes it visible to every sibling implementation.

The counter-argument in the bead - "every affected comparison was arguably
already wrong" - is about whose fault the breakage is, not whether breakage
occurs. Semver versions observable behavior, not blame. Calling it a patch
because the old behavior was undesirable is exactly the reasoning that makes
a version number stop meaning anything.

**Recorded as**: a `### Changed` entry under `## [Unreleased]` in
`CHANGELOG.md`, opening with **BREAKING**, naming both functions, the exact
before/after values, and the corpus case ids that moved. The next release cut
from that `Unreleased` section is therefore a major (7.0.0 from the current
6.0.0 in `mix.exs:5`) - and cutting it is a separate, human-requested act.

### Design call 2: `Math.sqrt` is IN - SETTLED, implemented

The bead offers to decline it. It is in, for three reasons:

1. **The motivating parity is ECMAScript's**, where `Math.sqrt(16) === 4` is
   true for the same reason `Math.pow(2,3) === 8` is. Fixing one and not the
   other leaves the namespace non-uniform - which is the exact defect this
   bead was filed about, just with a shorter list.
2. **The exactness check is cheap and exact.** A private integer square root
   (Newton's method on integers) answers "is this a perfect square" with no
   float involved, so it is correct for bignums where `:math.sqrt/1` would
   both lose precision and, above ~1.8e308, raise `badarith`.
3. **The breaking-ness is already paid for.** `Math.pow` alone forces the
   major bump. Landing `sqrt` in the same release costs consumers one
   migration instead of two.

### Implementation shape

`Math.pow`: add a clause above the existing one, guarded
`is_integer(base) and is_integer(exponent) and exponent >= 0`, returning
`{:ok, Integer.pow(base, exponent)}`. `Integer.pow/2` raises `ArithmeticError`
on a negative exponent, which the `exponent >= 0` guard excludes, so the
error-as-value rule (ADR-0004) is preserved without a rescue. Everything else
falls through to `:math.pow/2` unchanged.

`Math.sqrt`: add a clause above the existing non-negative one, guarded
`is_integer(value) and value >= 0`, that computes `isqrt(value)` and returns
the integer when `r * r == value`, else `:math.sqrt(value)`. `isqrt/1` is a
private integer Newton iteration - no float, no precision ceiling.

Note the guard order matters: the new integer clauses must be defined **before**
the existing `is_number(value)` clauses, or the general clause shadows them.

## Phase 1: Integer-preserving `Math.pow`

### Overview

`Math.pow` returns an integer for integer base, non-negative integer exponent,
computed exactly. Includes the corpus case edit and regeneration, because the
generator evaluates the case and the freshness test would otherwise be red.

### Changes Required:

#### 1. The builtin

**File**: `lib/predicator/functions/math_functions.ex`
**Changes**: new clause above `call_pow/2`'s numeric clause (currently `:61`);
update the moduledoc's function list and its doctest (`:9`, `:21-24`).

```elixir
@doc """
Raises base to the power of exponent.

Returns an integer when both arguments are integers and the exponent is
non-negative - computed exactly, with no float rounding at large magnitudes.
Returns a float otherwise (float argument, or negative exponent).
"""
@spec call_pow([Types.value()], Context.t()) :: function_result()
def call_pow([base, exponent], _context)
    when is_integer(base) and is_integer(exponent) and exponent >= 0 do
  {:ok, Integer.pow(base, exponent)}
end

def call_pow([base, exponent], _context) when is_number(base) and is_number(exponent) do
  {:ok, :math.pow(base, exponent)}
end
```

The moduledoc doctest changes `8.0` to `8`, and the bullet at `:9` becomes
"`Math.pow(base, exponent)` - Raises base to the power of exponent; integer in,
non-negative integer exponent, integer out".

#### 2. Unit tests

**File**: `test/predicator/functions/math_functions_test.exs`
**Changes**: tighten `:25` from `result == 8.0` to `result === 8`; tighten
`:238` (the `Math.pow(Math.abs(-2), 3)` nesting case) the same way; keep the
negative-exponent test at `:31` and tighten it to `result === 0.5`. Add:

- `Math.pow(2.0, 3) === 8.0` and `Math.pow(2, 3.0) === 8.0` - float in, float out
- `Math.pow(2, 0) === 1` and `Math.pow(0, 0) === 1` - integer, not `1.0`
- `Math.pow(10, 20) === 100_000_000_000_000_000_000` - the exactness the old
  `:math.pow/2` could not deliver
- `Math.pow(-2, 3) === -8` - negative base, non-negative exponent
- the existing non-numeric error path is unchanged and stays

Add an end-to-end case in
`test/predicator/integration/function_calls_test.exs` (which already exercises

## Phase 2: Integer-preserving `Math.sqrt` for exact roots

### Overview

`Math.sqrt` returns an integer when the argument is a non-negative integer
whose square root is exact. Independently committable: Phase 1 does not touch
`call_sqrt/2`, and this phase does not touch `call_pow/2`.

### Changes Required:

#### 1. The builtin

**File**: `lib/predicator/functions/math_functions.ex`
**Changes**: new clause above `call_sqrt/2`'s non-negative clause (currently
`:71`), plus a private `isqrt/1`; update the moduledoc bullet (`:10`) and its
doctest (`:26-29`).

```elixir
@doc """
Returns the square root of a number.

Returns an integer when the argument is a non-negative integer with an exact
integer square root (`Math.sqrt(16)` is `4`). Returns a float otherwise. A
negative argument is an error, not NaN.
"""
@spec call_sqrt([Types.value()], Context.t()) :: function_result()
def call_sqrt([value], _context) when is_integer(value) and value >= 0 do
  root = isqrt(value)
  if root * root == value, do: {:ok, root}, else: {:ok, :math.sqrt(value)}
end

def call_sqrt([value], _context) when is_number(value) and value >= 0 do
  {:ok, :math.sqrt(value)}
end
```

`isqrt/1` is a private integer Newton iteration returning
`floor(:math.sqrt(n))` exactly, with no float step - so it is correct for
integers beyond float range, where `:math.sqrt/1` both loses precision and
raises `badarith` above roughly 1.8e308. `isqrt(0)` is `0`. Give it a `@spec`;
`@doc` is not required on a private function, but a short comment explaining
why it is not `trunc(:math.sqrt(n))` is.

Note the residual: for a huge non-square integer the fallback
`:math.sqrt(value)` can still raise `badarith`. That is pre-existing behavior
for this clause and out of scope here; the integer-exact path this phase adds
is the part that must not have the ceiling.

#### 2. Unit tests

**File**: `test/predicator/functions/math_functions_test.exs`
**Changes**: tighten `:58` from `result == 4.0` to `result === 4`. Add:

- `Math.sqrt(0) === 0` and `Math.sqrt(1) === 1`
- `Math.sqrt(2)` is a float (`is_float/1`), value `1.4142135623730951`
- `Math.sqrt(15)` and `Math.sqrt(17)` are floats - the off-by-one neighbours
  of a perfect square, the case a sloppy `trunc(:math.sqrt(n))` check gets
  wrong
- `Math.sqrt(2.25) === 1.5` - float in, float out even for an exact root
- `Math.sqrt(10_000_000_000_000_000_000_000) === 100_000_000_000` - a perfect
  square past float precision, which is what `isqrt/1` exists for
- the existing negative and non-numeric error paths are unchanged and stay

Add an integration case in
`test/predicator/integration/function_calls_test.exs` asserting
`Predicator.evaluate("Math.sqrt(16) === 4", %{}) == {:ok, true}`.

#### 3. Conformance corpus

**File**: `conformance/cases/functions.json`
**Changes**: `functions/math-sqrt`'s `expected.result` becomes `4` (from
`4.0`), and its note - currently "always returns a float, even for a perfect
square" - is replaced with "a non-negative integer with an exact integer root
returns an integer; every other numeric argument returns a float". Add
`functions/math-sqrt-inexact` for `Math.sqrt(2)` => `1.4142135623730951`.
Leave `functions/math-sqrt-negative-error` untouched. Run
`mix corpus.generate` and commit the regenerated files; explain the diff in
the commit message and PR body (ADR-0003).

## Phase 3: State the return-type rule, and record the break

### Overview

Documentation only, no Elixir. Makes the rule the previous two phases
implemented findable, and records the breaking-vs-not decision where a
consumer will see it. Committable alone: a change touching no Elixir code has
no gate to run and commits on review of the diff (CLAUDE.md authority table),
though the full gate is still run since the repo is in a state to run it.

### Changes Required:

#### 1. The language reference

**File**: `docs/reference/language.md`
**Changes**: the Numeric Functions table (`:458-467`) **keeps its existing
`Function`, `Description`, and `Example` columns** and gains a fourth,
`Returns`. It stays **one row per function**, and it gains a ninth row for
`Math.random()`, which the table does not document today even though
`functions/0` in `math_functions.ex` provides it. So: the 8 existing rows each
gain a `Returns` cell, plus one new `Math.random()` row - nine rows, four
columns. Do not collapse functions into shared rows; the per-function row is
what makes the rule greppable and what the criterion below counts.

The `Returns` cell for each:

| Function | Returns |
|---|---|
| `Math.abs(number)` | same type as the argument |
| `Math.max(a, b)` | the winning argument, type unchanged |
| `Math.min(a, b)` | the winning argument, type unchanged |
| `Math.pow(base, exp)` | integer when both are integers and `exp >= 0`; float otherwise |
| `Math.sqrt(number)` | integer for a non-negative integer with an exact root; float otherwise |
| `Math.floor(number)` | always an integer |
| `Math.ceil(number)` | always an integer |
| `Math.round(number)` | always an integer |
| `Math.random()` | always a float |

Follow with a short paragraph explaining why it matters: `===` is type-strict
(`8.0 === 8` is `false`), so the return type is observable, and `==` is not,
which is why the existing `Math.pow(2, 10) == 1024` example at `:476` reads
as true either way. Add a `===` example alongside it so the reference
demonstrates the strict case, not only the loose one.

Match the file's existing house style (hyphens, no em dashes - confirm against
the surrounding lines before writing).

#### 2. The changelog

**File**: `CHANGELOG.md`
**Changes**: add `## [Unreleased]` above `## [6.0.0]` with a `### Changed`
entry opening **BREAKING**, covering: `Math.pow` now returns an integer for
integer base and non-negative integer exponent (`Math.pow(2, 3)` is `8`, not
`8.0`, so `Math.pow(2, 3) === 8` is now true) and is computed exactly with
`Integer.pow/2` so `Math.pow(10, 20)` no longer loses precision; `Math.sqrt`
now returns an integer for a non-negative integer with an exact root
(`Math.sqrt(16)` is `4`); float arguments and negative exponents are
unchanged; the corpus cases `functions/math-pow` and `functions/math-sqrt`
moved and three cases were added. State plainly that this is a breaking
change warranting a major version, and that the ISA version does **not** move
because no opcode changed and the builtin function set is not part of the ISA.

Do not touch `@version` in `mix.exs` and do not promote the section to a
version header - that is release work under an explicit release request.

## Testing Strategy

### Unit Tests:

`test/predicator/functions/math_functions_test.exs`, pattern-matching style,
asserting with `===` rather than `==` - the whole point of this bead is a type
distinction that `==` cannot see, and the three existing assertions at `:25`,
`:58`, `:238` pass either way today, which is why they did not catch this.

Edge cases that actually bite:

- `Math.pow(2, 0)` and `Math.pow(0, 0)` - both `1`, not `1.0`
- `Math.pow(-2, 3)` - negative base with non-negative exponent stays integer
- `Math.pow(2, -1)` - negative exponent falls through to float
- `Math.pow(2.0, 3)` and `Math.pow(2, 3.0)` - either float argument means float
- `Math.pow(10, 20)` - exactness past float precision
- `Math.sqrt(0)`, `Math.sqrt(1)` - the degenerate exact roots
- `Math.sqrt(15)`, `Math.sqrt(17)` - perfect-square neighbours must be float
- `Math.sqrt(10_000_000_000_000_000_000_000)` - exact root past float precision
- both existing error paths per function - the coverage gap the gate finds

### Integration Tests:

`test/predicator/integration/function_calls_test.exs` - end-to-end
`Predicator.evaluate/3`:

- `"Math.pow(2, 3) === 8"` => `{:ok, true}` (the bead's headline criterion)
- `"Math.sqrt(16) === 4"` => `{:ok, true}`
- `"Math.pow(2, -1) === 0.5"` => `{:ok, true}`
- `"Math.pow(2.0, 3) === 8.0"` => `{:ok, true}`

### Conformance:

Both Phase 1 and Phase 2 run `mix corpus.generate` and commit the result. The
generator evaluates each case against the live evaluator and fails on a
mismatch with the authored `expected`, so the corpus is self-checking here;
`corpus_freshness_test.exs` catches a forgotten regeneration.

### Manual Testing Steps:

1. `iex -S mix`, then `Predicator.evaluate("Math.pow(2, 3) === 8", %{})` -
   expect `{:ok, true}`.
2. `Predicator.evaluate("Math.pow(10, 20)", %{})` - expect the exact integer
   `100000000000000000000`, and confirm it is not `1.0e20`.
3. `Predicator.evaluate("Math.sqrt(16) === 4", %{})` - expect `{:ok, true}`;
   `Predicator.evaluate("Math.sqrt(17)", %{})` - expect a float.
