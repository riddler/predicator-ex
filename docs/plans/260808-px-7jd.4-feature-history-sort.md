# Sorting the Per-Feature History Implementation Plan

## Overview

`docs/architecture.md` carries two sections that are not architecture:
`## Recent Additions` (lines 217-967, twenty `###` subsections of per-feature
design prose spanning v1.1.0 through v4.0.0-unreleased) and
`## Breaking Changes` (lines 969-998, three release subsections). This plan
classifies every one of those subsections as **normative** (rehome to a
reference document or guide), **rationale** (rehome to an ADR or an existing
design/research note), or **historical** (delete; `CHANGELOG.md` carries it),
then executes the moves and deletes both sections.

Beads issue: **px-7jd.4**. Parent epic: **px-7jd**. Label: `area:docs`.
Siblings px-7jd.1 and px-7jd.2 are closed (merged via PR #94); px-7jd.3 (the
contributor how-tos) is still open and is deliberately not touched here.

This is documentation-only. No `lib/` file, no test, no opcode, and no ISA
version moves. The one non-doc file that comes up is `mix.exs`'s `docs()`
extras list, which is a decision point and is **not** edited by this plan -
see "The `mix.exs` decision" below.

## Desired End State

1. `docs/architecture.md` has no `## Recent Additions` section and no
   `## Breaking Changes` section. It ends (for this bead's purposes) at
   `## Key Design Decisions` and resumes at `## Common Tasks`, which px-7jd.3
   owns.
2. A new `docs/reference/ast.md` exists and is the reader-facing authority for
   the AST: the node inventory, the statement-grammar nodes, the trailing-slot
   contract, the defining-token table, and the span table. Written in the
   present tense, organized by node, with no release numbers in headings.
3. `docs/reference/language.md` gains four normative sections that currently
   exist only inside the release history: `+` coercion, unary `!`, the
   `concat/2` builtin, and Date/DateTime comparison semantics - plus the
   `on_unbound` default-vs-`:error` truth table.
4. `docs/guides/location-expressions.md` gains the `LocationError` type table
   and the frozen-contract statement for `ContextLocation.put/3`.
5. Every other subsection is deleted, and this plan records, per subsection,
   why - so that "deleted with the reason recorded" (the epic's acceptance
   criterion) is satisfied by this document.
6. `CHANGELOG.md` is unchanged. Nothing in this bead is a user-facing change to
   the library; it is a documentation reorganization, and no `## [Unreleased]`
   entry is added.

## The `mix.exs` decision

`docs/reference/ast.md` is a new file. `mix.exs:96-110` lists the ExDoc extras
explicitly, and `groups_for_extras` routes `~r{docs/(reference/|isa\.md)}` to
the **Reference** group (`mix.exs:112-116`) - so the new file would slot in
correctly *if* it were added to the `extras:` list, but ExDoc publishes only
what is listed. Without that one-line edit, `docs/reference/ast.md` is a
repo-only document.

**Editing `mix.exs` adds the `area:build` label, which is exclusive**
(`CLAUDE.md`): a bead carrying it batches with nothing and lands on `main`
alone. px-7jd.4 is currently `area:docs` and batchable.

**Two options, and the call this plan makes:**

- **Option A - add the extras entry here.** One line in `mix.exs`. Cost: the
  bead relabels to `area:docs` + `area:build`, serializing it against every
  other worktree in flight, for a one-line change. px-7jd.3 will very likely
  want the same edit for whatever file it lands (a `CONTRIBUTING.md` or
  `docs/workflow.md`), so the cost would be paid twice.
- **Option B (chosen) - defer the extras entry to a follow-up
  `area:build` bead.** Land `docs/reference/ast.md` as a repo document here;
  file `px-7jd.5` carrying `area:docs` + `area:build` to add the extras
  entries for both this bead's and px-7jd.3's new files in one serialized
  pass, once both are known.

Option B is chosen because the interim state is one this repo already ships:
`architecture.md:124-128` - a published extra - links `../conformance/README.md`
and `../conformance/RATCHET.md`, neither of which is an extra. A relative link
from a published extra to a repo-only doc resolves on GitHub and dead-ends on
hexdocs, and the repo has already accepted that trade for the conformance
tree. The exposure here is narrower and shorter-lived.

**Mitigation, in scope for Phase 1:** the surviving cross-references in
`language.md` and `architecture.md` that point at `ast.md` are written so the
sentence still reads correctly when the link does not resolve - "the node
inventory in `docs/reference/ast.md`", never "see [here]" - and the normative
*semantics* a hexdocs reader actually needs (what `:position` and `:span`
mean on an error, the exclusive end) land in `language.md`, which **is**
published. `ast.md` carries the node-by-node tables, whose audience is someone
writing a visitor against the Elixir API, and who has a checkout.

**This is a reversible call.** If the maintainer prefers Option A, the change
is: add `"docs/reference/ast.md"` to `mix.exs:96-110` after
`"docs/reference/language.md"`, add `area:build` to the bead, and land it
alone. Nothing else in this plan moves.

## Implementation Approach

Four phases, ordered so that **nothing is deleted before its replacement
exists**. Phases 1-3 are additive; Phase 4 is the deletion, and is the only
phase where `architecture.md` shrinks. Each phase is independently
committable and leaves the tree green.

The gate is unusual for this repo in that it is documentation-only, so the
`mix quality` signal is thin - but it is not zero: this repo doctests its
markdown guides, so any `iex>` block added to `language.md` or a guide is
executed by `mix test`. Every example this plan adds is written as a doctest
for that reason, and copied from a passing example in `architecture.md` or
verified in `iex` before it is written down.

Per CLAUDE.md, a change touching no Elixir code has no gate to run and may
commit on review of the diff alone - but `mix quality` is still run for every
phase here, because the doctested markdown means these edits *can* break the
suite.

## Testing Strategy

### Automated

There is no new Elixir code, so the suite's role here is narrow but real:
this repo doctests its markdown, so `mix test` executes every `iex>` block
added in Phases 2 and 3. That is the only mechanical check that a rehomed
example is still true. Run `mix quality` at each phase gate rather than only
at the end - a broken doctest introduced in Phase 2 is much cheaper to find
before Phase 4 deletes its source.

### Link and coverage checks

- `mix docs`, then confirm the Reference and Guides groups render and that
  `docs/architecture.md`'s remaining links resolve.
- The classification table in this plan is the checklist. Phase 4's manual
  verification walks it row by row; a row whose destination is empty is a
  blocked deletion, not an accepted loss.

### Manual verification steps

1. Read `docs/architecture.md` top to bottom after Phase 4 and confirm it
   answers "how does this work and what did it decide not to do" without
   detouring through a release history (the epic's stated goal).
2. Read `docs/reference/ast.md` as someone writing a visitor: is every node's
   shape, blame token, and span extent answerable from this page alone?
3. Read `docs/reference/language.md`'s new sections as someone who has never
   seen `architecture.md`: does anything read as a fragment of a release note?
4. Check `git diff --stat` at the end: the expectation is one new file, edits
   to `language.md` and two or three guides, and a large deletion from
   `architecture.md`. Any `lib/` or `mix.exs` file in that list is a scope
   error.
