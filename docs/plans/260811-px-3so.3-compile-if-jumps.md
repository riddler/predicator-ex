# Compiles if/else to jumps (ISA v5) Implementation Plan

## Overview

Mint ISA v5 by adding two opcodes - `jump` (unconditional, relative, forward)
and `pop_jump_if_falsy` (pops always, jumps on falsy) - and lower the already
parsed `{:if, ...}` / `{:block, ...}` AST nodes onto them in the
InstructionsVisitor. ADR-0013 settles the opcode names, their semantics, and
the exact lowerings; this plan is their mechanical execution plus the ISA
paperwork ADR-0003 attaches to the bead that mints the version. Bead:
`px-3so.3`.

## Current State Analysis

**The parser half is done.** `px-3so.2` landed the grammar, the AST nodes, the
reserved words, and the entry-point split:

- `lib/predicator/parser.ex:197-208` defines
  `{:block, [statement()], position()}` and
  `{:if, ast(), block(), block() | nil, position()}`. `else if` is desugared
  into an `else` block whose sole statement is the nested `if`
  (`parser.ex:682-690`), so there is no chain node to handle.
- `lib/predicator/lexer.ex:510` classifies `if` (and `else`, `while`) as
  reserved words.
- `test/predicator/if_statement_test.exs` covers the parse surface, including
  empty blocks, nesting, and the "an empty else block is distinguishable from
  an absent one" case that makes `else_block == nil` a meaningful discriminator.

**Both visitors currently decline the nodes**, deliberately and as values, not
crashes (`px-aen`):

- `lib/predicator/visitors/instructions_visitor.ex:355-363` throws
  `{:unsupported_node, ...}` for `{:if, ...}` and `{:block, ...}`, caught by
  `visit/2` and friends and returned as `{:error, %EvaluationError{reason:
  "unsupported_node"}}`.
- `lib/predicator/visitors/string_visitor.ex:292-296` does the same. That one
  is `px-3so.5`'s to replace, not this plan's.

**The ISA is at v4** (`lib/predicator/instructions.ex:45`), with `cast` as the
newest opcode (tier 7). Four mechanisms bind the ISA to its documentation and
its corpus, and all four fire when `@opcodes` gains a row:

1. `test/predicator/isa_sync_test.exs:38` - every `docs/isa.md` opcode-table
   row must round-trip through `required_isa/1` and `tier/1`; and
   `isa_sync_test.exs:30`'s `@opcode_count 28` literal is asserted against the
   §4 table's row count twice (lines 45-47 and 105-108), so adding two rows
   moves it to `30`.
2. `isa_sync_test.exs:65,86` - `isa_version/0` must equal the maximum version
   in the doc's table, and `docs/isa.md` §1's
   `Current version: **ISA v4**.` line must agree.
3. `isa_sync_test.exs:127` - the doc's tier-names table must match the map's
   tier assignment exactly, so a new tier row is mandatory.
4. `isa_sync_test.exs:163-204` - **every live opcode must have an
   `execute_instruction/2` clause head in `lib/predicator/evaluator.ex`**, and
   the clause-head count must equal the live opcode count.

**And two conformance mechanisms fire as well:**

5. `test/predicator/conformance/opcode_coverage_test.exs:34` - every opcode in
   `Instructions.opcode_set(Instructions.isa_version())` must appear in at
   least one authored case under `conformance/cases/*.json`, except the single
   documented exclusion (`relative_date`).
6. `test/predicator/conformance/corpus_freshness_test.exs:20` - the checked-in
   corpus must be byte-identical to what `mix corpus.generate` writes.
   `build_manifest/1` stamps `Predicator.isa_version()` into
   `conformance/manifest.json` (`generator.ex:570`), so bumping the version
   alone makes the corpus stale; and
   `test/predicator/conformance/ratchet_registry_test.exs:82` requires
   `conformance/examples/registry.example.json`'s `corpus_hash` and
   `isa_version` to equal the regenerated manifest's.

Together, 1-6 are why the opcode table, the evaluator clauses, `docs/isa.md`,
the corpus cases, and the regenerated corpus **cannot be split across
commits**: any proper subset leaves `mix quality` red.

**The evaluator's jump machinery already exists.**
`jump_to/2` (`evaluator.ex:1615-1617`) sets
`instruction_pointer = ip + offset - 1` so the unconditional `+1` in
`advance_instruction_pointer/1` lands exactly on `ip + offset`. The two
existing `_or_pop` jumps (`evaluator.ex:1572-1610`) are the clause shape to
model: a falsy guard clause, a `true` clause, a type-mismatch clause, and an
empty-stack clause, in that order.

**The compiler's offset arithmetic already exists too.**
`visit_annotated({:logical_and, ...})`
(`instructions_visitor.ex:249-262`) computes
`offset = length(right_instructions) + 1` over the *annotated* list, where one
entry is one instruction - so the same arithmetic works unchanged for the new
lowerings.

## Desired End State

`Predicator.execute/2,3` runs a program containing `if`/`else`, including
`else if` chains and nesting, producing the flat-context result ADR-0013
specifies. `Predicator.compile/1`-style compilation of an `if` program emits
exactly ADR-0013's two lowerings. `Predicator.Instructions.isa_version/0`
returns `5`, `docs/isa.md` documents `jump` and `pop_jump_if_falsy` as tier-8
ISA v5 opcodes with a v5 version-history row, and the conformance corpus has a
`conformance/corpus/tier-8.json` exercising both opcodes in both directions.

Verify with: `mix quality` green; `Predicator.execute("if x > 1 { y = 2 }",
%{"x" => 5})` returning `{:ok, %{"x" => 5, "y" => 2}}`;
`Predicator.Instructions.isa_version() == 5`.

### Key Discoveries:

- **`visit_statement/2`'s fallback would corrupt the stack.**
  `instructions_visitor.ex:408-410` appends `["pop"]` to any statement that is
  not an `{:assignment, ...}`. An `{:if, ...}` is stack-neutral by
  construction, so the fallback would emit a `pop` against an empty stack.
  `visit_statement/2` needs its own `{:if, ...}` clause that appends nothing.
  This is the single highest-risk detail in the plan.
- **A `{:block, ...}` is exactly a `{:program, ...}` body.**
  `instructions_visitor.ex:365-367` already compiles a program as
  `Enum.flat_map(statements, &visit_statement(&1, opts))`; a block's clause is
  the same expression, which is what makes ADR-0013's "each block's statements
  are already stack-neutral" true.
- **The corpus can only reach these opcodes through authored `instructions`.**
  `generator.ex:330-334` resolves a case's `source` through
  `Predicator.compile/1` - expression mode - and `evaluate_case/2`
  (`generator.ex:341-343`) runs `Predicator.evaluate/3`, also expression mode.
  A control-flow case therefore authors its instruction list by hand and ends
  with a `["load", ...]` to observe the branch's effect, exactly as
  `conformance/cases/statements.json` does for `store`.
- **Constraint - ADR-0013**: `jump` is forward-only with a positive integer
  offset; a v5 list contains no back edge, so it still provably halts in at
  most `length(program)` steps. Nothing here may introduce a negative or
  zero offset - `jump_backward` is `px-3so.4`'s, at v6.
- **Constraint - ADR-0003**: the ISA paperwork lands in the bead that mints the
  version, not ahead of it, and a corpus diff moves the exported specification,
  so it is explained in the commit message and the PR body.
- **Constraint - ADR-0004**: errors are values. The new opcodes return
  `{:error, %TypeMismatchError{}}` / `{:error, %EvaluationError{}}`, never
  raise.

## Decisions Taken During Planning

Recorded here so no open question survives into implementation.

1. **`docs/isa.md` §7's v5 row says "Shipped in 4.1.0."** `mix.exs` is at
   `4.0.0` and `CHANGELOG.md`'s `## [Unreleased]` already holds ISA v4's
   `cast`, whose §7 row claims 4.1.0. v5 lands in that same unreleased minor,
   so it carries the same number. ADR-0013's "each is a minor release" is about
   v5 versus v6, not v5 versus v4. No test binds this column; if the release
   bead numbers the release differently, `/wurk:release` corrects both rows
   together.
2. **This bead authors the minimum tier-8 corpus cases; `px-3so.6` broadens
   them.** Mechanism 5 above makes cases non-optional here - the gate is red
   without them. `px-3so.6` depends on this bead, so there is no parallel
   branch to collide with, and it extends the same
   `conformance/cases/control_flow.json`. **Add `area:conformance` to
   `px-3so.3`'s labels** (`bd update px-3so.3 --labels ...`) when this lands:
   the branch touches the conformance subtree, and an unlabeled area is worth
   noticing rather than silently accepting (ADR-0005).
3. **Both new instructions carry the `{:if, ...}` node's own annotation.**
   `docs/reference/ast.md:197` already declares the `if` node's defining token
   to be the `if` keyword, and `InstructionsVisitor`'s standing rule is that a
   node's own instructions carry its own position. Blaming the condition node
   instead was considered and rejected: it would add a second documented
   exception alongside `store_annotation/2` (`px-tbv.11`) for a case where the
   `if` genuinely is the construct that noticed the bad value, the same way
   `logical_and`'s jump blames the operator.
4. **Neither opcode gets a `Features` tag.**
   `lib/predicator/conformance/features.ex:36-38` tags the `_or_pop` jumps
   `short_circuit`; that tag is about expression-level short-circuiting and
   would be wrong here. Tier 8 is the cut for control flow, and
   `opcode_tags/1`'s `Map.get(_, opcode, [])` default already handles an
   untagged opcode. The tag vocabulary in that moduledoc stays as it is.

## What We're NOT Doing

- **`while`, `jump_backward`, and the loop budget.** ISA v6, `px-3so.4`.
  Nothing in this plan may add a backward or absolute jump.
- **`StringVisitor` rendering of `if`/`else`.** `px-3so.5`, already filed,
  `area:visitors`, shipping in the same v5 release. `.claude/wurk/plan.md`
  says a grammar change `StringVisitor` cannot render back is incomplete
  rather than a follow-up phase - that rule bit at `px-3so.2`, which is where
  the grammar actually changed, and it was answered there by the explicit
  declining clause plus a filed sibling bead. This bead adds no grammar. So
  `string_visitor.ex:292-296` keeps declining, and
  `Predicator.decompile/2` keeps returning `{:error, ...}` for a program
  containing an `if` after this lands. Phase 2's documentation edits say so
  explicitly rather than leaving the reader to infer it.
- **Broad conformance coverage of control flow.** `px-3so.6`. Phase 1 authors
  only what mechanism 5 requires.
- **Block scoping.** ADR-0013 settles that braces group statements and the flat
  Context is the only scope; a `store` inside a taken branch writes the same
  context as one outside it. No scope opcodes, no frames.
- **Changing the `_or_pop` jumps.** Expression-level `AND`/`OR` compile exactly
  as before; no existing instruction list changes meaning.
- **A release.** No `@version` bump, no changelog promotion, no tag.

## Implementation Approach

Two phases, split at the seam between the instruction set and the compiler -
the natural cut, and the one that keeps each phase's gate meaningful.

Phase 1 mints the opcodes end to end: table row, evaluator clause,
`docs/isa.md` prose, tier-8 corpus case, regenerated corpus. It has to be one
phase because mechanisms 1-6 above go red on any proper subset. After it, ISA
v5 exists and is runnable, but the compiler still never emits either opcode -
`docs/isa.md`'s "Emitted by compiler" column reads `no` for both, which is the
truth at that commit.

Phase 2 lowers the AST onto them and flips that column to `yes`. It touches
one visitor function group plus the documentation that currently promises
`if` does not execute.

## Phase 1: Mint ISA v5 - `jump` and `pop_jump_if_falsy`

### Overview

Add the two opcodes to the instruction set, the evaluator, the ISA
specification, and the conformance corpus, in one commit. No compiler change.

### Changes Required:

#### 1. The opcode table

**File**: `lib/predicator/instructions.ex`
**Changes**: bump `@isa_version` to `5`; add two `@opcodes` rows at tier 8.
The `required_isa/1` doctest at line 287 embeds `"this build supports ISA v4"`
in its expected message - it interpolates `@isa_version`, so update the
expected string to `v5`.

```elixir
  @isa_version 5

  # ... in @opcodes, after the "cast" row:
    "cast" => %{isa: 4, tier: 7},
    "jump" => %{isa: 5, tier: 8},
    "pop_jump_if_falsy" => %{isa: 5, tier: 8}
```

#### 2. The evaluator clauses

**File**: `lib/predicator/evaluator.ex`
**Changes**: two `execute_instruction/2` clause heads (placed beside the
existing jump clauses around line 551-562, so the jump family stays together)
and their private helpers beside `execute_jump_if_true_or_pop/2` and
`jump_to/2`. Guard the operand exactly as the existing jumps do
(`is_integer(offset) and offset > 0`), so a malformed operand falls through to
the catch-all and reports `unknown_instruction` - `docs/isa.md` §2's standing
rule.

```elixir
  # Unconditional forward jump (ISA v5, ADR-0013). Pops nothing, pushes
  # nothing; the one instruction `if/else` needs to skip its else branch.
  defp execute_instruction(%__MODULE__{} = evaluator, ["jump", offset])
       when is_integer(offset) and offset > 0 do
    {:ok, jump_to(evaluator, offset)}
  end

  # Statement-position conditional jump (ISA v5, ADR-0013): pops the top
  # ALWAYS, unlike jump_if_falsy_or_pop, which preserves it on the taken
  # branch.
  defp execute_instruction(%__MODULE__{} = evaluator, ["pop_jump_if_falsy", offset])
       when is_integer(offset) and offset > 0 do
    execute_pop_jump_if_falsy(evaluator, offset)
  end
```

```elixir
  @spec execute_pop_jump_if_falsy(__MODULE__.t(), pos_integer()) ::
          {:ok, __MODULE__.t()} | {:error, term()}
  defp execute_pop_jump_if_falsy(%__MODULE__{stack: [top | rest]} = evaluator, offset)
       when top == false or top == :undefined do
    {:ok, jump_to(%{evaluator | stack: rest}, offset)}
  end

  defp execute_pop_jump_if_falsy(%__MODULE__{stack: [true | rest]} = evaluator, _offset) do
    {:ok, %{evaluator | stack: rest}}
  end

  defp execute_pop_jump_if_falsy(%__MODULE__{stack: [top | _rest]}, _offset) do
    got_type = get_value_type(top)
    {:error, TypeMismatchError.unary(:pop_jump_if_falsy, :boolean, got_type, top)}
  end

  defp execute_pop_jump_if_falsy(%__MODULE__{stack: []}, _offset) do
    {:error, EvaluationError.insufficient_operands(:pop_jump_if_falsy, 0, 1)}
  end
```

Note that the falsy clause pops **before** jumping - that is the whole
difference from `jump_if_falsy_or_pop`, and it is what
`docs/isa.md` §5 will state.

`execute_pop_jump_if_falsy/2` must **not** write the evaluator's
last-popped-value field. `evaluator.ex:1550-1551` already records that only
`execute_pop/1` writes it, because the `_or_pop` jumps pop mid-expression
rather than at a statement boundary; a condition is not a statement's value
either, so `Predicator.execute_value/2` must not start reporting it. Extend
that comment to name the new opcode.

## Phase 2: Lower `if`/`else` in the InstructionsVisitor

### Overview

Replace the two declining clauses with ADR-0013's lowerings, teach
`visit_statement/2` that an `if` is stack-neutral, and update every doc that
currently promises `if` does not execute.

### Changes Required:

#### 1. The lowering

**File**: `lib/predicator/visitors/instructions_visitor.ex`
**Changes**: replace the `{:if, ...}` and `{:block, ...}` declining clauses
(lines 355-363) with real ones, keeping them in the same position - after
`relative_date`, before `{:program, ...}`. Two `if` clauses, discriminated on
`else_block == nil`, because ADR-0013 gives the two forms different offset
arithmetic and the parser makes `nil` versus `{:block, [], _}` meaningful.

```elixir
  # ADR-0013:  if c { A }  ->  c; pop_jump_if_falsy +(lenA + 1); A
  # The block's statements are stack-neutral (each ends in a store or a pop),
  # so the jump target is one past A and nothing needs mopping up.
  defp visit_annotated({:if, condition, then_block, nil, position}, opts) do
    condition_instructions = visit_annotated(condition, opts)
    then_instructions = visit_annotated(then_block, opts)
    offset = length(then_instructions) + 1

    condition_instructions ++
      [{["pop_jump_if_falsy", offset], position}] ++
      then_instructions
  end

  # ADR-0013:  if c { A } else { B }
  #   ->  c; pop_jump_if_falsy +(lenA + 2); A; jump +(lenB + 1); B
  # The +2 clears A and the unconditional jump that ends it; the +1 clears B.
  defp visit_annotated({:if, condition, then_block, else_block, position}, opts) do
    condition_instructions = visit_annotated(condition, opts)
    then_instructions = visit_annotated(then_block, opts)
    else_instructions = visit_annotated(else_block, opts)

    condition_instructions ++
      [{["pop_jump_if_falsy", length(then_instructions) + 2], position}] ++
      then_instructions ++
      [{["jump", length(else_instructions) + 1], position}] ++
      else_instructions
  end

  # A block is a statement sequence with no scope of its own (ADR-0013) - the
  # same body as {:program, ...}, and the reason each block is stack-neutral.
  defp visit_annotated({:block, statements, _position}, opts) do
    Enum.flat_map(statements, &visit_statement(&1, opts))
  end
```

Both emitted instructions carry the `if` node's own `position` slot
(Decision 3). The offsets are computed over the annotated list, one entry per
instruction, exactly as `logical_and` does.

#### 2. The statement-position clause - the correctness detail

**File**: `lib/predicator/visitors/instructions_visitor.ex`
**Changes**: add an `{:if, ...}` clause to `visit_statement/2` (before the
catch-all at line 408) so no `["pop"]` is appended.

```elixir
  # An `if` is stack-neutral by construction - its condition is consumed by
  # pop_jump_if_falsy and its blocks end stack-neutral - so unlike a bare
  # expression statement it takes no trailing pop. Without this clause the
  # catch-all below would emit one against an empty stack.
  defp visit_statement({:if, _condition, _then_block, _else_block, _position} = node, opts) do
    visit_annotated(node, opts)
  end
```

## ISA Impact

1. **Version.** This mints **ISA v5**, additive - two new opcodes, no opcode
   retired, no opcode's semantics changed under its own name. Additive means a
   minor library release (`docs/isa.md` §1); it ships in the same unreleased
   minor as ISA v4's `cast` (Decision 1). `@isa_version` moves from `4` to `5`
   in `lib/predicator/instructions.ex`.
2. **Stamp.** `docs/isa.md` owes: two opcode-table rows; a `| 8 | control flow
   |` tier row; a per-opcode subsection each in §5; the `Current version: **ISA
   v5**.` line in §1; the "Every opcode is ISA v1 except..." sentence in §4;
   and a v5 row in §7's version history. The conformance corpus owes a tier-8
   file, generated by `mix corpus.generate` from authored cases and never
   hand-edited. `Predicator.Instructions`'s `@opcodes` gains both entries at
   `%{isa: 5, tier: 8}`.
3. **Migration.** **None required.** Every instruction list compiled before
   this change still runs and produces the same answer: no opcode was retired,
   no operand form widened, and no existing opcode's clause was touched. The
   asymmetry is the expected one - a v5 artifact does not run on a v4 or
   earlier build, and a sibling behind v5 is an expected, documented state
   (ADR-0003), not a blocker here.

Two properties worth stating for the siblings: `pop_jump_if_falsy` is
deliberately **not** a renamed `jump_if_falsy_or_pop` - it consumes the tested
value on both branches, which is what a condition in statement position wants
- and ISA v5 introduces **no back edge**, so every v5 instruction list still
provably halts in at most `length(program)` steps. `jump_backward` and the
loop budget arrive at v6 (`px-3so.4`).

### Unit Tests:

- **`test/predicator/instructions_test.exs`** - `isa_version/0` is `5`; both
  new opcodes report `{:ok, 5}` from `required_isa/1` and `{:ok, 8}` from

- **Anti-drift** - `isa_sync_test.exs` and the conformance tests are the
  binding tests here; they need no new cases, only to stay green. Per
  `docs/research/260808-px-9ab-sabotage-notes.md`, a binding test carries a
  sabotage note; these already do and this plan adds no new binding test.
