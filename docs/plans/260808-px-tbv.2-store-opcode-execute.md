# The `store` and `pop` opcodes and `Predicator.execute/2` Implementation Plan

## Overview

px-tbv.2 completes the statement layer px-tbv.1 started at the parser. It adds
the two opcodes the ISA has reserved since ADR-0001 - `["store", n]` and
`["pop"]` - teaches `InstructionsVisitor` to compile `{:program, ...}` and
`{:assignment, ...}`, and adds the statement-mode entry point
`Predicator.execute/2`, which returns
`{:ok, %Context{}} | {:error, error, %Context{}}`.

Programs stay flat, serializable instruction lists: the mode lives at the entry
point, never in the artifact (ADR-0001, `docs/isa.md` §2). The write algorithm
stays single: `store` is the third caller of `ContextLocation.put/3`, beside
`put/3` itself and `Context.assign/3`.

Beads issue: **px-tbv.2**. Research: `docs/research/260808-px-tbv.2-store-opcode-execute.md`.

## Current State Analysis

The research doc maps this in full; the load-bearing facts:

- **The statement AST exists and is complete.** `{:program, [statement], pos}`
  (`lib/predicator/parser.ex:183`) and `{:assignment, lhs, rhs, pos}` (`:169`),
  produced by `Parser.parse_program/2` (`:361`) and `Predicator.parse_program/2`
  (`lib/predicator.ex:518`). The lhs is the **raw access chain**, deliberately:
  its depth is the `n` that `["store", n]` needs, and a bracket key may be an
  arbitrary sub-expression (`parser.ex:158-168`).
- **`InstructionsVisitor` has no `:program` or `:assignment` clause and no
  catch-all** (`lib/predicator/visitors/instructions_visitor.ex:116-277`), so
  both raise `FunctionClauseError` today. `StringVisitor` already handles both
  (`string_visitor.ex:265-271`), and `Visitor.accept/3`'s spec is already
  `Parser.ast() | Parser.program()` (`visitor.ex:65`), as is
  `Compiler.to_string/2` (`compiler.ex:118`). `Compiler.to_instructions/2`
  (`:50`) and `to_instructions_with_positions/2` (`:78-79`) are not.
- **The evaluator's context is read-only.** No `execute_instruction/2` clause
  writes `%__MODULE__{evaluator | context: ...}`; `load_from_context/2`
  (`evaluator.ex:1143-1150`) is the only touch. `store` is the first
  context-writing opcode in the VM's history.
- **The VM is already stop-on-error and already keeps the surviving state.**
  `run_state/1` (`evaluator.ex:287-295`, private) returns
  `{:error, error_struct, evaluator}` with the **pre-step** evaluator and never
  steps again. `run_prepared/1` (`:87-104`) wraps it but manufactures
  `empty_stack` on an empty stack at halt - the expression-mode rule
  `docs/isa.md:128-137` says must never fire in statement mode. `run/1`
  (`:275-281`) drops the state. **No public entry point today gives statement
  mode what it needs**: final state on both paths, no `empty_stack`.
- **`ContextLocation.put/3`** (`context_location.ex:206-215`) takes a **flat
  path** `[binary() | integer()]`, never an AST, and returns
  `{:ok, context} | {:error, %LocationError{}}` with `:not_assignable`,
  `:not_a_container`, and `:invalid_index`. `LocationError` carries **no
  `:position`/`:span`**, so `Errors.put_position/2` is a no-op on it
  (`errors.ex:52-54`).
- **`Predicator.execute/2` does not exist**; `evaluate/3`
  (`lib/predicator.ex:161-223`) is its structural model, including the
  three-clause `%Compiled{}` / `binary()` / `list()` dispatch and the
  normalize-a-bare-map-into-`%Context{}` step.
- **Four guard tests exist for this bead to flip**:
  `test/predicator/instructions_test.exs:210,219` (store/pop are unknown
  opcodes) and `test/predicator/parser_test.exs:1772,1780`
  (`Compiler.to_instructions/2` raises `FunctionClauseError` on a program and on
  an assignment).
- **Three gates bind the ISA together in lockstep.**
  `test/predicator/isa_sync_test.exs` parses `docs/isa.md` and asserts the §4
  opcode table, the §4 tier-names table, `@opcode_count 25` (`:30`),
  `Instructions.@opcodes`, and the literal `execute_instruction/2` clause heads
  all agree. `test/predicator/conformance/opcode_coverage_test.exs:33-45` fails
  for any opcode in `Instructions.opcode_set(isa_version())` with no authored
  case and no documented exclusion.
  `test/predicator/conformance/corpus_freshness_test.exs:19-30` fails if
  `conformance/corpus/*.json` and `manifest.json` are not byte-identical to a
  fresh `mix corpus.generate`.

### Key Discoveries

- The `isa_sync_test` evaluator-clause regex is
  `~r/defp execute_instruction\(%__MODULE__\{\}[^,]*, \["([a-z_]+)"/`
  (`isa_sync_test.exs:290`). `%__MODULE__\{\}` requires **literally empty
  braces**, so the dispatch clause must be
  `defp execute_instruction(%__MODULE__{} = evaluator, ["store", n])` and the
  stack pattern-matching must live in a delegated `execute_store/2`. This is
  the shape every existing multi-clause opcode already uses
  (`execute_compare/2`, `execute_make_list/2`).
- `Instructions.@opcodes` (`instructions.ex:64-90`) is the single registry every
  public function in that module reads; adding a row is the whole code change
  there.
- The conformance generator's `encode_error/1`
  (`conformance/generator.ex:373-385`) has **no catch-all clause**: it handles
  `EvaluationError`, `TypeMismatchError`, and `UndefinedVariableError` only, and
  `docs/isa.md:106-108` states those three are the whole normative taxonomy. A
  `LocationError` escaping the VM would crash corpus generation. This decides
  Q4 below.
- The generator evaluates every case through `Predicator.evaluate(instructions,
  context, [])` (`generator.ex:340-347`) - **expression mode**. This decides Q9
  below.
- `Instructions.opcode_set/1` is what both the corpus gate and the manifest's
  per-tier `opcodes` array read, so registering an opcode and covering it in the
  corpus cannot be split across commits.
- ADR-0009's Consequences (`0009:198-203`) pre-empt `execute/2`'s shape: inherit
  the `%Compiled{}` envelope rather than growing a fourth tuple element.

## Desired End State

After this plan:

```elixir
iex> {:ok, ctx} = Predicator.execute("x = 1; y = x + 2", %{})
iex> ctx.data
%{"x" => 1, "y" => 3}

iex> {:error, %Predicator.Errors.EvaluationError{reason: "not_a_container"}, ctx} =
...>   Predicator.execute("a = 1; a.b = 2; c = 3", %{})
iex> ctx.data
%{"a" => 1}          # prior write survives; `c` never ran
```

- `["store", n]` and `["pop"]` are live ISA v3 opcodes, tier 6, documented in

- `Compiler.to_instructions/2` and `to_instructions_with_positions/2` accept a
  `Parser.program()` and emit a flat statement program.
- `Predicator.compile_program/1`, `Predicator.compile_program_with_positions/1`,
  and `Predicator.execute/1,2,3` exist, specced, documented, doctested.
- `mix quality` is green, coverage stays above `coveralls.json`'s 90%, and
  `mix corpus.generate --check` is clean.

Verification: `mix quality` plus the round-trip
`Predicator.parse_program/2 |> Compiler.to_string/2` still returning the source

## What We're NOT Doing

- **Not minting ISA v4.** See "ISA Impact" - `store` and `pop` join v3.
- **Not giving `InstructionsVisitor` an error channel.** It still returns a bare
  list and still raises on an unhandled node. Research Q8; that convention gap
  is recorded in `docs/plans/260807-px-tbv.1-statement-grammar.md:1038-1042` and
  belongs to a bead of its own. Teaching it two nodes it can always handle is
  not the moment to change it.
- **Not surfacing the last expression statement's value** from `execute/2`. See
  Q3 below for the reasoning and the recorded open question.
- **Not adding statement-level control flow** (`if`, loops). ADR-0001
  `:107-109` puts it outside 4.0.
- **Not writing an ADR for the statement layer.** `docs/adr/README.md:52-54`
  schedules it with its release; ADR-0001 specifies `store` and ADR-0009
  pre-empts `execute/2`'s shape, which is enough to implement from.
- **No version bump and no changelog promotion.** Release mechanics are
  px-tbv.5's (CLAUDE.md authority table). This plan adds entries *under*
  `## [Unreleased]` only.
- **Not adding `:position`/`:span` to `LocationError`.** See Q4.
- **Not rewriting `docs/guides/porting.md` or `embedding.md`.** Both defer to
  `docs/isa.md` and `conformance/manifest.json` for opcode lists rather than
  duplicating them (verified: neither names an opcode set), so both stay correct
  by construction.

## Implementation Approach

Four phases, ordered so `mix quality` is green at every boundary.

The first phase is deliberately large and cannot be subdivided: `isa_sync_test`
binds `Instructions.@opcodes` to `docs/isa.md`'s tables **and** to the literal
`execute_instruction/2` clause heads, while `opcode_coverage_test` binds the
same registry to the authored corpus. Registering `store` without its evaluator
clause is red; adding the clause without registering it is red; doing both
without a corpus case is red. So the opcode lands end-to-end in one commit:
registry, VM, spec, sync constants, guard flips, corpus.

Phases 2 and 3 then split along the pipeline's natural seams - compiler/visitor,
then façade - and each is independently green because the opcodes already exist
and run. Phase 4 is the prose sweep and the changelog.

### The design decisions this plan settles

These are the research doc's open questions, answered here with reasoning. They
are not to be re-argued during implementation.

**Q1. ISA version: `store` and `pop` join ISA v3. No v4 is minted.**

§1's "a version's opcode set is fixed once minted" (`isa.md:42-47`) binds
versions that have *shipped*. §7 (`isa.md:473`) lists v3 as "Shipped in 4.0.0",
and 4.0.0 has not been cut - px-tbv.5 is the release bead and is still open, and
`git tag` tops out at `v3.8.0`. **No sibling, consumer, or stored artifact has
ever seen v3**, so nothing observable changes by widening its set. Minting v4
inside the same unreleased release would give 4.0.0 two ISA integers and leave
v3 as a version no build ever shipped, which is a worse artifact for a sibling
implementer to read than an introduce-and-retire row. §1's half-open-interval
model already permits a version that both introduces and retires: v3's set
becomes "everything from v1 and v2, minus `and`/`or`, plus `store`/`pop`", which
is exactly what `opcode_set(3)` will compute from the registry.

Consequence: §1's sentence "ISA v3 minted no opcode at all: it retired `and` and
`or`, shipping in 4.0.0 as the first version the integer moves for without a new
opcode" (`isa.md:27-28`) becomes **false** and must be rewritten. §7's row
becomes `| v3 | `store`, `pop` | `and`, `or` | 4.0.0 |`, and §7's prose "A
version whose only change is a retirement still gets a row here, as v3 does"
(`isa.md:477-478`) must lose its "as v3 does" example.

`@isa_version` stays `3`. `isa.md:58`'s `Current version:` line stays. The
`isa_sync_test` max-version test still passes: `max(ISA column ∪ removed_in) = 3`.

**Q2. `["store", n]`'s stack discipline: segments pushed first in root-to-leaf
order, value pushed last (stack top). `store` pops the value, then `n` segments,
reversing them back into root-first path order.**

This is the house convention, not a new one: `make_list` "pops `count` values
and pushes them as a list **in source order**: the stack holds them reversed,
deepest first, and this opcode reverses them back" (`isa.md:391-394`), and
`call` says "the deepest (pushed first) is the first argument"
(`isa.md:371-373`). Emitting the lhs chain before the rhs also preserves source
order, which keeps the position table's instruction indices monotonic in the
source and avoids the compiler having to hold the rhs's instructions aside.

For `user.items[0].name = 'Ada'` (path `["user", "items", 0, "name"]`, n = 4):

```json
[["lit","user"],["lit","items"],["lit",0],["lit","name"],["lit","Ada"],["store",4]]
```

**`n` is the chain's segment depth, not the number of instructions the segments
compiled to.** A computed bracket key compiles to arbitrary many instructions -
`a[k+1] = 1` emits `["lit","a"],["load","k"],["lit",1],["add"],["lit",1],["store",2]`
- so `n` is computed by recursing the lhs chain structurally, exactly as
ADR-0001 and `parser.ex:158-168` describe. It is **not** derived by counting the
emitted sub-list the way `logical_and`'s jump offset is.

**Q3. `store` pushes nothing (Pops `n+1`, Pushes 0). `pop` is emitted after
every expression statement and after no assignment statement.**

`docs/isa.md:130-134` is already published and already says "a well-formed
statement program ends each statement with a `store` **or** a `pop`". A `store`
that pushed would make that sentence false and would push a value whose only
possible next use is being discarded. So `store` consumes everything it pops.

The compiler therefore emits, per statement:

| Statement node | Emits |
|---|---|
| `{:assignment, lhs, rhs, _}` | segments ++ rhs ++ `["store", n]` |
| any expression node | its instructions ++ `["pop"]` |

The trailing `pop` is emitted **uniformly, including after the program's last
statement**. Two reasons. First, it makes each statement's instruction block
self-contained: the stack is empty at every statement boundary, which is what
makes §2's "halts with an empty stack by design" true and what makes
concatenating two compiled programs produce a valid third. Second, omitting the
final `pop` would make the compiled artifact depend on a statement's *position*
in the program, so the same statement compiles to two different lists - a
composition and serialization hazard in an interchange format ADR-0001 exists to
protect.

**The cost, stated plainly:** the AC's "plus cheaply the last expression's
value" is not delivered by this bead. The return type the bead itself fixes,
`{:ok, %Context{}}`, has no slot for it; `isa.md:144-147` already classes it a
host-API convenience rather than an ISA guarantee; and the two ways to deliver
it (a non-uniform final `pop`, or a third success-tuple element) are the two
things this plan and ADR-0009 respectively rule out. Recorded as Open Question 1
below with a concrete follow-up shape.

**Q4. A `put/3` failure is wrapped in an `EvaluationError`, not surfaced as a
`LocationError`.**

Decisive: `docs/isa.md:105-108` states three error types are the whole normative
taxonomy, and the conformance generator's `encode_error/1`
(`generator.ex:373-385`) has no catch-all - a fourth type reaching it crashes
generation, deliberately ("a fourth showing up here is a spec change worth a
loud crash"). Returning a `LocationError` from the VM would make a store-error
conformance case ungeneratable.

Wrapping also solves the position problem for free: an `EvaluationError` has
`:position`/`:span`, so the evaluator's existing `attach_position/2`
(`evaluator.ex:333-338`) stamps the failing `["store", n]` instruction's
position with no new machinery, where `Errors.put_position/2` on a
`LocationError` is a silent no-op.

The mapping, in `store`'s clause:

| `%LocationError{type: ...}` | becomes |
|---|---|
| `:not_assignable` | `EvaluationError.new(location_error.message, "not_assignable", :store)` |
| `:not_a_container` | `EvaluationError.new(location_error.message, "not_a_container", :store)` |
| `:invalid_index` | `EvaluationError.new(location_error.message, "invalid_index", :store)` |

The `LocationError`'s message is carried through verbatim (messages are
non-normative per `isa.md:105`); its `type` becomes the `reason`, which *is*
normative. `Context.assign/3` and `ContextLocation.put/3` keep returning
`LocationError` unchanged - they are not VM paths and no ISA rule binds them.

**Not adding `:position`/`:span` to `LocationError`.** It is the return type of
two non-VM functions that have no instruction to blame; adding evaluation-time
fields to it would repeat the mistake px-h66 rejected for the error structs
generally (`260807-px-h66:138-141`).

**A wrong-typed segment is a `TypeMismatchError`.** A popped segment that is not
a binary or an integer (a boolean, a float, `:undefined` from an unbound
computed key) is `TypeMismatchError` with operation `:store` and expected
`"string"`, message naming string and integer as the accepted segment types.
This mirrors `bracket_access` exactly (`isa.md:363-369`), which is the *read*
side of the same segment, and it keeps a bad key reported the same way whichever
side of the `=` it appears on. `put/3` is never called with an out-of-domain
path, so its `location_path()` spec stays honest.

**Q5. `execute/2` accepts source, an instruction list, or a `%Compiled{}` -
mirroring `evaluate/3` clause for clause.**

The bead says `program_or_source`, and ADR-0009 says later entry points inherit
the envelope. Three clauses, in `evaluate/3`'s order:

```elixir
def execute(%Compiled{} = compiled, context, opts)
def execute(source, context, opts) when is_binary(source)      # parse_program/2 path
def execute(instructions, context, opts) when is_list(instructions)
```

Producing a `%Compiled{}` for a program needs a compile entry point, so this
bead also adds `Predicator.compile_program/1` and
`Predicator.compile_program_with_positions/1`, the program-shaped echoes of
`compile/1` and `compile_with_positions/1`. Without them the `%Compiled{}`
clause is unreachable by any public path, and a consumer that wants to store a
compiled statement program (the whole point of ADR-0001's flat artifact) has no
way to make one.

**Q6. `Compiler.to_instructions/2` widens; no new compiler function appears.**

px-tbv.1 declined to widen `parse/2` because its **return type** would have had
to widen too (`program_result()` vs an expression AST). That reason does not
apply here: a statement program compiles to an ordinary flat instruction list,
which is the same return type - that is precisely ADR-0001's claim. `to_string/2`
and `Visitor.accept/3` already widened for the same reason. Widening keeps
"compile an AST" one function.

**Q7. Corpus: authored tier-6 cases using the existing `{"result": ...}` shape.
No new `expected` variant, no new generator path, no exclusion.**

The generator runs each case through `Predicator.evaluate(instructions, context,
[])` - expression mode. That is not an obstacle, because `store`'s effect is
**observable from expression mode through a subsequent `load`**: the opcodes are
identical in both modes (`isa.md:124-126`), and only what "result" means
differs. So a case ends with a read that puts the written value on the stack:

```json
{ "id": "statements/store-root",
  "instructions": [["lit","x"],["lit",42],["store",1],["load","x"]],
  "expected": { "result": 42 } }
```

This is better than a new `expected: {"context": ...}` variant on three counts:
it needs no generator change, no schema change, and no manifest change; it pins
exactly the property a sibling must reproduce (a later `load` sees the write)
rather than a context serialization the ISA does not specify; and it keeps every
corpus case a single uniform shape, which is what a sibling's runner is written
against (`conformance/README.md`, `RATCHET.md`). An exclusion entry is the wrong
answer outright - the exclusion mechanism exists for opcodes no case *can* pin
(`relative_date` reads the clock), and these two are fully deterministic.

**Q8. The four guard tests flip in the phase that makes them false**, two in
Phase 1 and two in Phase 2, as itemized there.

## Phase 1: The `store` and `pop` opcodes

### Overview

### Changes Required

#### 1. The opcode registry

**File**: `lib/predicator/instructions.ex`
**Changes**: two entries in `@opcodes` (`:64-90`). `@isa_version` stays `3`.

```elixir
"store" => %{isa: 3, tier: 6},

```

#### 2. The VM

**File**: `lib/predicator/evaluator.ex`
**Changes**: two `execute_instruction/2` clauses plus their helpers, placed with
the other opcode clauses and **before** the retired/unknown fallback at
`:503-515`. The clause heads must use literally-empty `%__MODULE__{}` braces so
`isa_sync_test.exs:290`'s regex sees them:

```elixir
defp execute_instruction(%__MODULE__{} = evaluator, ["store", n])
     when is_integer(n) and n >= 0 do
  execute_store(evaluator, n)
end

defp execute_instruction(%__MODULE__{} = evaluator, ["pop"]) do
  execute_pop(evaluator)
end
```

`execute_store/2`:
- pops the value (stack top), then `n` segments; fewer than `n + 1` values on
  the stack is `EvaluationError.insufficient_operands(:store, length(stack), n + 1)`;
- reverses the `n` popped segments into root-first order;
- validates every segment is a `binary()` or an `integer()`, else
  `TypeMismatchError.unary/4`-style error with operation `:store`, expected
  `"string"` (see Q4);
- calls `ContextLocation.put(evaluator.context, path, value)`;
- on `{:ok, new_context}` returns
  `{:ok, %__MODULE__{evaluator | context: new_context, stack: rest}}` - the
  first context write in the VM's history;
- on `{:error, %LocationError{}}` wraps per Q4's table.

`execute_pop/1`: pops one value, discards it; an empty stack is
`EvaluationError.insufficient_operands(:pop, 0, 1)`.

Add `alias Predicator.ContextLocation` and the `LocationError` alias if not
already present. **Check for a cyclic alias risk**: `ContextLocation` currently
calls `Lexer`/`Parser` in `resolve_expression/2` but not `Evaluator`, so
`Evaluator -> ContextLocation` is acyclic. Confirm at implementation time; if it
is not, call `Predicator.ContextLocation.put/3` fully qualified (a runtime call,
no compile-time dependency).

Operand guards follow `isa.md:99-104`: `["store", -1]`, `["store", "2"]`, and
`["pop", 1]` all fall through to the catch-all and are `"unknown_instruction"`.
`["store", 0]` is **accepted** by the guard and produces the wrapped
`not_assignable` error from `put/3`'s empty-path clause, so that specified error
path stays reachable - the same reasoning `object_set`'s non-map case is given
at `isa.md:386-390`.

The two §5 bullets must be precise enough for a sibling to implement from -
they are the normative statement of Q2 and Q4:

- **`store`** (`execute_store/2`) - pops the value from the stack top, then `n`
  location segments beneath it, and reverses those `n` into root-first path
  order: the compiler pushes segments root-to-leaf followed by the value, so the
  stack holds the segments deepest-first, exactly as `make_list` does. Writes
  `path -> value` into the evaluator's context via the same write algorithm
  `Predicator.ContextLocation.put/3` implements: a missing or `:undefined`
  interior slot is auto-vivified as a list when the next segment is an integer
  and a map otherwise, an integer past a list's end pads with `:undefined`, and
  the leaf is always overwritten. **Pushes nothing.** Fewer than `n + 1` values
  on the stack is `EvaluationError` insufficient operands. A segment that is
  neither a string nor an integer is `TypeMismatchError` (operation `store`,
  expected `string`), the mirror of `bracket_access`'s key rule. A write that
  cannot be performed is `EvaluationError` with reason `not_assignable` (empty
  path, only reachable from a hand-built `["store", 0]`), `not_a_container` (an
  interior segment holds a scalar), or `invalid_index` (a negative list index).
  This is the only opcode that writes the context.
- **`pop`** (`execute_pop/1`) - discards the stack top and pushes nothing. The
  statement-boundary opcode: the compiler emits it after every expression
  statement so the next statement starts from a clean stack. An empty stack is
  `EvaluationError` insufficient operands. It is unrelated to
  `jump_if_falsy_or_pop`/`jump_if_true_or_pop`, which pop conditionally as part
  of a jump.

## Phase 2: Compiling programs and assignments

### Overview

Teach `InstructionsVisitor` the two statement nodes and widen `Compiler`'s two

### Changes Required

#### 1. `InstructionsVisitor`

**File**: `lib/predicator/visitors/instructions_visitor.ex`
**Changes**: two `visit_annotated/2` clauses and a segment helper. All return
`[annotated()]`, one entry per instruction, so the existing offset arithmetic
and position zipping are unaffected.

```elixir
defp visit_annotated({:program, statements, _position}, opts) do
  Enum.flat_map(statements, &visit_statement(&1, opts))
end

defp visit_annotated({:assignment, lhs, rhs, position}, opts) do
  segments = location_segments(lhs, opts)
  depth = location_depth(lhs)

  segments ++ visit_annotated(rhs, opts) ++ [{["store", depth], position}]
end
```

`visit_statement/2` dispatches: an `{:assignment, ...}` compiles to its own
instructions, anything else compiles to its instructions ++
`[{["pop"], node_position}]` (Q3). Take the statement node's own position slot
for the `pop`; a `pop` never errors, so this is for the position table's
completeness, not for blame.

`location_segments/2` walks the chain root-to-leaf:

```elixir
defp location_segments({:identifier, name, position}, _opts), do: [{["lit", name], position}]

defp location_segments({:property_access, object, property, position}, opts),
  do: location_segments(object, opts) ++ [{["lit", property], position}]

defp location_segments({:bracket_access, object, key, _position}, opts),
  do: location_segments(object, opts) ++ visit_annotated(key, opts)
```

`location_depth/1` counts segments structurally - `1` at the identifier, `+1`
per wrapper - and is **not** `length(location_segments(...))`, which a computed
bracket key would inflate (Q2). Comment this at the definition; it is the one
place a plausible-looking simplification is wrong.

The parser guarantees the lhs is an identifier/property_access/bracket_access
chain (`assignable_location?/1`, `parser.ex:533-541`), so no other clause is
needed and no error channel is introduced (see What We're NOT Doing).

## Phase 3: `Predicator.execute/2` and the program compile path

### Overview

The statement-mode entry point. Adds the state-preserving runner the VM is
missing, the two program compile functions, and `execute/1,2,3`.

### Changes Required

#### 1. A statement-mode runner

**File**: `lib/predicator/evaluator.ex`
**Changes**: promote the private `run_state/1` (`:287-295`) to a public,
`@doc`'d, `@spec`'d function. `run_prepared/1` and `run/1` keep calling it
unchanged.

```elixir
@doc """
Runs an already-built evaluator to halt, returning the final state on both
paths.

This is statement mode's entry point (`docs/isa.md` section 2): unlike
`run_prepared/1` it applies no expression-mode result rule, so an empty stack
at halt is a normal halt rather than `empty_stack`. On error the state
returned is the pre-step one, holding every write the statements before the
failing instruction performed.
"""
@spec run_state(t()) :: {:ok, t()} | {:error, struct(), t()}
def run_state(%__MODULE__{halted: true} = evaluator), do: {:ok, evaluator}
```

#### 2. The façade

**File**: `lib/predicator.ex`
**Changes**: three new public functions plus a private core.

```elixir
@spec compile_program(binary()) :: {:ok, Types.instruction_list()} | {:error, binary()}
@spec compile_program_with_positions(binary()) :: {:ok, Compiled.t()} | {:error, binary()}
@spec execute(binary() | Types.instruction_list() | Compiled.t(), Context.t() | Types.context(), keyword()) ::
        {:ok, Context.t()} | {:error, struct(), Context.t()}
def execute(program_or_source, context \\ %{}, opts \\ [])
```

`compile_program/1` and `compile_program_with_positions/1` are `compile/1` and
`compile_with_positions/1` with `Parser.parse_program/2` in place of
`Parser.parse/2`; they return the same `{:error, binary()}` shape those two use
(not `parse_program/2`'s raw 4-tuple - the compile family's convention wins on
the compile family's functions, and the research notes the two conventions
already coexist).

`execute/3`'s three clauses mirror `evaluate/3` (`:161-197`) exactly, including
`reject_positions_option!/1` on the `%Compiled{}` clause and returning a
`%ParseError{}` (not a raw tuple) on the source clause, matching `evaluate/3`'s
convention for a runtime entry point.

The private core, beside `evaluate_instructions/3` (`:200-223`):

```elixir
defp execute_instructions(instructions, %Context{} = context, opts) do
  evaluator = %Evaluator{
    instructions: instructions,
    context: context.data,
    functions: context.functions,
    positions: Keyword.get(opts, :positions, %{}),
    on_unbound: context.on_unbound
  }

  case Evaluator.run_state(evaluator) do
    {:ok, final} ->
      {:ok, %{context | data: final.context}}

    {:error, error_struct, final} ->
      {:error, unbound_or_type_mismatch(error_struct, final), %{context | data: final.context}}
  end
end

defp execute_instructions(instructions, context, opts) when is_map(context) do
  execute_instructions(instructions, Context.new(context, opts), opts)
end
```

Four properties this shape delivers, each worth a test:

- **No `empty_stack`.** `run_state/1` has no result rule, so a well-formed
  statement program halting with an empty stack succeeds.
- **Stop-on-error without rollback** (px-h66, ADR-0009 unaffected). `final` on
  the error path is the pre-step evaluator, so `final.context` holds every
  completed statement's write and nothing from the failing one.
- **Errors keep evaluate's shapes.** Reusing `unbound_or_type_mismatch/2`
  (`:323-333`) means an unbound root reported by a statement program reads the
  same as one reported by an expression.
- **The returned `%Context{}` is the input one with `data` rebound.**
  `functions` and `on_unbound` survive, and no re-normalization is needed: every
  value `store` writes is already in the VM's normalized value domain.

Document in `execute/3`'s `@doc`, with a doctest each: the success shape, the
partial-context error shape, and the one-clause discard idiom px-h66 names -

```elixir
case Predicator.execute(program, ctx) do
  {:ok, ctx} -> ctx
  {:error, _error, _partial} -> ctx    # all-or-nothing is a caller policy
end
```
