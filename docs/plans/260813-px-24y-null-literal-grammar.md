# Null Literal Grammar Implementation Plan

## Overview

Give null a source spelling. `null` becomes a reserved literal keyword that
lexes to a literal token, parses to `{:literal, nil, pos}`, lowers through the
existing generic clause to `["lit", nil]`, and renders back as `null` through
`StringVisitor`. This is the deferred **literal half** of px-o9v, which landed
the value half: null already survives the context boundary, has defined
semantics at every opcode, and is pinned in the conformance corpus.

This plan adds a way to **write** null. It changes nothing about what null
**means** - px-o9v's decisions D1-D6 are settled and are not reopened here.

Bead: px-24y (depends on px-o9v, closed).

## Current State Analysis

`null` has no clause in `classify_identifier/1`
(`lib/predicator/lexer.ex:498-520`), so it falls to the catch-all at `:520` and
becomes `{:identifier, "null"}`. That single line is why `x === null` compiles
to `[["load","x"],["load","null"],["compare","STRICT_EQ"]]` today, and why a
predicate asking the question that *looks* like a null test silently answers
`false` for a variable genuinely bound to null - the phantom `null` variable
loads as `:undefined` under the default `on_unbound` policy.

Everything downstream of the parser is already null-ready:

- Every literal folds into one AST tag, `{:literal, value, position}`
  (`lib/predicator/parser.ex:159-160`). There is no per-literal tag.
- `InstructionsVisitor.visit_annotated/2`
  (`lib/predicator/visitors/instructions_visitor.ex:174-176`) passes the value
  through structurally to `["lit", value]`. No new clause.
- `execute_instruction(evaluator, ["lit", value])`
  (`lib/predicator/evaluator.ex:489-491`) is guardless and pushes whatever it
  is handed. No operand validation exists anywhere on the `lit` path.
- `Predicator.Types.value/0` (`lib/predicator/types.ex:38-66`) already ends
  `| :undefined | nil`, widened by px-o9v.
- The conformance codec already round-trips null: `to_json(nil)`
  (`lib/predicator/conformance/values.ex:77`) and `from_json(nil)` (`:131`).
  Null is JSON-native, so `["lit", nil]` does **not** enlarge px-a2w's
  four-member lossy set (`docs/isa.md:205-210`).

What is missing is entirely upstream: a lexer clause, a parser primary clause,
a `format_token/2` clause, and a `StringVisitor` clause - the exact four
production clauses px-ocp's `undefined` literal touched in 5.0.0.

**The blast radius of the reservation is narrower than the bead implies.** An
exhaustive sweep (research §3) found **zero** uses of `null` as a predicate
identifier in `lib/`, `test/`, `conformance/cases/`, `conformance/corpus/`, or
`README.md`. Every px-o9v corpus null case sources its null from `context`
(`{"x": null}`) with `x`/`y` identifiers, so **the corpus needs no sweep** -
only additive cases. The entire executable breakage is four doctest lines in
one file, `docs/reference/language.md:929-934` and `:940-945`, executed by
`test/docs_examples_test.exs:14`. They exist precisely as the tripwire this
bead must trip.

Two whitelists mean the breakage at the other two sites falls out for free:
property access after `.` accepts an explicit token-type list
(`lib/predicator/parser.ex:1263-1290`) and object keys accept only
`:identifier` or `:string` (`:1768-1781`). A new keyword's token type is on
neither list, so `user.null` and `{null: 1}` become parse errors with no edit.
`format_token/2` (`:1561-1613`) is the one site that **must** be edited: it has
no catch-all, and an omission turns those two parse errors into a
`FunctionClauseError`, which is an ADR-0004 breach.

## Desired End State

- `null` is a reserved literal keyword. `null`, `x === null`, `[null]`, and
  `{k: null}` all parse; `null = 3`, `user.null`, and `{null: 1}` are parse
  errors with helpful messages; `{"null": 1}` still parses; `NULL` and `Null`
  stay ordinary identifiers.
- `Predicator.compile("x === null")` returns
  `{:ok, [["load","x"],["lit",nil],["compare","STRICT_EQ"]]}`, and
  `Predicator.evaluate("x === null", %{"x" => nil})` returns `{:ok, true}` -
  the question a user thought they were asking now gets the answer they
  expected.
- `Predicator.decompile/1` renders the literal back as `null`, and
  parse -> decompile -> parse is a fixpoint for `x === null` and `[null]`.
- The conformance corpus carries literal-form null cases beside px-o9v's
  context-sourced ones, generated by `mix corpus.generate`.
- `docs/isa.md` §§1, 3, 5, 6 no longer contain a false sentence about null
  having no source spelling, and §1's versioning rule no longer rests on a
  condition this change falsifies. **The ISA version does not move** - see ISA
  Impact.
- `CHANGELOG.md`'s `## [Unreleased]` carries the paired entries a literal
  reservation gets: an `### Added` bullet for the literal and a `### Changed`
  bullet, marked BREAKING, for the reserved word, carrying the migration note -
  and px-o9v's own still-unreleased bullet no longer claims null has no source
  spelling.

Verified by: full `mix quality` green at the end of every phase, plus each
phase's manual checks.

### Key Discoveries:

- The reserved-word table is a function, not data:
  `lib/predicator/lexer.ex:498-520`. There is no list to append to, and "the
  reserved words" cannot be enumerated programmatically -
  `docs/reference/language.md:394-405` is the human-readable list and nothing
  binds it to the lexer.
- `format_token/2` (`lib/predicator/parser.ex:1561-1613`) has no catch-all.
  px-ocp's plan calls this "the easiest thing in the change to miss".
- `test/predicator/visitor_clause_coverage_test.exs:48` asserts exactly 23 AST
  constructors. Reusing `{:literal, value, pos}` adds none, so that binding
  test must pass **unchanged**; needing to edit it means a new tag was
  introduced by mistake.
- `test/predicator/isa_sync_test.exs` binds only §1's `Current version:` line
  (`:86-88`) and §4's tables. Edits confined to §1's prose bullets, §3, §5
  prose, or §6 do not trip it - and are therefore unguarded and must be checked
  by reading.
- `conformance/examples/registry.example.json` is hand-maintained, not
  generated; `ratchet_registry_test.exs` goes red on both the pin (`:81`) and
  R5 completeness (`:112`) when `corpus_hash` rotates.
- ADRs in scope: ADR-0001, ADR-0002 (the notice-period precedent), ADR-0003
  (this repo leads the ISA; the corpus is exported specification), ADR-0004
  (errors are values - the `format_token/2` obligation), ADR-0011 (the
  contextual-keyword counterexample), ADR-0013 (reserve-early).

### Decisions taken as given (not re-litigated here)

**Scheduling.** The bead requires the change to "land on a breaking bump, never
forcing one", and nothing in the tracker schedules a 6.0.0. **This does not
block the work.** Implementing the reservation on this feature branch does not
force a release: version bumps, tags, and publishing are separately human-gated
(CLAUDE.md's authority table - release mechanics need an explicit human ask
naming the version, and `mix hex.publish` has no trigger at all). This plan
therefore lands with its CHANGELOG entry under `## [Unreleased]`, clearly
marked BREAKING, and leaves the bump to whoever cuts the release. **No
`@version` edit in `mix.exs`. No tag. No README pin bump.** The PR body carries
this reasoning so a reviewer does not read the missing bump as an omission.

**No deprecation cycle.** A straight break, matching the
`if`/`else`/`while`/`undefined` reservations in 5.0.0 rather than the `=`
deprecation in ADR-0002. The deprecation infrastructure was deleted in 4.0.0
(`grep -rn "deprecat" lib/` returns nothing) and rebuilding it for one keyword
is not proportionate, especially against a sweep this clean. The migration note
carries the warning instead, and it must name the silent case concretely: a
predicate using `null` as a variable name **keeps evaluating rather than
failing** in the `x === null` shape - the answer changes from `false` to `true`
- while `null = 3`, `user.null`, and `{null: 1}` fail loudly.

**Case sensitivity.** `NULL` and `Null` stay ordinary identifiers, matching
every existing keyword in this lexer (there is no `TRUE` clause and no
`UNDEFINED` clause). Pinned by a test in Phase 1.

**Semantics are px-o9v's.** The four-way matrix (`null === undefined` false,
`null == undefined` `:undefined`, `null === null` true, `null == null`
`:undefined`), falsiness at a jump, rejection by `not` and arithmetic,
identity under membership, and collapse to `:undefined` under any cast are all
fixed by `docs/plans/260813-px-o9v-null-vs-undefined-in-context.md` D1-D6.
This plan writes tests that *observe* them through the new spelling; it changes
none of them. If any evaluator behavior appears to need changing to make a
literal work, that is a bug in the change, not a semantics question.

## Implementation Approach

Mirror px-ocp's three-phase shape for the `undefined` literal
(`docs/plans/260812-px-ocp-undefined-literal.md`), with one deliberate
difference: **the language-reference edits move into Phase 1 rather than the
documentation phase.** `docs/reference/language.md`'s doctests are executed by
the suite, so the moment `null` lexes as a keyword the gate goes red until they
are fixed. A phase that reserves the keyword and a phase that repairs the
doctests it breaks cannot be separate phases without leaving an intermediate
gate red, which is exactly what the phase-sizing rule forbids.

The remaining documentation - `docs/isa.md`, the architecture EBNF, and the
changelog - is inert with respect to the gate and stays in its own phase, which
keeps the ISA argument reviewable on its own diff.

1. **Phase 1** - lexer, parser, `StringVisitor`, the ExUnit suites, and every
   edit `docs/reference/language.md` needs to be true and green again.
2. **Phase 2** - conformance: authored cases, `mix corpus.generate`, and the
   ratchet example the new `corpus_hash` invalidates.
3. **Phase 3** - `docs/isa.md` §§1/3/5/6, the architecture EBNF, and the paired
   changelog entries with the migration note.

## ISA Impact

**1. Version - no. The ISA stays at v6.**

The rule, quoted in full from `docs/isa.md:33-38`:

> - Adding an operand form or widening an accepted type is a new version but
>   not a new name. This rule speaks to operand forms carried *in the
>   instruction list* - widening §3's value domain with a value that only a
>   host-supplied context can produce, and that no opcode can place on the
>   stack, moves no version, because no opcode-name scan can express it (§6's
>   `undefined` literal precedent, and line 415's, are the same shape).

The rule's antecedent is **"adding an operand form or widening an accepted
type"** - it is about what a conformant implementation must *accept and
execute*. A null literal widens neither:

- §3's value domain already contains `null` (`docs/isa.md:176-186`), put there
  by px-o9v.
- §5's `lit` entry already documents the operand as "any value in §3's value
  domain" (`docs/isa.md:350-355`), and calls `["lit", nil]` "legal under that
  same widened §3 domain in principle".
- This build already executes `["lit", nil]` correctly:
  `execute_instruction(_, ["lit", value])` is guardless
  (`lib/predicator/evaluator.ex:489-491`).

So **the set of instruction lists a conformant v6 implementation must run is
identical before and after this change.** What changes is only which of those
lists *this compiler emits from source*, and §6 (`docs/isa.md:769-786`)
excludes surface syntax from the ISA, with `=`/`==` and the `undefined` literal
as worked examples of exactly that shape.

The reinforcing argument from px-ocp still holds: `required_isa/1`
(`lib/predicator/instructions.ex:292-303`) computes a list's required version
as `max` over `@opcodes[name].isa` and never inspects an operand. A v7 whose
only content is "the compiler now emits an operand it could always execute"
attaches to no opcode name, so no instruction list would ever report requiring
it and `opcode_set(7)` would equal `opcode_set(6)`. ADR-0003 makes the
opcode-name scan a *sound* answer to "what version does this list require";
minting a version the scan can never produce degrades that soundness for
nothing.

**The wrinkle, answered.** px-o9v's clarifying sentence above is scoped by a
conjunction - a value "that only a host-supplied context can produce, **and
that no opcode can place on the stack**" - and a null literal falsifies the
second conjunct. That sentence must be amended, and the amendment does **not**
imply a version move, because the condition it states was **sufficient, not
necessary**. It was written to excuse px-o9v's domain widening, which is the
step that could have looked like "widening an accepted type"; it is not a
general test for when a version moves. The general test is the bullet's own
antecedent plus §1's opcode-name rule at `:29-32` ("An opcode's semantics never
change under its own name"), and by that test:

- px-o9v widened §3's domain at the host boundary and moved no version - a
  decision already taken, shipped in `## [Unreleased]`, and not reopened here.
- px-24y adds a **spelling** for a value that domain already admits and that
  `lit` already accepted. Under §6 that is surface syntax and moves no version,
  identically to the `undefined` literal in 5.0.0.

Reading the sentence the other way would produce an absurdity: it would mean
px-o9v's no-move decision is retroactively invalidated by a later source-syntax
change that adds no opcode and changes no instruction's meaning. The
instruction lists a v6 implementation must run would have to differ depending
on which *compiler* wrote them, which contradicts §1's premise that a list's
required version is a function of its opcode names alone.

**Library semver is a separate question and is unambiguous**: reserving a word
is a breaking change to the grammar and needs a major bump, regardless of what
the ISA integer does. That is what the BREAKING changelog entry records, and
per the scheduling decision the bump itself is not this branch's to make.

**Consequent obligations - none is engaged.** Stated explicitly so
implementation is unambiguous; do **not** touch any of these:

| Site | Action |
|---|---|
| `docs/isa.md:62` `Current version: **ISA v6**.` | unchanged |
| `docs/isa.md` §4 opcode table (ISA / tier / Removed-in columns) | unchanged |
| `docs/isa.md:796-812` §7 version-history table | unchanged - no new row |
| `docs/isa.md:197-243` §3's plain-JSON lossy table | unchanged - null is JSON-native, the lossy set stays at four |
| `lib/predicator/instructions.ex:45` `@isa_version 6` | unchanged |
| `lib/predicator/instructions.ex:64-96` `@opcodes` | unchanged - no new name |
| `test/predicator/isa_sync_test.exs` | unchanged - no edit should be needed |
| `conformance/manifest.json` `isa_version` | stays `6` (regenerated, never hand-edited) |
| `lib/predicator/instructions/upgrade.ex` | untouched - nothing retired |

**2. Stamp.** No opcode subsection, no version entry, no new tier. Four prose
amendments to `docs/isa.md`, all outside every table `isa_sync_test.exs`
parses, specified in Phase 3: §1's px-o9v sentence (`:33-38`), §3's null
paragraph (`:179-186`), §5's `lit` entry (`:350-355`), and §6's surface-syntax
bullet (`:778-786`). Corpus coverage lands in Phase 2 at tier 1 (`lit`, `load`,
`compare`) and tier 3 (`access`).

**3. Migration.** For the ISA: none. No stored instruction list changes
meaning, none becomes invalid, nothing is retired, and a sibling at v6 that
implements `lit` per §3's value domain needs no change to run the new corpus
cases - if it fails them, the corpus has surfaced a pre-existing v6 conformance
gap in that sibling, not a new obligation. A sibling's *lexer* is a different
matter and diverges deliberately until it adopts the break on its own schedule
(ADR-0002's sibling consequence, ADR-0003).

For the **language**, migration is real and is what the changelog entry owes:

- **Loud**: `null = 3`, `user.null`, `{null: 1}` become parse errors. Fix by
  renaming the variable or quoting the key (`{"null": 1}` still parses).
- **Silent, and the one to name first**: a predicate that used `null` as a
  *variable name* in expression position keeps evaluating rather than failing,
  and can change answer. `x === null` compiled to
  `[["load","x"],["load","null"],["compare","STRICT_EQ"]]` and answered
  `false` for a bound null (the phantom variable loaded as `:undefined`); it
  now compiles to `[["load","x"],["lit",nil],["compare","STRICT_EQ"]]` and
  answers `true`. Anyone who genuinely had a variable called `null` bound in
  context stops reading it. There is no automated detection for this; the
  changelog entry must say so.

## Phase 1: The literal - lexer, parser, round-trip, and the language reference

### Overview

`null` becomes a reserved literal keyword that parses to `{:literal, nil, pos}`
and renders back as `null`, together with every edit
`docs/reference/language.md` needs in order to be true and green again.

**Reserved word, not a contextual keyword.** The codebase's two precedents are
`true`/`false`/`undefined` (reserved, in `classify_identifier/1`) and the seven
cast type names (contextual, ADR-0011). The cast names can be contextual
because `::` makes their position unambiguous. `null` appears in ordinary
primary-expression position, exactly where an identifier may appear, so there
is no delimiter to key off: a contextual reading would make `x === null` mean
different things depending on whether a variable named `null` happened to be
bound. `null` is a literal, and every literal keyword in this language is
reserved.

**What it breaks:**

| Source | Before | After |
|---|---|---|
| `Predicator.compile("x === null")` | `[["load","x"],["load","null"],["compare","STRICT_EQ"]]` | `[["load","x"],["lit",nil],["compare","STRICT_EQ"]]` |
| `Predicator.evaluate("x === null", %{"x" => nil})` | `{:ok, false}` | `{:ok, true}` |
| `Predicator.parse("null = 3")` | assignment-ish error path | `"'=' is not an equality operator ..."` shape, as `true`/`undefined` produce |
| `Predicator.parse_program("null = 3")` | assignment to a variable named `null` | `"Left side of '=' must be an assignable location ..."` |
| `Predicator.parse("user.null")` | property access | `"Expected property name after '.' but found 'null'"` |
| `Predicator.parse("{null: 1}")` | object with key `null` | `"Expected identifier or string for object key but found 'null'"` |
| `Predicator.parse(~s({"null": 1}))` | parses | still parses |
| `NULL`, `Null` | identifiers | still identifiers |

The exact message strings above are the `undefined` shapes with the word
substituted; the implementer asserts whatever the code actually produces and
copies it verbatim into the tests, as `reserved_words_test.exs` already does.

### Changes Required:

#### 1. Lexer
**File**: `lib/predicator/lexer.ex`
**Changes**: one clause in the reserved-word table, plus the two typespecs it
touches. Nothing else - `handle_regular_identifier/6` (`:522-555`) already
consults `classify_identifier/1` before turning an identifier into a
`:function_name`, so `null(1)` is refused for free.

```elixir
# beside the boolean and undefined clauses at the head of the table (:499-501)
defp classify_identifier("null"), do: {:null, nil}
```

- Widen `classify_identifier/1`'s `@spec` return to admit `nil`
  (`{atom(), binary() | boolean() | :undefined | nil}`) - dialyzer will
  otherwise reject the new clause.
- Add `{:null, pos_integer(), pos_integer(), pos_integer(), nil}` to the
  `token()` union (`:40-92`), beside the `:boolean` and `:undefined` arms, with
  the same doc-comment style as its neighbours.

The token type is `:null` rather than `:null_kw`: a bare type name marks a
*literal* in this lexer (`:boolean`, `:undefined`, `:date`, `:datetime`), `_kw`
marks statement keywords, `_op` marks operators.

**Watch for the `nil` value slot.** `:undefined`'s token carries the atom
`:undefined` in its value position; `null`'s carries `nil`. Any code that
pattern-matches a token value truthily (rather than positionally) would treat
that as absent. The lexer's own tuples are positional, so this is expected to
be a non-issue - but it is the one place this literal differs from every
previous one, and a dialyzer or test failure here is the signal.

#### 2. Parser
**File**: `lib/predicator/parser.ex`
**Changes**: one primary-expression clause, one `format_token/2` clause, one
typespec.

```elixir
# immediately after the undefined clause at :1370-1372
# Parse the null literal
defp parse_primary_token(state, {:null, _line, _col, _len, _value} = token) do
  {:ok, {:literal, nil, leaf_loc(state, token)}, advance(state)}
end
```

```elixir
# with the other keyword clauses, beside :undefined at :1566
defp format_token(:null, _value), do: "'null'"
```

`format_token/2` is **required, not optional**: it has no catch-all, and both
`user.null` (`:1284`) and `{null: 1}` (`:1773`) route their message through it.
Without the clause those inputs raise `FunctionClauseError` instead of
returning a `ParseError` - the ADR-0004 breach this change must not introduce.

Add `| nil` to the parser-local `value()` type (`:122-130`) and name it in that
type's `@typedoc`.

No change to the statement-keyword rejection clause (`:1442-1447`): a literal
keyword is legal in expression position. No change to the property-access
(`:1263-1290`) or object-key (`:1768-1781`) whitelists: they accept token types
by name and `:null` is simply not among them, which is how the breakage falls
out.

#### 3. StringVisitor
**File**: `lib/predicator/visitors/string_visitor.ex`
**Changes**: one clause, beside the undefined clause at `:130`.

```elixir
defp do_visit({:literal, nil, _position}, _opts), do: "null"
```

Placement is safe anywhere among the `:literal` clauses as the file stands
today - `is_integer/1`, `is_boolean/1`, `is_binary/1`, and `is_list/1` are all
`false` for `nil`, and the `%Date{}`/`%DateTime{}` clauses are struct patterns
- but confirm that by reading the surrounding clauses (`:122-166`) rather than
assuming it, since `nil` is the one literal value a carelessly written guard
could swallow. The list recursion at `:152-156` covers `[null]` for free.

#### 4. `InstructionsVisitor` and the evaluator
**Files**: `lib/predicator/visitors/instructions_visitor.ex`,
`lib/predicator/evaluator.ex`
**Changes**: **none.** Stated so the implementer does not go looking. The
instructions visitor matches the `:literal` tag generically (`:174-176`) and
`execute_instruction(_, ["lit", value])` matches the opcode name only
(`:489-491`). Note the all-literal list fold at `:279-286`, which collapses
`[null, null]` into one `["lit", [nil, nil]]` - that is existing behavior and
is correct; add a test rather than an edit.

#### 5. Tests
**Files**:
- `test/predicator/lexer_test.exs` - `null` tokenizes as
  `{:null, 1, 1, 4, nil}`; `NULL` and `Null` tokenize as `:identifier` (the
  case-sensitivity decision, pinned); `null(` does not produce a
  `:function_name`.
- `test/predicator/parser_test.exs` - `null` parses to `{:literal, nil, pos}`
  with the right position; `[null, 1]` and `{k: null}` parse.
- `test/predicator/reserved_words_test.exs` - a `describe` block per breakage
  row, following the file's four-entry-point shape (`parse/2`,
  `parse_program/2`, `evaluate/3`, `compile/1`) with one message constant per
  site, plus the `{"null": 1}` still-parses test. Model on the `undefined` half
  at `:159-236`.
- `test/predicator/visitors/string_visitor_test.exs` - renders `"null"`; a
  parse -> decompile -> parse fixpoint for `x === null` and for `[null]`.
- `test/predicator/integration/full_pipeline_test.exs` -
  `Predicator.compile("x === null")` is
  `{:ok, [["load","x"],["lit",nil],["compare","STRICT_EQ"]]}`;
  `Predicator.evaluate("x === null", %{"x" => nil})` is `{:ok, true}`;
  `null === null` is `{:ok, true}` and `null == null` is `{:ok, :undefined}`
  (px-o9v D2 observed through the new spelling, not redecided);
