# Adds `while` with a termination bound (ISA v6) Implementation Plan

## Overview

Mint ISA v6 by adding one opcode - `jump_backward`, the only back edge in the
instruction set - together with the loop budget that keeps a list containing it
bounded, then add `while expr { stmts }` to the grammar and lower it onto that
opcode. ADR-0013 settles the opcode name, its semantics, the lowering, and the
budget's shape; this plan is their mechanical execution plus the ISA paperwork
ADR-0003 attaches to the bead that mints the version. Because `px-3so.5` and
`px-3so.6` are scoped to `if`/`else` at v5, this bead also carries `while`'s
`StringVisitor` clause and its tier-9 corpus cases. Bead: `px-3so.4`.

## Current State Analysis

**ISA v5 landed on this branch's lineage** (commits `eaf9ad1`, `d979d1d`,
`d8f49a4`): `jump` and `pop_jump_if_falsy` exist at tier 8, `if`/`else` lowers
and runs, and `conformance/cases/control_flow.json` holds fifteen tier-8 cases.
`lib/predicator/instructions.ex:93-94` carries both rows at `%{isa: 5, tier: 8}`
and `@isa_version` is `5`.

**The lexer already tokenizes `while`.** `lexer.ex:512` classifies it as
`{:while_kw, "while"}`, and `@type token` (`lexer.ex:81-83`) declares
`while_kw` beside `if_kw`/`else_kw`. Nothing in the lexer changes.

**The parser rejects `while` from three sites, all sharing one message.**
`statement_keyword_message(:while_kw)` (`parser.ex:544-546`) returns
`"'while' is a reserved word - while statements are not supported yet."` and is
called from:

- `parse_statement/1`'s `{:while_kw, ...}` clause (`parser.ex:560-561`) - the
  exact slot a `parse_while_statement/2` call replaces, mirroring the `if_kw`
  clause immediately above it at `parser.ex:557-558`.
- `finish_program/4`'s `kw in [:else_kw, :while_kw]` clause
  (`parser.ex:456-457`) - a keyword *trailing* a program.
- `parse_primary_token/2`'s dedicated `while_kw` clause
  (`parser.ex:1401-1407`), whose comment says pointing at `parse_program/2`
  "would be a dead end - while statements aren't implemented there yet".

`if` in expression position instead gets `parse_primary_token/2`'s
`kw in [:if_kw, :else_kw]` clause (`parser.ex:1394-1399`): `"'if' is a
statement keyword, not an expression - control flow is only valid in a program
(Predicator.parse_program/2)."` Once `while` parses, it joins that guard and
its own clause and message helper go away.

**The block machinery is already generic.** `parse_block/1`
(`parser.ex:606-622`), `parse_block_body/3` (624-646), and `finish_block/4`
(648-662) contain no `if`-specific logic and are callable unchanged from a
`while` parser. `brace_terminated?/1` (`parser.ex:534-538`) has a single
`{:if, ...}` clause and needs a `{:while, ...}` sibling so a `}` still ends a
statement without a `;`.

**`Parser.visitable/0` is a binding contract with a hard counter.**
`parser.ex:220` is `program() | statement() | block()`, and
`test/predicator/visitor_clause_coverage_test.exs:47` asserts
`@constructor_count 22` against the typespec's expansion **and** against the
clause-tag sets of `StringVisitor.do_visit/2` and
`InstructionsVisitor.visit_annotated/2`, in both directions. Adding a
`while_statement()` member to `statement()` moves that to 23 and **forces a
`:while` clause in both visitors in the same commit**. This is the single
constraint that fixes this plan's phase boundary.

That test's sabotage note is written *as* this change: its comments at lines
57-59, 84-86, and 134-137, and the dated entry at
`docs/research/260808-px-9ab-sabotage-notes.md:237-257`, all use "a throwaway
`{:while, ast(), block(), position()}` member" as the mutation. Making `:while`
real retires that sabotage, so the note has to be re-taken with a different
throwaway tag and re-dated.

**`StringVisitor` still declines `{:if, ...}` and `{:block, ...}`**
(`string_visitor.ex:289-296`, via `unsupported_node/2` at 457-466). `px-3so.5`
is `in_progress` in a parallel worktree and owns those two clauses; this bead's
claim note records the `area:visitors` collision as a deliberate override. The
module renders flat, single-line output - a program is
`Enum.map_join(statements, "; ", ...)` (`string_visitor.ex:298-300`) - with no
indentation logic anywhere.

**`InstructionsVisitor` has real `:if` and `:block` clauses**
(`instructions_visitor.ex:342-374`) and a `visit_statement/2` `:if` clause that
suppresses the trailing `["pop"]` (`414-429`). A `while` needs the same pair.

**The evaluator's jump machinery is one function.** `jump_to/2` sets
`instruction_pointer = ip + offset - 1` so `advance_instruction_pointer/1`'s
unconditional `+1` lands on `ip + offset`. Errors get their position for free:
`step/1` (`evaluator.ex:374-390`) routes every error through
`attach_position/2` -> `attach_error_position/2` (`evaluator.ex:411-414`),
which stamps `positions[ip]` of the *failing* instruction.

**`:on_unbound`'s plumbing, and why `:loop_budget` copies only half of it.**
`on_unbound` lives on `%Context{}` (validated in `Context.new/2`,
`context.ex:128, 204-210`) and is copied onto `%Evaluator{}` at three
construction sites: `Predicator.evaluate_instructions/3` (`predicator.ex:235`),
`Predicator.execute_instructions/3` (`predicator.ex:547`), and
`Evaluator.evaluate/3` (`evaluator.ex:290`). There is **no options whitelist
anywhere in `lib/`** - every option is read ad hoc with `Keyword.get/3`. Both
`Predicator` sites already have `opts` in scope and already read
`:positions`/`:segment_positions` straight off it, so a run-scoped option needs
no `Context` change at all (see Decision 2).

**Six mechanisms bind an opcode addition, all of which fire here.** These are
the same six `px-3so.3` enumerated, re-verified against the current tree:

1. `test/predicator/isa_sync_test.exs` - every `docs/isa.md` §4 opcode row must
   round-trip through `required_isa/1` and `tier/1`, and the `@opcode_count`
   literal (now `30`) is asserted against the table's row count twice. One new
   row moves it to `31`.
2. `isa_sync_test.exs` - `isa_version/0` must equal the maximum version in the
   doc's table, and §1's `Current version: **ISA v5**.` line must agree.
3. `isa_sync_test.exs` - the doc's tier-names table must match the opcode map's
   tier assignment exactly, so a tier-9 row is mandatory.
4. `isa_sync_test.exs` - **every live opcode must have exactly one
   `execute_instruction/2` clause head** in `lib/predicator/evaluator.ex`, and
   the clause-head count must equal the live opcode count. This is why the
   budget's two outcomes live in a private helper, not in two clause heads
   (Decision 4).
5. `test/predicator/conformance/opcode_coverage_test.exs` - every opcode in
   `opcode_set(isa_version())` must appear in at least one authored case under
   `conformance/cases/*.json`, except the documented `relative_date` exclusion.
6. `test/predicator/conformance/corpus_freshness_test.exs` - the checked-in
   corpus must be byte-identical to `mix corpus.generate`'s output;
   `build_manifest/1` stamps `isa_version` into `conformance/manifest.json`, so
   the bump alone makes the corpus stale, and
   `ratchet_registry_test.exs` requires
   `conformance/examples/registry.example.json`'s `corpus_hash` and
   `isa_version` to equal the regenerated manifest's.

**The corpus cannot pass evaluation options.** `Generator.evaluate_case/2`
(`lib/predicator/conformance/generator.ex:343`) calls
`Predicator.evaluate(instructions, context, [])` with a **hardcoded empty
option list**, and `conformance/schema/case.json` is
`"additionalProperties": false` over exactly `id`, `source`, `instructions`,
`context`, `expected`, `tier`, `features`, `notes`. A tier-9 case therefore
cannot request a smaller budget; the exhaustion case must exhaust the *default*
(Decision 5).

**An `EvaluationError` reason encodes into the corpus with no new machinery.**
`Generator.encode_error/1` (`generator.ex:375-387`) maps
`%EvaluationError{reason: r}` to `%{"type" => "EvaluationError", "reason" => r}`
verbatim, so `"loop_budget_exceeded"` needs no generator or schema change.

**Two tier-name maps and no tier-9 entry.** `generator.ex:43-52` and
`coverage.ex:135-144` each stop at `8 => "control flow"` and fall back to
`"tier 9"` if unmapped. `conformance/README.md` and `RATCHET.md` carry no
tier-name listing, so nothing else needs the word "loops".

## Desired End State

`Predicator.execute/2,3` runs a program containing `while`, terminating either
because the condition goes falsy or because the loop budget is exhausted -
never by hanging. `Predicator.decompile/2` renders a `while` statement back to
source. `Predicator.Instructions.isa_version/0` returns `6`, `docs/isa.md`
documents `jump_backward` as a tier-9 ISA v6 opcode with the normative bound
and a v6 version-history row, `docs/reference/language.md` records the default
budget and the `:loop_budget` option, and `conformance/corpus/tier-9.json`
exercises the opcode including a case that exhausts the bound.

Verify with: `mix quality` green;
`Predicator.execute("i = 0; while i < 3 { i = i + 1 }", %{})` returning
`{:ok, %{"i" => 3}}`; `Predicator.execute("while true { }", %{})` returning an
`{:error, %EvaluationError{reason: "loop_budget_exceeded"}}` within a second;
`Predicator.execute("while true { }", %{}, loop_budget: 5)` returning the same
error; `Predicator.Instructions.isa_version() == 6`.

### Key Discoveries:

- **The visitor-coverage test fuses parsing and both visitors into one phase.**
  `visitor_clause_coverage_test.exs:47`'s `@constructor_count` and its two
  both-directions assertions go red on any commit that adds `{:while, ...}` to
  `Parser.visitable/0` without a `do_visit/2` clause in `string_visitor.ex`
  *and* a `visit_annotated/2` clause in `instructions_visitor.ex`. There is no
  green intermediate commit, so Phase 2 carries parser, compiler, and
  decompiler together. This is also the answer to `.claude/wurk/plan.md`'s rule
  that a grammar change `StringVisitor` cannot render back is incomplete rather
  than a follow-up phase - here the rule is enforced by a test.
- **`isa_sync_test.exs`'s clause-head count forbids two `jump_backward`
  `execute_instruction/2` heads.** The budget-available and budget-exhausted
  paths must be two clauses of a private `execute_jump_backward/2`, reached
  from a single `execute_instruction/2` clause head - the same shape
  `pop_jump_if_falsy` already uses.
- **The error position is free.** `attach_error_position/2`
  (`evaluator.ex:411-414`) stamps `positions[ip]` on any error a clause
  returns, and `ip` at that moment is the `jump_backward`'s own index. ADR-0013's
  "carrying that instruction's source position" needs no code beyond returning
  the error value.
- **`Generator.evaluate_case/2` hardcodes `[]` for options**
  (`generator.ex:343`), and `conformance/schema/case.json` is a closed object -
  so the corpus's budget-exhaustion case runs at the shipping default. That is
  the right outcome anyway: ADR-0013 says the tier-9 case pins the error type,
  **not** the count at which a default fires, and an unconditionally infinite
  loop exhausts any finite budget a sibling picks.
- **Constraint - ADR-0013**: `jump_backward` is a distinct opcode name rather
  than a negative offset on `jump`, precisely so opcode-name scanning stays a
  sound version check and *absence of `jump_backward` remains a termination
  proof*. Nothing in this plan may widen `jump`'s operand.
- **Constraint - ADR-0003**: the ISA paperwork lands in the bead that mints the
  version, and a corpus diff moves the exported specification, so it is
  explained in the commit message and the PR body.
- **Constraint - ADR-0004**: budget exhaustion is an `EvaluationError` **value**
  returned from the opcode's clause, never a raise. A malformed `:loop_budget`
  option is the other side of that line - host-API misuse, which raises, exactly
  as `Context.new/2` does for a bad `:on_unbound` and
  `reject_positions_option!/1` does for a contradictory `:positions`.
- **Constraint - ADR-0005**: `px-3so.5` is in flight and owns
  `string_visitor.ex`'s `{:if, ...}`/`{:block, ...}` clauses. Decision 3 keeps
  this branch's diff to that file strictly additive.

## Decisions Taken During Planning

Recorded here so no open question survives into implementation.

1. **`docs/isa.md` §7's v6 row says "Shipped in 4.1.0."** `mix.exs` is at
   `4.0.0` and `CHANGELOG.md`'s `## [Unreleased]` already holds ISA v4's `cast`
   and ISA v5's two jumps, both claiming 4.1.0. Nothing has been released, so
   v6 lands in that same unreleased minor and carries the same number. ADR-0013's
   "each is a minor release" is a statement about the *kind* of release an
   additive version needs and about judging the loop questions on their own
   merits - not a requirement that two unreleased versions be split across two
   published minors. No test binds this column; `/wurk:release` corrects all
   three rows together if the release is numbered differently.
2. **`:loop_budget` is run-scoped on the `Evaluator` only - it does not go on
   `%Context{}`.** `on_unbound` is a persistent *policy* that survives
   `Context.bind/3` and `assign/3`, which is why it lives on the context. A
   budget is a consumable resource decremented during a single run; putting a
   fuel counter on `Context` would make it mutate under `bind/3` and would give
   the same context two different meanings across two runs. It is read through the shared
   `Evaluator.loop_budget_from_opts/1` of Decision 6 - which is where the
   `Keyword.get/3` and its validation both live - called at the same three
   `%Evaluator{}` construction sites `on_unbound` is copied at (`predicator.ex:235`,
   `predicator.ex:547`, `evaluator.ex:290`), beside the `:positions` reads
   already there. This also keeps the branch out of `area:context`, which the
   bead is not labeled with.
3. **`string_visitor.ex`'s `{:block, ...}` declining clause is left alone;
   `while` renders its block through a new private `render_block/2` helper.**
   `px-3so.5` is `in_progress` in a parallel worktree and owns both declining
   clauses; the bead note records the `area:visitors` collision as a deliberate
   override, and the cheapest way to honor that is a strictly additive diff -
   one new `do_visit({:while, ...})` clause plus one new helper, touching no
   line `px-3so.5` will touch. `px-3so.5` can adopt the same helper for `if`
   when it lands. Whichever branch rebases second resolves the
   `@constructor_count` / moduledoc edits in
   `visitor_clause_coverage_test.exs`, which is the one genuinely shared hunk.
4. **One `execute_instruction/2` clause head, two private helper clauses.**
   `isa_sync_test.exs` counts clause heads and requires exactly one per live
   opcode, so `["jump_backward", offset]` gets a single guarded head delegating
   to `execute_jump_backward/2`, whose two clauses are "budget remains" and
   "budget exhausted". Identical to `pop_jump_if_falsy`'s shape.
5. **The tier-9 exhaustion case is an unconditionally infinite loop run at the
   shipping default budget.** Per-case options do not exist
   (`generator.ex:343`, `schema/case.json`) and adding them is out of scope. An
   infinite loop exhausts *any* finite budget, which is exactly what ADR-0013
   asks the corpus to pin - the error type, not the count. The cost is bounded
   and measured in Performance Considerations.
6. **A malformed `:loop_budget` raises `ArgumentError`.** Anything that is not
   a non-negative integer is host-API misuse written in the host's own source,
   not a predicate-derived failure, so ADR-0004's errors-as-values does not
   apply - the same line `Context.new/2` draws for `:on_unbound`. Validation
   lives in one public `Evaluator.loop_budget_from_opts/1` so all three
   construction sites share it and cannot disagree.
7. **`jump_backward` gets no `Features` tag.** `features.ex:36-56`'s
   `@opcode_tags` has no entry for `jump` or `pop_jump_if_falsy` either - tier 8
   landed untagged, and `Map.get(@opcode_tags, opcode, [])` handles the default.
   Tier 9 is the cut for loops; inventing a `loops` feature tag here would be a
   vocabulary change with no consumer.
8. **Budget `0` is legal and means "no back edge may be taken".** It is the
   natural bottom of a non-negative counter, it gives a host a one-option way to
   forbid loops at run time (complementing ADR-0013's "scan for one opcode
   name" static answer), and it needs no special case: the exhausted clause
   fires on the first `jump_backward`.

## What We're NOT Doing

- **Per-case evaluation options in the conformance corpus.** Supporting a
  `loop_budget` override in an authored case would mean changes to
  `schema/case.json`, `schema/corpus.json`, `generator.ex`'s
  `evaluate_case/2`/`assemble_case/6`, and every sibling runner. Decision 5
  makes it unnecessary. If a later bead wants it, that is its own change with
  its own corpus-diff explanation.
- **`:loop_budget` on `%Context{}`.** Decision 2. No field, no
  `validate_loop_budget!/1` in `context.ex`, no `bind/3`/`assign/3` carry-over
  semantics to specify.
- **Tuning the default away from 10,000.** ADR-0013 records it as a guess made
  without production data and says moving it later is implementation-local and
  needs no ISA motion. This bead ships the guess.
- **`StringVisitor` rendering of `if`/`else`, and the real `{:block, ...}`
  clause.** `px-3so.5`, in flight. Decision 3.
- **Broadening tier-8.** `px-3so.6` landed (`d8f49a4`); tier 8 is done.
- **Nested-function or early-exit control flow.** No `break`, no `continue`, no
  `return`. ADR-0013's grammar is `while expr { stmts }` and nothing else; a
  loop leaves only by its condition or by the budget.
- **Block scoping.** ADR-0013 settles that braces group statements and the flat
  Context is the only scope. A `store` inside a loop body writes the same
  context every iteration.
- **Changing `jump`, `pop_jump_if_falsy`, or the `_or_pop` jumps.** No existing
  instruction list changes meaning, and `jump`'s operand stays a positive
  forward offset.
- **A release.** No `@version` bump, no changelog promotion, no tag.
- **Fixing `docs/reference/language.md`'s stale "execute/2 does not accept an
  `if` program until the ISA v5 opcodes land" sentence** (around line 324) or
  its neighbours, beyond what the `while` sections require. It is `px-3so.3`
  drift, noticed here and worth a follow-up bead, but rewriting v5's prose from
  a v6 branch widens this diff for no acceptance criterion. Phase 2 adds
  `while`'s own text and leaves the `if` paragraphs as it found them.

## Implementation Approach

Two phases, split at the same seam `px-3so.3` used: the instruction set first,
the language on top of it.

Phase 1 mints ISA v6 end to end - opcode table row, evaluator clause, the loop
budget and its option, `docs/isa.md` prose, tier-9 corpus cases, regenerated
corpus. It must be one phase because mechanisms 1-6 above go red on any proper
subset. After it, ISA v6 exists and is runnable, but the compiler never emits
`jump_backward` and `docs/isa.md`'s "Emitted by compiler" column reads `no`,
which is the truth at that commit.

Phase 2 adds the `while` grammar and flips that column to `yes`. It carries the
parser, both visitors, and the documentation in one commit because
`visitor_clause_coverage_test.exs` admits no green intermediate (Key
Discoveries).

## Phase 1: Mint ISA v6 - `jump_backward` and the loop budget

### Overview

Add the opcode, the fuel counter, the `:loop_budget` option, the ISA
specification, and the tier-9 conformance corpus, in one commit. No parser and
no visitor change.

### Changes Required:

#### 1. The opcode table

**File**: `lib/predicator/instructions.ex`
**Changes**: bump `@isa_version` to `6`; add one `@opcodes` row at tier 9,
after the `pop_jump_if_falsy` row. The `required_isa/1` doctest embeds
`"this build supports ISA v5"` by interpolating `@isa_version` - update the
expected string to `v6`.

```elixir
  @isa_version 6

  # ... in @opcodes, after the "pop_jump_if_falsy" row:
    "pop_jump_if_falsy" => %{isa: 5, tier: 8},
    "jump_backward" => %{isa: 6, tier: 9}
```

#### 2. The fuel counter and the `:loop_budget` option

**File**: `lib/predicator/evaluator.ex`
**Changes**: a `loop_budget` field on the struct and `@type t`, a module
attribute for the default, and one public accessor plus one public
option-reader.

```elixir
  @default_loop_budget 10_000

  # in @type t:
        loop_budget: non_neg_integer(),

  # in defstruct, beside on_unbound:
    loop_budget: @default_loop_budget,
```

```elixir
  @doc """
  The default number of back edges a single execution may take.

  ADR-0013: a program with no `jump_backward` never touches this counter, so
  the v5 termination-by-construction property is unaffected. The value is
  implementation-local, exactly as `:on_unbound` is - ISA v6 makes only the
  *existence* of a bound and the `"loop_budget_exceeded"` reason normative.
  """
  @spec default_loop_budget() :: non_neg_integer()
  def default_loop_budget, do: @default_loop_budget

  @doc """
  Reads and validates the `:loop_budget` evaluation option.

  Raises `ArgumentError` for anything that is not a non-negative integer -
  host-API misuse, not a predicate-derived failure (ADR-0004), the same line
  `Predicator.Context.new/2` draws for a malformed `:on_unbound`.
  """
  @spec loop_budget_from_opts(keyword()) :: non_neg_integer()
  def loop_budget_from_opts(opts) do
    case Keyword.get(opts, :loop_budget, @default_loop_budget) do
      budget when is_integer(budget) and budget >= 0 -> budget
      other -> raise ArgumentError, "loop_budget must be a non-negative integer, got: #{inspect(other)}"
    end
  end
```

**File**: `lib/predicator.ex`
**Changes**: add `loop_budget: Evaluator.loop_budget_from_opts(opts)` to the
`%Evaluator{}` literal in `evaluate_instructions/3` (line 227-236) and in
`execute_instructions/3` (line 539-548), beside the existing `:positions`
reads. Add `:loop_budget` to `execute/3`'s enumerated options list
(`predicator.ex:350-351`) and document it in `evaluate/3`'s options prose,
naming the default and the `"loop_budget_exceeded"` error.

**File**: `lib/predicator/evaluator.ex`, `evaluate/3`
**Changes**: add `loop_budget: loop_budget_from_opts(opts)` to the struct built

#### 3. The evaluator clause

**File**: `lib/predicator/evaluator.ex`
**Changes**: **exactly one** `execute_instruction/2` clause head (Decision 4),
placed beside the `jump`/`pop_jump_if_falsy` heads so the jump family stays
together, plus a two-clause private helper and a `jump_backward_to/2` beside
`jump_to/2`.

```elixir
  # The one back edge in the ISA (ISA v6, ADR-0013). Guarded on a positive
  # integer offset AND on a target at or after index 0, so a malformed or
  # out-of-range operand falls through to the catch-all and reports
  # unknown_instruction - docs/isa.md §2's standing rule.
  defp execute_instruction(
         %__MODULE__{instruction_pointer: ip} = evaluator,
         ["jump_backward", offset]
       )
       when is_integer(offset) and offset > 0 and ip - offset >= 0 do
    execute_jump_backward(evaluator, offset)
  end
```

```elixir
  # The only place the loop budget is charged. A program with no back edge
  # never reaches this function, so ISA v5's termination-by-construction
  # property survives verbatim (ADR-0013).
  @spec execute_jump_backward(t(), pos_integer()) :: {:ok, t()} | {:error, struct()}
  defp execute_jump_backward(%__MODULE__{loop_budget: budget} = evaluator, offset)
       when budget > 0 do
    {:ok, jump_backward_to(%{evaluator | loop_budget: budget - 1}, offset)}
  end

  defp execute_jump_backward(%__MODULE__{} = _evaluator, _offset) do
    {:error,
     EvaluationError.new(
       "loop budget exhausted - execution stopped at a backward jump",
       "loop_budget_exceeded",
       :jump_backward
     )}
  end

  # Mirror of jump_to/2: advance_instruction_pointer/1's unconditional +1
  # means the target lands on ip - offset.
  @spec jump_backward_to(t(), pos_integer()) :: t()
  defp jump_backward_to(%__MODULE__{instruction_pointer: ip} = evaluator, offset) do
    %{evaluator | instruction_pointer: ip - offset - 1}
  end
```

No position plumbing is needed - `attach_error_position/2` stamps the failing
instruction's position automatically (Key Discoveries).

#### 4. The ISA specification

**File**: `docs/isa.md`
**Changes**: eight edits, each bound by a test or by section-internal
consistency.

- §1, the current-version line: `Current version: **ISA v6**.` (bound by
  `isa_sync_test.exs`).
- §2, the "Jumps are relative and forward-only" bullet: rewrite. Jumps are
  relative; the operand is always a positive integer; `jump`,
  `jump_if_falsy_or_pop`, and `jump_if_true_or_pop` target `index + offset`,
  and `jump_backward` targets `index - offset`. There is no absolute jump.
- §2, a **new normative bullet on the bound**: execution of a list containing
  `jump_backward` must be bounded; an implementation charges a per-execution

#### 2. The lowering

**File**: `lib/predicator/visitors/instructions_visitor.ex`
**Changes**: one `visit_annotated/2` clause beside the `:if` clauses
(342-368), and one `visit_statement/2` clause beside the `:if` one (419-425).

```elixir
  # ADR-0013:  while c { A }
  #   ->  c; pop_jump_if_falsy +(lenA + 2); A; jump_backward -(lenC + lenA + 1)
  # The +2 clears A and the back edge that ends it; the back edge's offset is
  # measured from its own index to the condition's first instruction, which is
  # why it counts lenC as well.
  defp visit_annotated({:while, condition, body, position}, opts) do
    condition_instructions = visit_annotated(condition, opts)
    body_instructions = visit_annotated(body, opts)

    back_offset = length(condition_instructions) + length(body_instructions) + 1

    condition_instructions ++
      [{["pop_jump_if_falsy", length(body_instructions) + 2], position}] ++
      body_instructions ++
      [{["jump_backward", back_offset], position}]
  end
```

```elixir
  # Stack-neutral by construction, exactly as an `if` is: the condition is
  # consumed by pop_jump_if_falsy on every iteration including the last, and
  # the body's statements each end in a store or a pop. Without this clause the
  # catch-all would append a ["pop"] against an empty stack.
  defp visit_statement({:while, _condition, _body, _position} = node, opts) do
    visit_annotated(node, opts)
  end
```

Both emitted instructions carry the `while` node's own annotation, following
`px-3so.3`'s Decision 3 for `if`. Offsets are computed over the annotated list,
one entry per instruction.

## ISA Impact

1. **Version.** This mints **ISA v6**, additive - one new opcode, none retired,
   no opcode's semantics changed under its own name. Additive means a minor
   library release (`docs/isa.md` §1); it ships in the same unreleased minor as
   v4's `cast` and v5's two jumps (Decision 1). `@isa_version` moves from `5` to
   `6` in `lib/predicator/instructions.ex`.
2. **Stamp.** `docs/isa.md` owes: one opcode-table row; a ``| 9 | loops |``
   tier row; a `jump_backward` subsection in §5; the
   `Current version: **ISA v6**.` line in §1; the rewritten
   relative-and-forward-only bullet plus a new normative bound bullet in §2;
   the "Every opcode is ISA v1 except..." sentence in §4; the narrowed §6
   exclusion; and a v6 row in §7's version history. The conformance corpus owes
   a tier-9 file, generated by `mix corpus.generate` from authored cases and
   never hand-edited. `Predicator.Instructions`'s `@opcodes` gains one entry at
   `%{isa: 6, tier: 9}`.
3. **Migration.** **None required.** Every instruction list compiled before this
   change still runs and produces the same answer: no opcode was retired, no
   operand form widened, and no existing opcode's clause was touched - in
   particular `jump` keeps its positive-forward-offset operand rather than
   growing a negative form, which is the whole point of the separate name. The
   asymmetry is the expected one: a v6 artifact does not run on a v5 or earlier
   build, and a sibling behind v6 is an expected, documented state (ADR-0003),
   not a blocker here.

Two properties worth stating for the siblings. First, **the bound is
normative and its size is not**: a sibling claiming ISA v6 must bound execution
of any list containing `jump_backward` and must report exhaustion as an
`EvaluationError` with reason `"loop_budget_exceeded"`, but it picks its own
default and its own option surface, exactly as it does for `on_unbound`. A v6
implementation that can hang on a stored artifact does not conform. Second,
**absence of `jump_backward` remains a termination proof**: a list without it
still halts in at most `length(program)` steps, so a consumer that must never
block - statifier's guards are the named case - can keep loops out entirely by
scanning for one opcode name, with no budget and no runtime cost.

## Performance Considerations

The fuel counter is a single integer field decremented in one clause that only
a back edge reaches. A program containing no `jump_backward` never executes
that clause, so v5's per-instruction cost is unchanged - which is precisely why
ADR-0013 put the counter on the back edge rather than in the step loop.

The one measurable new cost is Phase 1's
`loops/budget-exhausted-on-infinite-loop` corpus case, which by construction
runs the full default budget: 10,000 back edges over a three-instruction list,
about 30,000 evaluator steps. It executes at least twice per suite run - once
when the corpus test replays it, once when `corpus_freshness_test.exs`
regenerates the corpus in memory - plus once per `mix corpus.generate`.
Confirm during Phase 1 that this is milliseconds, not seconds, and that the
suite's wall-clock time has not moved noticeably; it is a Phase 1 manual
verification item. If it ever does become material, the fix is per-case
evaluation options in the corpus, which this plan explicitly defers.

## Testing Strategy

### Unit Tests:

- **`test/predicator/instructions_test.exs`** - `isa_version/0` is `6`;
  `jump_backward` reports `{:ok, 6}` from `required_isa/1` and `{:ok, 9}` from
  `tier/1`; `opcode_set(5)` excludes it and `opcode_set(6)` includes it.
- **Evaluator (Phase 1)** - one test per clause, over hand-built instruction
  lists, pattern-matching style: the back edge lands on `ip - offset`; a
  counted loop terminates; the budget decrements exactly once per back edge;
  exhaustion is `%EvaluationError{reason: "loop_budget_exceeded", operation:
  :jump_backward}` with the failing instruction's position; malformed operands
  (`0`, negative, non-integer, target before index 0) are each
  `unknown_instruction`; a program with no back edge leaves the budget
  untouched.
- **Options (Phase 1)** - `:loop_budget` honored and validated at
  `Predicator.evaluate/3`, `Predicator.execute/3`, and
  `Predicator.Evaluator.evaluate/3`; the default comes from
  `Evaluator.default_loop_budget/0`; a malformed value raises `ArgumentError`;
  a budget of `0` forbids the first back edge.
- **Parser (Phase 2)** - the shapes listed in Phase 2 §8, including the two
  block error messages and the expression-position rejection.
- **InstructionsVisitor (Phase 2)** - whole-list assertions per lowering shape,
  the empty-body and nested-loop edge cases where the two offsets are easiest
  to get wrong, and the no-trailing-pop assertion.
- **StringVisitor (Phase 2)** - rendering plus the
  `parse_program |> decompile |> parse_program` fixpoint, which is the project's
  standing criterion for a new AST node.
- **Positions (Phase 2)** - `visit_with_positions/2` and the `spans: true`
  variant carry the `while` node's annotation on both emitted instructions.
- **Anti-drift** - `isa_sync_test.exs`, `visitor_clause_coverage_test.exs`, and
  the conformance tests are the binding tests here. This plan adds no new
  binding test, but it **invalidates an existing sabotage note** - Phase 2 §4
  re-takes it and records the new pass, per
  `docs/research/260808-px-9ab-sabotage-notes.md`.

### Integration Tests:

`test/predicator/integration/while_execution_test.exs` - end-to-end
`Predicator.execute/2,3` over source strings: a counted loop; a zero-iteration
loop; a loop writing a variable observed after it; a nested loop; a loop inside
an `if` branch; a non-boolean condition's `TypeMismatchError`; an unbound
condition taking the falsy path; an unconditionally infinite loop hitting the
default budget; the same under a small `:loop_budget`; and two sequential loops
