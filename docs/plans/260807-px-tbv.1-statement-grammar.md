# Statement Grammar and Parser Implementation Plan

## Overview

Adds a statement-sequence entry point to the parser and removes `=` from the
expression grammar. Beads issue: **px-tbv.1** (parent epic px-tbv; depends on
px-8um.5 and px-z5m; blocks px-tbv.2 and px-tbv.5).

```text
program    := statement (";" statement)* [";"]
statement  := assignment | expression
assignment := location "=" expression
location   := IDENTIFIER ( "." IDENTIFIER | "[" expression "]" )*
```

`=` leaves the expression grammar entirely. `==` and `===` become the only
equality operators, and a bare `=` in expression position is a pointed parse
error naming `==`, never a silent reinterpretation (ADR-0002). The instruction
set is untouched: `=` and `==` both still compile to `["compare", "EQ"]`.

Scope is parser and grammar only. No compiler, no evaluator, no opcodes, no ISA
version bump - px-tbv.2 owns `store`, `pop`, and `Predicator.execute/2`.

## Current State Analysis

Established by `docs/research/260807-px-tbv.1-statement-grammar.md`, verified
against the tree at commit `babed48`.

- **The lexer already separates `=` / `==` / `===`** by maximal munch
  (`lib/predicator/lexer.ex:293-306`), emitting `{:eq, line, col, 1, "="}`.
  **There is no `;` token**: `;` falls to the catch-all at `lexer.ex:421-422`
  and errors as `"Unexpected character ';'"`. Newlines are pure whitespace
  (`lexer.ex:176-186`); the stream carries no statement marker.
- **`Predicator.Parser.parse/2` is the only public parser entry point**
  (`parser.ex:263-286`): one `parse_expression/1` call wrapped in a
  "did we consume everything" gate at `parser.ex:272-281`. No `:program`
  production, no assignment node, no top-level loop.
- **`:eq` is indistinguishable from any other comparison operator today.** It
  sits in the guard list at `parser.ex:467-478`, falls through the
  `_other_op_type` catch-all at `parser.ex:484-490`, and lands in
  `{:comparison, :eq, left, right, pos}`. `InstructionsVisitor` maps both `:eq`
  and `:equal_equal` to `"EQ"` (`instructions_visitor.ex:280-289`).
- **`warn_deprecated_equals/1` (`parser.ex:288-315`)** is a pre-parse
  `Enum.find/2` over the raw token list, logging once, gated by
  `config :predicator, deprecation_warnings`. Its own leading comment
  (`parser.ex:288-291`) names this bead and says the check "must refine this
  check rather than inherit it".
- **The AST union is 17 shapes at `parser.ex:132-149`**, each ending in one
  `position() | span() | nil` slot (`parser.ex:160`). `types.ex` holds no AST
  type.
- **The assignable-location machinery already exists.**
  `ContextLocation.resolve/2` (`context_location.ex:125-131`) walks
  identifier / property_access / bracket_access into a flat path and rejects
  the other shapes; `put/3` (`context_location.ex:206-215`) takes the flat
  path. `ContextLocation` already calls `Parser.parse/2`, so the dependency
  runs ContextLocation -> Parser and must not be reversed.
- **Three modules pattern-match on AST tags**: `InstructionsVisitor` (no
  catch-all - `FunctionClauseError`), `StringVisitor` (no catch-all - same),
  and `ContextLocation` (has a catch-all at `context_location.ex:307-309`, so
  an unknown node silently reads as "not assignable").
- **Position helpers already generalize.** `node_start/1` and `node_end/1`
  (`parser.ex:953-957`) read `elem(node, tuple_size(node) - 1)`, so they work
  on any new arity; `loc/3`, `binary_loc/4`, and `leaf_loc/2` need no change.
- **`=`-as-equality is spread across the suite.** Roughly ten test files parse
  source strings using `=` for equality (`predicator_test.exs`,
  `parser_test.exs`, `compiler_test.exs`, both visitor test files,
  `strict_equality_test.exs`, `date_arithmetic_string_visitor_test.exs`,
  `integration/context_integration_test.exs`,
  `instructions_visitor_positions_test.exs`, `lexer_test.exs`), plus
  `test/predicator/equals_deprecation_test.exs` in full.
- **Three lib doctests use `=` as equality**: `lexer.ex:135`, `parser.ex:251`,
  `parser.ex:255`.
- **`test/docs_examples_test.exs` doctests five files** (`README.md`,
  `docs/reference/language.md`, and three guides). Verified by grep: none of
  their `iex>` blocks passes a `=`-as-equality string to Predicator, so none
  breaks mechanically. Their *prose* is stale.
- **The deprecation shipped in a released version.** `git tag` shows `v3.7.0`
  and `v3.8.0`; `CHANGELOG.md:539` sits under `## [3.7.0] - 2026-08-05`, and
  `mix.exs` is at `@version "3.8.0"`. The `=` deprecation is released history.

### Constraints from landed spec

- `docs/isa.md` §2 "Two execution modes" (isa.md:115-150, landed by px-z5m):
  **the mode is carried by the entry point, not by the artifact**;
  `empty_stack` is expression-mode-only; a well-formed statement program ends
  each statement with a `store` or a `pop`.
- `docs/isa.md` §6 (isa.md:431-459) reserves `store` and `pop`, and records
  that no statement entry point exists in any evaluator. This bead does not
  change that - it adds a *parser* entry point only.
- px-h66: `Predicator.execute/2` returns `{:ok, %Context{}} | {:error, e,
  %Context{}}` - stop-on-error, explicitly not rollback. That is px-tbv.2's
  contract; it places no requirement on this bead's AST beyond the source
  positions the parser already threads.
- ADR-0001:83-84: `["store", n]` pops **n path segments** plus a value. n must
  be derivable from the assignment node at compile time.
- ADR-0002: one grammar, not two selected by position or config. `=` is
  unconditionally assignment wherever it is legal, and a parse error
  everywhere else.

## Desired End State

1. `Predicator.Parser.parse_program/2` parses a token list into
   `{:ok, {:program, [statement], position}}`, and `Predicator.parse_program/2`
   is the string-in façade. Both accept `spans: true`.
2. `Predicator.Parser.parse/2` is unchanged in signature and still returns a
   bare expression `ast()`. It rejects `=` with a fix-it message.
3. `{:assignment, lhs_ast, rhs_ast, position}` and
   `{:program, [statement], position}` are new tagged nodes, declared as their
   own types (`statement/0`, `program/0`) and deliberately **not** members of
   `ast/0`.
4. `StringVisitor` round-trips both new nodes, and renders `:eq` as `"=="`.
5. `warn_deprecated_equals/1`, `deprecation_warnings_enabled?/1`, the
   `require Logger`, the moduledoc admonition, and the
   `config :predicator, deprecation_warnings` switch are gone.
6. `docs/architecture.md`, `docs/reference/language.md`, `README.md`,
   `docs/isa.md` §6's one stale sentence, and `CHANGELOG.md` describe the
   shipped rule.

### How to verify

- `mix quality` green.
- `Predicator.parse_program("a = 1; b = a + 1")` returns a two-statement
  program whose statements are both `{:assignment, ...}`.
- `Predicator.parse("status = 'active'")` returns
  `{:error, "'=' is not an equality operator - use '==' for equality. " <>
  "Assignment is only valid at the start of a statement.", 1, 8}`.
- `Predicator.evaluate("status == 'active'", %{"status" => "active"})` still

- `Predicator.decompile/2` round-trips a parsed program back to re-parseable
  source.

## Resolved Questions

The research doc left eight questions. All eight are decided here.

**1. Separate program entry point, or an option on `parse/2`?**
**A separate entry point** - `Parser.parse_program/2` and
`Predicator.parse_program/2`. Rationale: it is the parser-level echo of
`docs/isa.md` §2's rule that the mode belongs to the entry point, and it keeps
`parse/2`'s return type narrow, so no existing caller's pattern match widens
and dialyzer keeps its specificity. An option would make one function return
two disjoint shapes.

**2. How is a statement sequence represented?**
**A new tagged node `{:program, [statement()], position()}`** - arity 3, same
shape family as `{:list, [ast()], pos}`. Rationale: `Visitor`'s documented
contract (`visitor.ex:46-50`) is that every node carries a trailing
position/span/nil slot; a bare list would be the only AST value in the system
that is not a tagged tuple.

**3. Does a single-statement program parse to the same AST as a bare
expression?**
**No** - `parse_program/2` always returns `{:program, [...], pos}`, even for
one statement. Rationale: a uniform shape gives px-tbv.2's compiler one clause
instead of two, and makes "which entry point produced this" recoverable at the
type level. The statements *inside* are ordinary expression ASTs, byte-identical
to what `parse/2` produces, so no expression node changes.

**4. What does the assignment lhs node hold?**
**The raw access chain** - the ordinary `{:identifier, ...}` /
`{:property_access, ...}` / `{:bracket_access, ...}` subtree `parse_postfix/1`
already builds, stored unmodified as `{:assignment, lhs, rhs, pos}`. Rationale:
ADR-0001's `n` is the chain depth, derivable structurally at compile time
(`user.items[0].name` -> identifier + property + bracket + property = 4
segments = `["user", "items", 0, "name"]`); and a pre-flattened segment list
*cannot* represent a computed bracket key, which is exactly why
`ContextLocation.resolve/2` needs a context. Keeping the chain also satisfies
px-tbv.2's AC that "lhs computed segments compile as ordinary expressions
pushing segment values ahead of the store" - they already are expressions.

**5. Where does the assignability check happen?**
**Parse time, syntactic half only.** A new private `assignable_location?/1` in
the parser recurses through property/bracket accessors down to an identifier
root. The runtime half - `:undefined_variable`, `:invalid_key`, `:computed_key`,
`:not_a_container`, `:invalid_index` - stays in `ContextLocation`, unchanged.
Rationale: the AC says "must parse as an assignable location", which is parse
time; the runtime half genuinely needs a context and cannot move. The parser
gets its own predicate rather than calling `ContextLocation`, because
`ContextLocation` already depends on `Parser` and the dependency must not
become mutual.

**6. Fix-it message wording, and what happens to `warn_deprecated_equals/1`?**
The message is:

```text
'=' is not an equality operator - use '==' for equality. Assignment is only
valid at the start of a statement.
```

Two sentences because the error has two distinct causes worth naming: someone
who meant equality, and someone who meant assignment in a nested position
(`a = b = 1`, `(a = 1) and b`). The non-assignable-lhs case gets its own,
different message so the two paths stay separable:

```text
Left side of '=' must be an assignable location - an identifier, a property
access, or a bracket access.
```

`warn_deprecated_equals/1` is **deleted**, along with
`deprecation_warnings_enabled?/1`, `require Logger`, and the config key.
Rationale: `parser.ex:288-291` says "refine rather than inherit", and deletion
is what refinement terminates in here - under the new grammar every `:eq` token
is either an assignment (nothing to warn about) or a hard parse error (already
reported, with a better message and a real position). A warning has no
remaining domain. Note this **is** a released-behavior removal (the deprecation
shipped in 3.7.0), so it earns a `### Removed` changelog entry rather than a
silent deletion.

**7. Does `;` become a lexer token? Does newline?**
**`;` becomes `:semicolon`. Newline does not become a terminator.** Rationale:
the bead's grammar names only `;`. Newline-as-terminator is automatic semicolon
insertion in miniature, with its own ambiguity hazards, and nothing asks for it.
Whitespace stays whitespace.

**8. The doctests and the doctested docs files.**
- `parser.ex:251` and `parser.ex:255` **break the gate** and are therefore in
  scope: rewritten to `==` with `:equal_equal` in the expected AST.
- `lexer.ex:135` **does not break** - the lexer is unchanged and still emits
  `{:eq, ...}`. It is fixed anyway (in scope, discretionary), because leaving a
  headline example that teaches removed syntax is a documentation defect.
- The five `test/docs_examples_test.exs` files **do not break** - verified by
  grep, none passes a `=`-as-equality string to Predicator. Their prose is
  stale and is corrected in Phase 5.
- `docs/architecture.md:20-49`, `docs/reference/language.md:39-57`,
  `README.md:64-70`, and `docs/isa.md:451-455` are all in scope (Phase 5). A
  breaking change whose reference documentation still describes the old rule is
  not done.

## What We're NOT Doing

- **No compiler or evaluator changes.** `Compiler.to_instructions/2` and
  `InstructionsVisitor.visit/2` are not taught the new nodes - that needs
  `store` and `pop`, which are px-tbv.2's. Passing a program AST to them raises
  `FunctionClauseError`, exactly as any unhandled node does today. This is
  pinned by a guard test (Phase 3) rather than left to chance, mirroring
  px-z5m's `"pop is currently an unknown opcode"` guard at
  `test/predicator/instructions_test.exs:198-201`, so px-tbv.2 has an
  expectation to flip.
- **No opcodes, no ISA version bump, no `docs/isa.md` table edits.** The only
  isa.md change is one stale prose sentence in §6. `isa_sync_test.exs` checks
  tables, not prose.
- **No `Predicator.execute/2`.** px-tbv.2.
- **No control flow** (`if`, `while`) in the statement grammar. Out of scope for
  4.0 by ADR-0001:107-109.
- **`:eq` is not removed from `comparison_op/0`.**
  `{:comparison, :eq, left, right, pos}` stays a legal, fully supported AST node
  that compiles to `["compare", "EQ"]`; only the *parser* stops producing it
  from source. Removing the tag would break hand-built ASTs for no gain.
- **No explicit `ContextLocation` clause for the new nodes.** They reach its
  catch-all (`context_location.ex:307-309`) and read as `invalid_node`, which is
  correct - assigning to a program or an assignment is nonsense, and neither is
  reachable through `resolve_expression/2`, which parses with the *expression*
  entry point. A test pins that behavior (Phase 3) so it is a decision rather
  than an accident.
- **No runtime key validation at parse time.** `a[len(b)] = 1` parses; whether
  the key resolves is `ContextLocation`'s runtime job, unchanged.
- **No empty statements.** `""`, `";"`, and `"a;;b"` are parse errors. Only a
  single trailing `;` is optional, per the grammar's `[";"]`.
- **No version bump or changelog promotion.** px-tbv.5, human-gated.
- **No sibling changes.** px-tbv.4, closed.

## Implementation Approach

Five phases, ordered so each ends green on `mix quality`.

The `=` break and the statement grammar are **separate phases**, in that order.
Removing `=` from the expression grammar breaks roughly ten test files at once;
landing that migration alone, with nothing else moving, makes `mix test` the
forcing function that finds every call site a grep would miss. Adding the
statement grammar afterwards is then purely additive and cannot be confused with
migration churn. The intermediate commit is a real state - `=` is an error and
assignment does not exist yet - but the gate is green and it is one commit long.

The statement layer itself is a **thin backtracking probe** over the unchanged
expression grammar. At each statement boundary, parse a `postfix`-level lhs
candidate and look at the next token. If it is `:eq` and the candidate is
location-shaped, commit to an assignment and parse the rhs with the ordinary
`parse_expression/1`. Otherwise discard the probe - `parser_state` is a plain
immutable map, so discarding costs nothing - and fall through to
`parse_expression/1` from the original state.

The probe is what buys the good error message. The alternative considered and
rejected was to have `parse_comparison/1` simply *stop* on `:eq` and leave it
unconsumed, letting the caller decide: that is single-pass, but a nested `=`
then surfaces as `"Expected ')' but found '='"` from the paren/list/argument
closer rather than the pointed fix-it message the AC requires. Threading a
"top-level" flag through the precedence chain to fix that touches six descent
sites and is more fragile than re-parsing one `postfix` production per
statement.

## Phase 1: The `;` token

### Overview

Adds `:semicolon`, the only new lexical element the grammar needs. Independent
of everything else.

## Phase 2: `=` leaves the expression grammar

### Overview

`=` becomes a parse error in expression position with a pointed fix-it message;
the 3.7 deprecation machinery is deleted; every `=`-as-equality call site in the
suite and in the lib doctests migrates to `==`. These land together because the
grammar change alone leaves the suite red.

### Changes Required

#### 1. `lib/predicator/parser.ex` - remove the deprecation machinery

**Changes**: delete `warn_deprecated_equals/1` (`parser.ex:288-310`),
`deprecation_warnings_enabled?/0` (`parser.ex:312-315`), the
`warn_deprecated_equals(tokens)` call at `parser.ex:265`, `require Logger`
(`parser.ex:93`, now unused), and the
`> #### Deprecated: = as equality` moduledoc admonition (`parser.ex:34-39`).

#### 2. `lib/predicator/parser.ex` - reject `:eq` in `parse_comparison/1`

**Changes**: remove `:eq` from the operator guard at `parser.ex:467-478`, and
add a dedicated clause **before** it in the same `case peek_token(...) do`:

```elixir
{:eq, op_line, op_col, _len, _value} ->
  {:error,
   "'=' is not an equality operator - use '==' for equality. " <>
     "Assignment is only valid at the start of a statement.", op_line, op_col}
```

`:eq` no longer reaches the `_other_op_type` normalization at
`parser.ex:484-490`. `comparison_op/0` (`parser.ex:188-189`) keeps `:eq` - the
node shape stays legal, the parser just stops building it.

Update the moduledoc grammar block at `parser.ex:20` to drop
`"=" (deprecated) |` from the `comparison` production.

#### 3. `lib/predicator/parser.ex` and `lib/predicator/lexer.ex` - doctests

**Changes**: `parser.ex:251-253` and `parser.ex:255-257` switch to `==` with
`:equal_equal` in the expected AST and corrected columns. `lexer.ex:135-141`
switches to `name == "John"` with an `:equal_equal` token (discretionary - it
does not break, but it teaches removed syntax).

#### 4. `test/predicator/equals_deprecation_test.exs` -> replaced

**Changes**: delete the file. Add `test/predicator/equals_grammar_break_test.exs`
covering:

- the fix-it error, with position, from `Parser.parse/2`, `Predicator.parse/2`,
  `Predicator.evaluate/3`, `Predicator.evaluate!/3`, `Predicator.compile/1`,
  and `Predicator.context_assign/4`
- the fix-it error from every *nested* expression position: parenthesized
  subexpression `"(a = 1) and b"`, list element `"[a = 1]"`, function argument
  `"len(a = 1)"`, bracket key `"x[a = 1]"`, object value `"{k: a = 1}"`
- `==`, `===`, `!=`, `!==`, `>=`, `<=` all unaffected
- a `=` inside a string literal is still just text
- a hand-built `{:comparison, :eq, left, right, nil}` still compiles to
  `["compare", "EQ"]` - the instruction set is untouched
- setting `config :predicator, deprecation_warnings: false` has no effect and
  no warning is logged on any path

#### 5. Suite-wide migration to `==`

**Changes**: every source string using `=` for equality moves to `==`, with
expected ASTs, instruction lists, positions, spans, and decompiled strings
updated to match. Files: `test/predicator_test.exs`,
`test/predicator/parser_test.exs`, `test/predicator/compiler_test.exs`,
`test/predicator/strict_equality_test.exs`,
`test/predicator/date_arithmetic_string_visitor_test.exs`,
`test/predicator/visitors/string_visitor_test.exs`,
`test/predicator/visitors/instructions_visitor_test.exs`,
`test/predicator/visitors/instructions_visitor_positions_test.exs`,
`test/predicator/integration/context_integration_test.exs`,
`test/predicator/lexer_test.exs`.

Hand-built `{:eq, ...}` **token** lists in `parser_test.exs` (lines ~426, 430,
448) that exist to test OR/NOT/precedence rather than `=` switch to
`:equal_equal` tokens. Hand-built `{:comparison, :eq, ...}` **AST** fixtures in
compiler/evaluator/visitor tests that never go through the parser stay as they
are - that shape is still supported, and keeping them is the coverage that
proves it.

Note: switching `=` to `==` shifts columns by one, so position and span
assertions in `parser_positions_test.exs`, `parser_spans_test.exs`, and

#### 6. `test/test_helper.exs`

**Changes**: the comment at lines 272-274 justifies `capture_log: true` by the
suite's `=` predicates. That rationale is gone. Keep `capture_log: true` (other
paths log), update the comment.

## Phase 3: The statement grammar

### Overview

Purely additive: the new node types, `Parser.parse_program/2`, and the
`Predicator.parse_program/2` façade. Nothing existing changes behavior.

### Changes Required

#### 1. `lib/predicator/parser.ex` - types

**Changes**: three new typedocs/types, placed after `ast/0`. They are
deliberately **not** added to `ast/0`.

```elixir
@typedoc """
An assignment statement: `location "=" expression`.

`location` is the raw access chain the parser built - an `{:identifier, ...}`
optionally wrapped in any number of `{:property_access, ...}` and
`{:bracket_access, ...}` nodes. It is kept as a chain rather than flattened to
a path because a bracket key may be an arbitrary expression, resolvable only
against a context; `Predicator.ContextLocation.resolve/2` does that at runtime.
The chain's depth is the segment count `["store", n]` needs (ADR-0001).
"""
@type assignment :: {:assignment, ast(), ast(), position()}

@typedoc """
One statement: an assignment, or a bare expression.
"""
@type statement :: assignment() | ast()

@typedoc """
A parsed statement sequence: `statement (";" statement)* [";"]`.

Produced only by `parse_program/2`. A program is never an `t:ast/0`: the
expression entry point cannot return one, and an expression consumer never has
to handle one.
"""
@type program :: {:program, [statement()], position()}

@typedoc """
Program parser result.
"""
@type program_result ::
        {:ok, program()} | {:error, binary(), pos_integer(), pos_integer()}
```

#### 2. `lib/predicator/parser.ex` - `parse_program/2`

**Changes**: public entry point mirroring `parse/2`'s state construction and
leftover gate, plus the statement loop.

```elixir
@spec parse_program([Lexer.token()], keyword()) :: program_result()
def parse_program(tokens, opts \\ []) when is_list(tokens) do
  state = %{tokens: tokens, position: 0, spans?: Keyword.get(opts, :spans, false) == true}
  # parse_statement, then parse_program_rest/2 looping on :semicolon,
  # then the same "did we consume everything" gate parse/2 uses,
  # reporting "Unexpected token ... after statement".
end
```

`parse_program_rest/2` consumes a `:semicolon`; if the next token is `:eof` or
end-of-input it stops (the optional trailing `;`), otherwise it parses another
statement and recurses. A `:semicolon` immediately following a `:semicolon`
falls into `parse_statement` and produces the ordinary "Unexpected token ';'"
primary-position error - empty statements are not allowed.

`parse_statement/1`:

```elixir
defp parse_statement(state) do
  case try_parse_assignment(state) do
    {:ok, _ast, _state} = ok -> ok
    {:error, _m, _l, _c} = error -> error
    :not_assignment -> parse_expression(state)
  end
end
```

`try_parse_assignment/1` probes `parse_postfix/1`, then decides on the next
token. If it is `:eq` and the candidate is location-shaped, consume the `=` and
parse the rhs with `parse_expression/1`, building
`{:assignment, lhs, rhs, binary_loc(state, {eq_line, eq_col}, lhs, rhs)}` - the
infix convention, so the point position is the `=` token and the span runs lhs
start to rhs end. If it is `:eq` and the candidate is not location-shaped,
return the location-shape error at the `=` token's position. Anything else
returns `:not_assignment` and the probe's parse result is discarded.

```elixir
@spec assignable_location?(ast()) :: boolean()
defp assignable_location?({:identifier, _name, _pos}), do: true
defp assignable_location?({:property_access, inner, _property, _pos}),
  do: assignable_location?(inner)
defp assignable_location?({:bracket_access, inner, _key, _pos}),
  do: assignable_location?(inner)
defp assignable_location?(_other), do: false
```

The `{:program, statements, pos}` slot: in position mode the `{line, column}` of
the program's first token; in span mode `{node_start(first), node_end(last)}` -
the statements only, **excluding** a trailing `;`, which is punctuation the node
does not own. Built through the existing `loc/3` so position mode pays nothing.

#### 3. `lib/predicator.ex` - `Predicator.parse_program/2`

**Changes**: the string-in façade beside `parse/2` (`lib/predicator.ex:439-446`),
tokenizing then delegating, propagating lexer errors as the same 4-tuple
`parse/2` does.

```elixir
@spec parse_program(binary(), keyword()) :: Parser.program_result()
def parse_program(source, opts \\ []) when is_binary(source) do
  case Lexer.tokenize(source) do
    {:ok, tokens} -> Parser.parse_program(tokens, opts)
    {:error, message, line, column} -> {:error, message, line, column}
  end
end
```

#### 4. `docs/architecture.md` - the node inventory

**Changes**: `docs/architecture.md:211-230` lists the AST node inventory. Add
`{:program, ...}` and `{:assignment, ...}` with a one-line note that they are
produced only by the program entry point. (Grammar-block and prose changes are
Phase 5; this is the inventory the new nodes belong in immediately.)

#### 5. Tests

**Changes**: a new `describe "parse_program/2"` in
`test/predicator/parser_test.exs` plus program coverage in
`test/predicator_test.exs`, covering:

- single-statement program; multi-statement `a = 1; b = 2`; trailing `;`
- an expression statement (`score > 85`) alone and mixed with assignments
- assignment to a property chain (`user.profile.name = 'Ada'`), a bracket
  (`items[0] = 1`), a mixed chain (`a.b[0].c = 1`), and a computed key
  (`a[k] = 1`)
- rhs is a full expression (`b = a + 1`, `b = x > 1 and y`)
- non-assignable lhs -> the location-shape error, **not** the `==` fix-it:
  `42 = 1`, `len(x) = 1`, `'s' = 1`, `[1] = 2`, `-a = 1`
- nested `=` -> the `==` fix-it error: `a = (b = 1)`, `a = b = 1`
- empty input, `";"`, and `"a;;b"` all error

- `spans: true` on a program: the program node's span covers all statements and

### Changed

## Performance Considerations

`try_parse_assignment/1` re-parses the statement's leading `postfix` production
on the non-assignment path: once as the probe, once inside the
`parse_expression/1` fallback. The cost is bounded by the leading location chain
of one statement, involves no re-lexing, and is paid once per statement rather
than per token. No acceptance criterion concerns parse throughput, so the probe
result is not memoized. If it ever matters, the fix is to thread the probe's
result into `parse_expression/1` as a pre-parsed left operand, which is a local
change to two functions.

## ISA Impact

**None.** This bead adds no opcode, retires none, and alters no opcode's
semantics, so ADR-0003's versioning obligation is not triggered and
`Predicator.isa_version/0` stays at `2`. `=` and `==` both compiled to
`["compare", "EQ"]` before this change and still do, so every stored instruction
list remains valid and cross-language interchange is unaffected - the break is
surface syntax only, exactly as `docs/isa.md` §6 and ADR-0002 record.

The one isa.md edit is a prose correction in §6 (Phase 5), not a table, opcode,
or version-history change. `store`, `pop`, their tier-6 reservation, and the
`"store"` / `"pop"` unknown-opcode guard tests in
`test/predicator/instructions_test.exs:189-201` are untouched and remain
px-tbv.2's to flip.

Nothing here belongs in the conformance corpus: `docs/isa.md` §8 records that
the corpus does not cover parse or lexer errors, so `area:conformance` is not
implicated.
