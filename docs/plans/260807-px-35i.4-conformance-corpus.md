# Cross-Language Conformance Corpus Implementation Plan

## Overview

Ship a checked-in, language-neutral JSON conformance corpus plus a manifest, so
a Ruby or JavaScript implementer can verify their compiler and evaluator
against predicator's instruction set one tier at a time, without an Elixir
toolchain. Beads issue: px-35i.4 (epic px-35i, ADR-0003).

The corpus is authored as minimal JSON cases and *completed* by the real
compiler and evaluator: `mix corpus.generate` fills in `instructions`,
`expected_result`/`expected_error`, `tier`, and `features`, and an ExUnit test
regenerates it in memory and byte-compares against the checked-in files, so a
semantic change nobody meant to make turns the gate red with a diff.

The design was settled in `docs/design/260806-px-35i.4-corpus-format-and-tooling.md`
(PR #81). This plan structures that design into landable phases, and makes the
few decisions the design doc left open.

## Current State Analysis

### What already exists

- **`docs/isa.md`** (px-35i.2, 395 lines) is the ISA specification: the opcode
  table with an **ISA version column and a tier column already filled in**
  (section 4), per-opcode semantics and error reasons (section 5), and the
  scope exclusions (section 6). The tier split the bead proposed "to argue
  with" has already been argued and written down there:

  | Tier | Name | Opcodes |
  |---|---|---|
  | 1 | core | `lit`, `load`, `compare`, `not`, `unary_bang`, `unary_minus`, `jump_if_falsy_or_pop`, `jump_if_true_or_pop`, `and`, `or` |
  | 2 | arithmetic | `add`, `subtract`, `multiply`, `divide`, `modulo` |
  | 3 | access | `in`, `contains`, `access`, `bracket_access`, `make_list` |
  | 4 | rich types | `object_new`, `object_set`, `duration`, `relative_date` |
  | 5 | functions | `call` |
  | 6 | statements | (none yet - reserved for `store`) |

  `docs/isa.md:126-143` also settles that **tier is a function of opcode only**,
  and that value-level requirements (dates, durations) are carried by feature
  tags rather than tiers.

- **`lib/predicator/instructions.ex`** (px-35i.3) holds `@opcode_isa`, a
  25-entry map of opcode to introducing ISA version, plus `isa_version/0` and
  `required_isa/1`. The map is **private**; the only way to ask about an opcode
  today is to probe `required_isa([[opcode]])`. It carries **no tier**.

- **`test/predicator/isa_sync_test.exs`** already parses `docs/isa.md`'s
  section 4 table and `lib/predicator/evaluator.ex`'s `execute_instruction/2`
  clause heads and binds both to the opcode map, asserting a literal count of
  25 to guard against a vacuously-passing regex. This is the pattern the tier
  binding should extend, not duplicate.

- **`Predicator.evaluate/3`** (`lib/predicator.ex:157-209`) accepts *either* a
  source string *or* an instruction list, with the same context and options.
  That dual entry point is exactly the two conformance surfaces the corpus
  needs, and it already exists.

- **`Predicator.compile/1`** (`lib/predicator.ex:352`) returns
  `{:ok, instructions} | {:error, binary()}`.

### Constraints verified in this checkout

- **No JSON dependency exists or may be reintroduced.** `mix.exs`'s `@deps`
  contains `castore`, `dialyxir`, `ex_doc`, `credo`, `excoveralls`,
  `ex_quality` - all `only: [:dev, :test]`. `jason` appears in `mix.lock` only
  as a transitive dependency of credo, ex_quality, and excoveralls; predicator
  itself has **zero runtime dependencies**. px-tbv.6 is closed (merged via
  PR #80), `mix.exs` declares `elixir: "~> 1.18"`, the toolchain here is Elixir
  1.18.3/OTP 27, and `lib/predicator/functions/json_functions.ex:39,45` already
  uses the built-in `JSON.encode!/1` and `JSON.decode/1`. **The corpus work
  therefore uses the built-in `JSON` module and adds no dependency of any
  kind - dev, test, or runtime.**

- **Hex package files list** (`mix.exs`, `package/0`) is currently
  `~w(lib/predicator* mix.exs README.md LICENSE CHANGELOG.md)`. It deliberately
  excludes `docs/`. The corpus must be added to it explicitly.

- **Coverage floor is 90%** (`coveralls.json`), enforced on everything under
  `lib/`. Any generator code placed in `lib/` is subject to it. `skip_files`
  today lists only `test/support` (which does not exist yet).

- **`.quality.exs`** compiles with `warnings_as_errors: true` and runs
  `credo --strict`; the `loop` profile skips dialyzer and coverage. Dialyzer's
  `plt_add_apps` already includes `:mix`, so a `Mix.Task` module in `lib/`
  type-checks without a PLT change.

- **`conformance/` does not exist yet.** This is greenfield.

### Key discoveries

- The tier table in `docs/isa.md:130-137` means the plan does **not** need to
  invent a tier split; it needs to make that table executable and keep the two
  from drifting.
- `docs/isa.md:355-359` records that `relative_date` **reads the system clock**,
  so "a conformance case exercising it cannot pin an exact expected value".
- `docs/isa.md:310-317` records that `object_set` on a non-map **crashes rather
  than returning `{:error, _}`** and is explicitly unspecified behavior.
- `docs/isa.md:225-232` records that ordering comparisons between two maps are
  **unspecified for siblings** and "the conformance corpus does not exercise
  them" - a promise this plan must keep.
- `docs/isa.md:88-94` records that `on_unbound` is an *evaluation option*, not
  part of the ISA.
- `Predicator.evaluate/3` can return `{:ok, :undefined}`
  (`lib/predicator.ex:199-200`), so `:undefined` is a first-class expected
  result the corpus must be able to encode.
- ADR-0001's `["and"]`/`["or"]` are accepted by the evaluator forever but never
  emitted by the compiler (`docs/isa.md:234-243`), so those cases exist only on
  the evaluator surface and have no `source`.

## Desired End State

A `conformance/` directory at the repo root, shipped in the hex package:

```
conformance/
  README.md              runner contract, tagged values, never-skip, how to add a case
  cases/*.json           authored source - minimal cases, one file per feature group
  corpus/tier-N.json     shipped corpus, generated, one file per tier
  manifest.json          ISA version, tier/opcode table, case counts, content hash
  schema/case.json       JSON Schema for an authored case
  schema/corpus.json     JSON Schema for a shipped tier file
  schema/manifest.json   JSON Schema for the manifest
  schema/report.json     JSON Schema for a runner's report - result enum is ["pass","fail"]
```

Verification that the end state holds:

- `mix corpus.generate` regenerates `conformance/corpus/` and
  `conformance/manifest.json` deterministically; running it twice on an
  unchanged tree produces a byte-identical result and no git diff.
- `mix test test/predicator/conformance/` is green, including a **staleness
  test** that regenerates in memory and byte-compares against the checked-in
  files.
- A deliberate semantic change (e.g. altering an evaluator clause) turns that
  staleness test red, naming the case ids whose results moved.
- Placing a case in the wrong tier is impossible: tier is *computed* from the
  instructions. Authoring a `tier` that disagrees fails generation naming the
  case.
- `mix hex.build` (build only - **never publish**, per CLAUDE.md) lists the
  `conformance/` files in the tarball.
- `docs/isa.md` points at the corpus.
- Full `mix quality` is green, coverage above 90%.

## What We're NOT Doing

- **Not covering surface syntax.** The `=` vs `==` grammar break (ADR-0002)
  produces identical instructions (`["compare", "EQ"]`), so a source-level
  corpus would encode a divergence that does not exist. `docs/isa.md:371-375`
  already says so.
- **Not covering parse or lexer errors.** Every authored `source` must compile;
  a source that fails to compile is a generator error, not a case.
- **Not covering `relative_date`** (clock-dependent, cannot pin an expected
  value) or **`object_set` on a non-map** (unspecified, crashes). Both are
  named as known-uncovered in `conformance/README.md`. See Open Questions.
- **Not covering `GT`/`LT`/`GTE`/`LTE` between two maps** - `docs/isa.md`
  promises the corpus does not exercise them.
- **Not covering the `on_unbound: :error` policy** - an evaluation option, not
  part of the ISA. All cases run with default options.
- **Not migrating the existing 16k-line ExUnit suite.** It stays authoritative
  for Elixir-internal behavior. It contributes a one-time seed of statically
  extractable assertions and, thereafter, a coverage checklist.
- **Not writing a sibling runner.** Runners are per-language and per-sibling; a
  reference runner spec belongs to px-35i.8.
- **Not writing the report validator packaging** (sh+jq vs spec-only) - px-35i.8.
- **Not deciding CI regeneration mechanics for sibling-authored PRs** - px-9ab.
- **Not retiring redundant ExUnit assertions.** Its own bead if ever wanted.
- **No ISA change.** No opcode is added, removed, or altered, so this plan
  carries no `## ISA Impact` section. `Predicator.Instructions` gains a tier
  accessor, which is API surface, not instruction set.

## Implementation Approach

### The generation mechanism (the decision this plan makes)

**Chosen: a declarative, language-neutral authored source, completed and
verified by the real Elixir pipeline.** Authored cases are hand-written JSON in
`conformance/cases/`. `mix corpus.generate` runs each through the real compiler
and the real evaluator and fills in everything derivable.

**This departs from the bead description's literal wording** - "Generated from
the existing suite rather than hand-written". The bead's own notes are why: of
310 `Predicator.evaluate` assertions in the suite, only **75 are fully static**;
152 take their context from a bound variable that cannot be resolved without
executing setup, 76 carry a third `opts` argument, 26 assert error shapes, 11
feed instruction lists. A static AST pass therefore reaches about a quarter of
the suite. The description's *intent* - "so it cannot drift from behavior" - is
preserved exactly, and arguably better: it is served by round-tripping every
case through the real pipeline at generation time plus a byte-compare staleness
test, not by where the case text came from.

The three literal mechanisms and why each fails:

| Mechanism | Verdict |
|---|---|
| Static extraction from the ExUnit files | ~25% coverage, and fragile against ordinary test refactoring - a renamed variable silently shrinks the corpus. **Rejected as the ongoing mechanism**; used once, as a seed. |
| Runtime capture (instrument `evaluate/2,3` during a generation run) | Near-total coverage, since contexts are resolved terms by then. But it captures whatever the suite happened to call, needs dedup and curation forever, produces **unstable case ids** - fatal for px-35i.8's ratchet registry, which references ids - and enshrines any bug a test currently asserts. **Rejected as the source**; kept as a coverage instrument (Phase 6). |
| A declarative source generating both the ExUnit tests and the corpus | Cleanest end state, but forces a 16k-line test migration before a single corpus case exists. **Rejected on cost**; nothing here forecloses it later. |
| **Authored JSON completed by the real pipeline (chosen)** | Stable human-chosen ids, no migration, curation is authoring rather than pruning, and behavior still comes from the real compiler and evaluator. Costs: cases must be written, and coverage is what someone wrote rather than what the suite happens to hit - which Phase 6's coverage report answers. |

Two further constraints force the authoring format:

- The bead's user-added requirement: **a sibling implementer must be able to
  add a case and run the corpus without an Elixir toolchain.** That rules out
  `.exs` authoring outright.
- JSON over YAML: YAML parsing itself diverges across languages (YAML 1.1 vs
  1.2 boolean coercion for `no`/`on`, Psych's implicit timestamp parsing,
  integer-vs-string ambiguity). A conformance corpus whose *authoring layer*
  can be read differently by Ruby and JavaScript would smuggle in the exact
  class of divergence the corpus exists to eliminate. JSON also needs no
  dependency in Elixir 1.18 or in any sibling's standard library. The cost is
  no comments, mitigated by an optional free-text `notes` field on every case.

### The tier check (mechanical, not editorial)

Tier is **computed**: `tier(case) = max(tier(opcode) for opcode in
instructions)`, where the opcode-to-tier map lives in
`Predicator.Instructions` beside the existing opcode-to-ISA-version map, and
`test/predicator/isa_sync_test.exs` binds it to `docs/isa.md`'s tier column the
same way it already binds the ISA column. There is **no second hand-maintained
opcode list anywhere in the corpus tooling** - the generator, the manifest, and
the tier check all read `Predicator.Instructions`.

Consequences that fall out for free:

- A case cannot be in the wrong tier, because nobody places it. An authored
  `tier` is treated as an *assertion*; disagreement fails generation naming the
  case, both tiers, and the opcode that forced the higher one.
- A new opcode that appears in any case's instructions without an entry in
  `Predicator.Instructions` fails generation - the tier map is self-maintaining.
- The manifest's tier table is generated, so it cannot drift from the code, and
  the isa_sync test keeps the code from drifting from `docs/isa.md`.

### Authored `expected` is an assertion, not data

The generator computes the real result. If an authored `expected` disagrees,
generation **fails loudly** naming the case and both values. This is how a
sibling author's belief about semantics gets checked against Elixir's behavior
rather than silently overwritten: a disagreement is either a bug here or a
misreading of `docs/isa.md`, and both deserve a stop. `expected` is optional
but recommended, and Phase 5's seeded cases all carry one.

### Never-skip, expressed to siblings

The never-skip rule (statifier ADR-0006) governs a *sibling's runner*, which
this repo does not write. It is therefore expressed in the two places a sibling
actually reads:

1. **Structurally, in `conformance/schema/report.json`**: the per-case `result`
   enum is `["pass", "fail"]` with **no skip value**. A runner that hits a case
   whose feature it has not implemented must emit `fail` with a `reason` naming
   the feature. Skip is unrepresentable rather than merely discouraged - a
   report containing one fails schema validation in any language.
2. **Normatively, in `conformance/README.md`**, under a "Never skip" heading
   that states the rule, the reason (a skipped case reads as a pass in every
   summary anyone actually looks at), and the tier mechanism that makes it
   affordable: an implementation that has only tier 1 runs only `tier-1.json`
   and gets a green, rather than skipping its way through the whole corpus.

The one adjacent case that is *not* a skip: an evaluator-only case
(`["and"]`/`["or"]`) has `"source": null` and is **absent from the compiler
surface's case set**, not skipped by it. The validator knows from the corpus
which case set each surface contains, so absence-because-inapplicable stays
distinguishable from a skip.

### Determinism

Deterministic output is what makes the byte-compare staleness test possible and
keeps corpus diffs reviewable. `JSON.encode!/1` does not guarantee map key
order, so the corpus is written by a **canonical encoder** in this repo that
sorts object keys explicitly, emits one case per line, and sorts cases by id.
`JSON.encode!/1` is still used for scalar/string escaping, so the escaping
rules stay the standard library's.

## Phase 1: Make the opcode/tier table executable

### Overview

Give `Predicator.Instructions` a public, tier-aware opcode table and bind the
tier column of `docs/isa.md` to it, before anything reads it. Small, useful on
its own, and lands without any of the corpus existing.

### Changes Required:

#### 1. Opcode table gains tiers and a public accessor
**File**: `lib/predicator/instructions.ex`
**Changes**: Replace `@opcode_isa`'s values with a two-field shape carrying
both the introducing ISA version and the conformance tier, sourced from
`docs/isa.md` section 4. Add public `opcodes/0` returning the whole table, and
`tier/1` returning `{:ok, tier} | {:error, EvaluationError.t()}` with the same
`"unknown_opcode"` reason `required_isa/1` already uses. `required_isa/1`'s
behavior and error values are unchanged.

```elixir
# opcode => %{isa: introducing ISA version, tier: conformance tier}
# Both columns are docs/isa.md section 4; isa_sync_test binds them.
@opcodes %{
  "lit" => %{isa: 1, tier: 1},
  "make_list" => %{isa: 2, tier: 3},
  # ...
}

@spec opcodes() :: %{optional(String.t()) => %{isa: pos_integer(), tier: pos_integer()}}
def opcodes, do: @opcodes

@spec tier(String.t()) :: {:ok, pos_integer()} | {:error, EvaluationError.t()}
def tier(opcode)
```

Tiers to enter, from `docs/isa.md:147-173`: tier 1 = `lit`, `load`, `compare`,
`not`, `unary_bang`, `unary_minus`, `jump_if_falsy_or_pop`,
`jump_if_true_or_pop`, `and`, `or`; tier 2 = `add`, `subtract`, `multiply`,
`divide`, `modulo`; tier 3 = `in`, `contains`, `access`, `bracket_access`,
`make_list`; tier 4 = `object_new`, `object_set`, `duration`, `relative_date`;
tier 5 = `call`.

#### 2. Bind the tier column to the doc
**File**: `test/predicator/isa_sync_test.exs`
**Changes**: Widen `@isa_table_row_regex` to capture column 6 (tier) alongside
columns 1 and 5, and assert every row's tier round-trips through
`Instructions.tier/1`. Add a test that the tier *names* table
(`docs/isa.md:130-137`) lists exactly the opcodes the map assigns to each tier,
so a new opcode added to one table and not the other is caught. Keep the
existing `@opcode_count 25` guard against a vacuous regex.

#### 3. Public API note
**File**: `lib/predicator/instructions.ex` moduledoc, `CHANGELOG.md`
**Changes**: Document `opcodes/0` and `tier/1` under `## [Unreleased]` /
`### Added`. Tier is defined as "a conformance-corpus grouping, a function of
opcode only", citing `docs/isa.md`.

### Success Criteria:

#### Automated Verification:
- [x] Full gate passes: `mix quality`
- [x] `mix test test/predicator/isa_sync_test.exs` green, with the tier assertions
- [x] Deliberately mis-tiering one opcode in the map turns isa_sync_test red
      naming that opcode (check by hand, then revert)
- [x] Coverage for `lib/predicator/instructions.ex` stays above 90%

#### Manual Verification:
- [ ] `Predicator.Instructions.opcodes()` in iex returns 25 entries whose tiers
      match `docs/isa.md`'s tier table by eye
- [ ] The moduledoc reads as one table with two columns, not as two tables

## Phase 2: Canonical JSON encoding and the tagged-value codec

### Overview

The two pure, dependency-free primitives everything downstream needs: a
deterministic JSON writer and the tagged encoding for values JSON cannot
represent. Pure functions, no file I/O, fully unit-testable, lands alone.

### Changes Required:

#### 1. Canonical encoder
**File**: `lib/predicator/conformance/json.ex`
**Changes**: `encode_canonical/1` walks a term and emits JSON with **object
keys sorted by codepoint**, no incidental whitespace, and scalars escaped by
delegating to `JSON.encode!/1`. Also `encode_lines/1`, which emits a list of
objects one per line (the shipped corpus format, so a case change is a one-line
diff). No dependency: built-in `JSON` only.

#### 2. Tagged-value codec
**File**: `lib/predicator/conformance/values.ex`
**Changes**: `to_json/1` and `from_json/1` over the tagged encoding. Plain JSON
scalars, arrays, and objects mean themselves; an object with a `$type` key is
always a tag.

```json
{"$type": "date", "value": "2026-08-06"}
{"$type": "datetime", "value": "2026-08-06T12:00:00Z"}
{"$type": "duration", "value": {"years":0,"months":0,"weeks":0,"days":3,"hours":0,"minutes":0,"seconds":0}}
{"$type": "undefined"}
```

`duration` carries the **normative seven-key map** from `docs/isa.md:100-106`
(all seven keys present, plus `milliseconds` only when a `ms`-family unit was
used) - see Open Questions for why this rather than the `["duration", units]`
operand pair shape. `to_json/1` returns `{:error, {:unencodable, term}}` for
anything outside the ISA value domain rather than raising. `from_json/1`
rejects an unknown `$type`.

#### 3. `$type` collision guard
**File**: `lib/predicator/conformance/values.ex`
**Changes**: `to_json/1` fails on a plain map containing a literal `"$type"`
key, so the tag namespace can never be ambiguous. The generator surfaces this
as a per-case error.

### Success Criteria:

#### Automated Verification:
- [x] Full gate passes: `mix quality`
- [x] Round-trip property tests: `from_json(to_json(v)) == v` for every ISA
      value type including `:undefined`, nested lists, nested maps, `Date`,
      `DateTime`, and a duration with and without `milliseconds`
- [x] `encode_canonical/1` is order-independent: two maps built by inserting
      the same keys in different orders encode byte-identically
- [x] A map containing `"$type"` returns an error, not a tag
- [x] Coverage for `lib/predicator/conformance/` above 90%

#### Manual Verification:
- [ ] A sample encoded case is readable as one line in a terminal and diffs
      cleanly against a one-field change

## Phase 3: The generator core and the authored case format

### Overview

The pure half of generation: read authored cases, run them through the real
compiler and evaluator, derive everything derivable, and return either a
completed corpus or a list of errors. No mix task, no files written yet - which
keeps this phase independently testable against fixtures.

### Changes Required:

#### 1. Authored case shape and schema
**File**: `conformance/schema/case.json`, plus a seed of authored tier-1 cases
in `conformance/cases/`
**Changes**: An authored case is minimal:

```json
{
  "id": "comparison/gt-int-true",
  "source": "score > 85",
  "context": {"score": 90},
  "expected": {"result": true},
  "notes": "boundary is exclusive; see comparison/gt-int-boundary"
}
```

- `id` - required, human-chosen, path-like, globally unique, **stable forever**
  (px-35i.8's ratchet registry references ids; the generator never renames).
- `source` **or** `instructions` - exactly one. `instructions` is for
  evaluator-only cases (`["and"]`, `["or"]`) that no source compiles to.
- `context` - optional, default `{}`, tagged-value encoded.
- `expected` - optional assertion, `{"result": ...}` or
  `{"error": {"type": "TypeMismatchError", "reason": "..."}}`.
- `tier`, `features` - optional assertions; both are computed.
- `notes` - optional free text, carried into the shipped corpus (JSON has no
  comments; this is the substitute).

#### 2. Generator
**File**: `lib/predicator/conformance/generator.ex`
**Changes**: `generate/1` takes decoded authored cases and returns
`{:ok, %{tiers: %{1 => [case], ...}, manifest: map}}` or
`{:error, [%{id: ..., problem: ...}]}` accumulating **all** failures rather
than halting on the first - a contributor fixing five cases should see five
errors.

Per case:
1. decode `context` through `Values.from_json/1`;
2. if `source`, compile with `Predicator.compile/1`; a compile error is a
   generator error (parse errors are out of scope);
3. evaluate via `Predicator.evaluate/3` with **default options** against the
   compiled or authored instructions;
4. record `expected_result` (tagged) or `expected_error`
   (`%{"type" => module short name, "reason" => reason}`; **message never**);
5. compute `tier` as `max` over `Predicator.Instructions.tier/1` of each
   opcode - an opcode not in the table is a generator error;
6. compute `features` from an opcode-and-value-to-tag table merged with any
   authored extras;
7. fail on: duplicate id, authored `expected` mismatch, authored `tier`
   mismatch, `$type` collision, both or neither of `source`/`instructions`.

#### 3. Feature tags
**File**: `lib/predicator/conformance/features.ex`
**Changes**: A single table mapping opcodes and value types to tags -
`comparison`, `strict_equality`, `short_circuit`, `arithmetic`, `membership`,
`access`, `objects`, `dates`, `datetimes`, `durations`, `functions`,
`legacy_logical`, `undefined`, `errors`. Tags are the finer cut *across* tiers
(bead description), so an implementation wanting one advanced feature early can
select for it, and a sibling reports what it lacks in these terms.

### Success Criteria:

#### Automated Verification:
- [x] Full gate passes: `mix quality`
- [x] Generator unit tests over fixture cases cover every failure mode: dup id,
      expected mismatch (result *and* error), tier mismatch, unknown opcode,
      uncompilable source, both/neither of source and instructions,
      `$type` collision
- [x] A case whose instructions include a tier-3 opcode computes `tier: 3`
      regardless of any authored value, and an authored `tier: 1` on it fails
      with a message naming the opcode
- [x] Errors accumulate: a fixture set with three bad cases reports three
- [x] Coverage above 90%

#### Manual Verification:
- [ ] The failure message for an `expected` mismatch is legible to someone with
      `docs/isa.md` open and no Elixir knowledge - it names the case id, the
      asserted value, and the computed value

## Phase 4: `mix corpus.generate`, the shipped artifact, and the staleness gate

### Overview

Turn the generator into files on disk, check them in, ship them in the hex
package, and make a stale corpus fail the suite. After this phase the
acceptance criteria are structurally satisfied; Phase 5 fills in breadth.

### Changes Required:

#### 1. The mix task
**File**: `lib/mix/tasks/corpus.generate.ex`
**Changes**: `mix corpus.generate` reads `conformance/cases/*.json`, runs the
generator, and writes `conformance/corpus/tier-N.json` (cases sorted by id, one
per line) and `conformance/manifest.json`. `--check` regenerates and diffs
without writing, exiting non-zero on drift, for CI. Failures print every
per-case error and exit non-zero. Kept thin - all logic is in
`Predicator.Conformance.*`, which is what keeps it coverable.

#### 2. The manifest
**File**: `conformance/manifest.json` (generated)
**Changes**:

```json
{
  "isa_version": 2,
  "corpus_hash": "sha256:...",
  "tiers": [
    {"tier": 1, "name": "core", "opcodes": ["and","compare","jump_if_falsy_or_pop", "..."], "case_count": 42, "file": "corpus/tier-1.json"}
  ]
}
```

`isa_version` from `Predicator.isa_version/0`; the tier table from
`Predicator.Instructions.opcodes/0` grouped by tier (so it cannot drift from
the code, and the isa_sync test keeps the code from drifting from the doc);
`corpus_hash` a `:crypto.hash(:sha256, ...)` over the canonical corpus content,
which is the pin px-35i.8's ratchet references. **`opcodes` is cumulative-safe
as stated**: the manifest documents the opcodes each tier *unlocks*, and the
README states that running tier N means running tiers 1..N.

#### 3. Staleness test
**File**: `test/predicator/conformance/corpus_freshness_test.exs`
**Changes**: Read the authored cases, regenerate in memory, byte-compare

## Phase 5: Corpus breadth, schemas, and the runner contract

### Overview

The editorial phase: enough cases that a sibling implementing a tier gets real
coverage, plus the language-neutral documents a sibling needs to consume them.
This is where the existing suite's 75 statically extractable assertions are
used, once, as seed candidates.

### Changes Required:

#### 1. Seed and author cases across tiers 1-5
**File**: `conformance/cases/*.json`
**Changes**: One file per feature group (`core.json`, `comparison.json`,
`arithmetic.json`, `membership.json`, `access.json`, `objects.json`,
`dates.json`, `durations.json`, `functions.json`, `legacy.json`,
`short_circuit.json`, `errors.json`).

Seeding: a throwaway script extracts the 75 fully-static
`Predicator.evaluate` assertions into candidate authored cases; they are
curated by hand (dedup, naming, tier spread) and committed; **the extractor is
then deleted**. It is scaffolding, not infrastructure - which is precisely why
the mechanism decision does not rest on it.

Authored beyond the seed, driven by `docs/isa.md` section 5: every `compare`
operator including both strict forms; the `1 == 1.0` true / `1 STRICT_EQ 1.0`
false pair `docs/isa.md:210-216` explicitly calls out as "worth a conformance
case"; `:undefined` propagation and rejection per opcode; the type-mismatch vs
`:undefined` distinction (`1 > "a"` is `:undefined`, not an error); the
short-circuit jump examples from `docs/isa.md:325-343` including
`undefined AND x` vs `undefined OR x`; `divide` zero-before-type and
`modulo`'s no-float-zero asymmetry; `make_list` source order and `count: 0`;
the `and`/`or` legacy evaluator-only cases with `"source": null`.

**Coverage rule, enforced by a test rather than by taste**: every opcode in
`Predicator.Instructions.opcodes/0` appears in at least one case, except the
two documented exclusions (`relative_date`, and `object_set` on a non-map -
`object_set` itself is covered via its normal post-`object_new` form). A new
opcode with no case turns the suite red.

#### 2. Remaining schemas
**File**: `conformance/schema/corpus.json`, `manifest.json`, `report.json`
**Changes**: JSON Schema (draft 2020-12) for each. `report.json`'s per-case
`result` enum is exactly `["pass", "fail"]` - the structural half of never-skip.
A test validates the generated artifacts against their own schemas, so a schema
that drifts from the generator is caught here rather than in a sibling's CI.

#### 3. The runner contract
**File**: `conformance/README.md`
**Changes**: The document a sibling implementer reads first. Sections: what the
corpus is and what it is not (no surface syntax, no parse errors - point at
`docs/isa.md` section 6); the two surfaces (evaluator: run `instructions`,
compare to `expected_result`/`expected_error`; compiler: parse `source`,
compare emitted instructions structurally - and a `"source": null` case is
absent from the compiler surface, not skipped); the tagged-value encoding,
normatively; **error type and reason are normative, error message is not**;
tiers, and that running tier N means tiers 1..N; **the never-skip rule**, its
reason, and the fact that the report schema makes skip unrepresentable; how to
add a case without any Elixir (edit `conformance/cases/*.json`, validate
against `schema/case.json` with any JSON Schema tool, open a PR - a maintainer
or CI regenerates); the known-uncovered list with reasons.

#### 4. Point the spec at it
**File**: `docs/isa.md`, `CHANGELOG.md`, `README.md`
**Changes**: `docs/isa.md` gains a short section pointing at
`conformance/README.md` as the executable form of the spec, and restates the
corpus's scope boundary (no surface syntax, no parse errors) so nobody reads it
as covering them. `CHANGELOG.md` gets an `## [Unreleased]` entry. `README.md`'s
cross-language section points at the corpus as the way a sibling verifies a
claim - the versioned-contract framing ADR-0003 asks for, not a parity deficit.

- [x] Every generated artifact validates against its own JSON Schema

## Testing Strategy

### Unit Tests
- `Predicator.Instructions.opcodes/0` and `tier/1`: every opcode, an unknown
  opcode, the error struct shape.
- Canonical encoder: key-order independence, escaping delegation, one-per-line
  output.
- Tagged values: round-trip for every ISA value type, unknown `$type`,
  `$type` collision, unencodable term.
- Generator: every failure mode listed in Phase 3, error accumulation, computed
  tier vs asserted tier, computed features.
- Feature tags: opcode-derived and value-derived tags, authored extras merged.

### Integration Tests
- `corpus_freshness_test.exs`: regenerate in memory, byte-compare against the
  checked-in files. The load-bearing test of this whole bead.
- Schema conformance: every generated artifact validates against its schema.
- Opcode coverage: every opcode except documented exclusions has a case.
- Doc binding: `isa_sync_test.exs` extended to the tier column and the tier
  names table.

### Manual Testing Steps
1. Change an evaluator clause, run `mix test` - the staleness test must fail
   naming affected case ids. Revert.
2. Mis-tier an opcode in `Predicator.Instructions` - isa_sync_test must fail
   naming it. Revert.
3. Author a case with a wrong `expected` - `mix corpus.generate` must fail
   naming the case and both values.
4. `mix hex.build`; inspect the tarball for `conformance/`. **Never
   `mix hex.publish`** (CLAUDE.md: no trigger exists).
5. Read `conformance/README.md` cold, as a sibling implementer.

## Performance Considerations

Generation runs the real compiler and evaluator once per case. At the expected
scale (low hundreds of cases) that is well under a second; the staleness test
does the same work inside the suite, so it is a per-run cost of the same order
as a handful of existing integration tests. The canonical encoder is a single
term walk. Nothing here is on a hot path, and nothing is added to the library's
runtime.

## Open Questions

Per this repo's planning rules these are resolved with a stated assumption so
the plan stays executable; each names what would reopen it.

1. **Duration tag shape.** The design doc left open whether a `duration` tag
   carries the unit map or a string in predicator's literal syntax.
   **Assumption: the normative seven-key map from `docs/isa.md:100-106`**
   (all seven keys present and defaulting to 0, plus `milliseconds` only when a
   `ms`-family unit was used). Rationale: `docs/isa.md` already declares that
   shape normative, so the tag adds no second definition, and a sibling decodes
   it with plain field reads rather than a parser - and a duration string would
   be surface syntax, which the corpus excludes. Reopen if a sibling's duration
   type cannot represent a seven-key map without loss.

2. **`relative_date` coverage.** Its result depends on the system clock
   (`docs/isa.md:355-359`), so no case can pin an expected value.
   **Assumption: excluded from the corpus in this bead**, listed in
   `conformance/README.md`'s known-uncovered section with the reason, and
   excluded from the Phase 5 opcode-coverage test by an explicit list rather
   than silently. A clock-injection seam would make it coverable and is its own
   bead if wanted.

3. **`object_set` on a non-map.** `docs/isa.md:310-317` records that the Elixir
   evaluator crashes rather than returning `{:error, _}`, and calls it
   unspecified. **Assumption: not covered.** `object_set` in its normal
   post-`object_new` form is covered, so the opcode itself is not exempt.

4. **Corpus size per tier.** The design doc left the initial case count
   editorial. **Assumption: no target number; the bar is the mechanical
   coverage rule** - every opcode has at least one case, plus every distinct
   error path named in `docs/isa.md` section 5, plus every `compare` operator.
   A count is a proxy for the thing the rule states directly, and only the rule
   is testable.

5. **`expected_error` granularity.** `docs/isa.md:84-87` says error *types* are
   normative and messages are not, but section 5 also names specific reasons
   (`division_by_zero`, `modulo_by_zero`, `invalid_duration_unit`).
   **Assumption: `type` and `reason` are both normative and both checked;
   `message` is never carried in the corpus.** Reasons are enumerated in the
   spec, so they are part of it; prose is not. Reopen if a sibling's idiom
   cannot produce a matching reason token, in which case `reason` becomes
   advisory and moves to `notes`.

6. **Where the `and`/`or` legacy cases sit.** They are tier 1 by opcode, and a
   v1 sibling must run them. **Assumption: they stay in tier 1 with
   `"source": null` and the `legacy_logical` feature tag**, so a sibling can
   select them out by tag if it has taken px-tbv.9's retirement early, without
   the tier moving.

7. **Shipped `instructions` operands containing `Date`/`DateTime`/duration
   values were not tagged-value encoded before Phase 5.** Phases 2-4 never
   authored a case whose compiled `instructions` carried one of these as a
   `lit` operand (e.g. `#2024-01-15# + 3d` compiles to
   `["lit", ~D[2024-01-15]]`), so `Predicator.Conformance.JSON`'s canonical
   encoder - which sorts and escapes but does not know the ISA value domain -
   never had to encode one, and `Predicator.Conformance.Generator` shipped the
   raw compiled `instructions` list as-is. The first tier-4 date/duration case
   authored in this phase crashed `mix corpus.generate`
   (`Protocol.UndefinedError`, `Enumerable` not implemented for `Date`), since
   a struct is `is_map/1`-true and the encoder's map clause tried to
   `Enum.map/2` over it. **Resolution: `Generator.generate_case/2` now
   round-trips the resolved `instructions` list through
   `Predicator.Conformance.Values.to_json/1` before shipping it** (added as
   `encode_instructions/1`, a private function), the same tagged-value codec
   already used for `context` and `expected_result`/`expected_error` -
   `to_json/1` already walks nested lists generically, so this required no
   change to `Values` itself, only to where `Generator` calls it. This is the
   conservative reading: the codec's own moduledoc says the tagged encoding
   applies "everywhere a predicator value appears in a case", and
   `instructions` is exactly that. `conformance/README.md`'s tagged-value
   section and `conformance/schema/corpus.json`'s `instructions` field
   description now state this explicitly. Reopen only if a future opcode adds
   an operand shape `to_json/1` cannot represent.
